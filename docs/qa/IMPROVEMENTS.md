## 1. 장부 쓰기의 DB 단위 단일 작성자 보장

- **문제**: 장부·정기 작업의 '한 번만' 보장이 JVM 안의 `ReentrantLock`(`PaperLedgerService.exclusively`)과 작업별 `running` 플래그에만 기댑니다. 같은 DB에 프로세스가 둘이면
  (dev-backend + compose, 장래 복제본) 스탑 이중 체결과 현금 불일치가 생깁니다(QA-251에서 재현 — STOP 체결 2, 현금 대조 어긋남). DB가 막는 것은 `paper_fills.order_id` 유일 제약뿐입니다.
- **제안**: 책 처리 트랜잭션 첫머리에서 `SELECT … FROM paper_book_state WHERE book_code = ? FOR UPDATE`로 책 행을 잡고 잠금 안에서 `last_processed_collected_at`을 다시 확인
  (READ COMMITTED에서 두 번째 트랜잭션은 커밋된 행을 보고 건너뜀 — 범위가 책 단위라 가장 좁음). 또는 `pg_advisory_xact_lock(고정 키)`, 정기 작업 기동 때 `pg_try_advisory_lock`으로
  리더 하나만(ADR 0011이 알림에서 예고한 방식). QA-251의 장부 두 벌 시험을 회귀 시험으로.
- **기대 효과**: 되돌릴 수 없는 장부 손상을 DB 단계에서 막음(위험 1순위). 설정·프레임·알림 등 다른 단일 프로세스 가정도 같은 방식으로 옮길 길이 생김.
- **위험·비용**: 중간(잠금 한 곳 + 시험 + ADR). 잠금 대기가 정기 작업 시간에 더해짐 — 책 단위면 작음.
- **승인**: 필요 — 장부 구조 변경.

## 2. 장부 불변식 점검을 배포·진단에 붙임

- **문제**: 이번에 쓴 장부 불변식 17개(현금 ≥ 0, 체결 대조 현금·보유, FILLED만 체결, 시작 전 계좌 무체결, 비운용 계좌 대기 주문 없음 등)는 사람이 SQL로 돌려야만 확인됩니다.
- **제안**: 읽기 전용 점검 SQL(`scripts/qa/paper-invariants.sql`)을 두고 `deploy.sh` 배포 뒤 요약과 `make doctor`에서 실행해 위반이 있으면 `경고:`를 찍습니다.
- **기대 효과**: 배포·복원 직후 장부 손상을 바로 알 수 있음(되돌리기 판단이 빨라짐).
- **위험·비용**: 작음. 읽기 전용이라 운영 영향 없음.
- **승인**: 불필요.

## 3. AI 호출의 '응답 뒤 보호'를 한 곳으로, 계좌2 소상한은 호출 기록으로

- **문제**: 모델 응답을 받은 뒤 생기는 예외를 처리하는 방식이 경로마다 다릅니다(결정은 persist try, 복기는 persist 안의 classify, 장중 확인은 `called` 집합, 프레임 제안은 보호 없음).
  그래서 classify 같은 앞 단계 예외가 틈으로 빠져 과금 재호출·정기 결정 누락이 생깁니다(QA-252). 계좌2 소상한(`claude2.maxCallsPerCycle`)은 결정 행으로만 세어 행을 남기지 못한 호출
  (출발 실패·응답 뒤 예외)이 셈에서 빠집니다.
- **제안**: `ClaudeDecisionPipeline.send`·`ReviewService`·`FrameworkService`의 호출 직후에 '응답 뒤 보호'를 한 곳에 둠 — `calls.record` 뒤에 나는 어떤 예외든 그 호출을 '부름'으로
  표시하고 실패 행으로 남기며 다시 부르지 않음. `StructuredSchema.validate`가 예외를 던지지 않는다는 성질 시험(무작위 JSON 생성). 소상한은 호출마다 계좌·주기를 적는 호출 기록으로 셈.
- **기대 효과**: 과금 재호출·정기 결정 누락의 갈래를 한 번에 막고, 소상한이 실제 과금 호출 수와 같아짐.
- **위험·비용**: 중간. 소상한 셈이 바뀌면 지금보다 일찍 막히는 경우가 생김(막는 쪽).
- **승인**: 보호 일원화는 불필요, 소상한 셈 방식은 필요(명세 §5-3 변경).

## 4. 시험 격리·순서·게이트 점검 보강

- **문제**: 수집기와 백엔드 시험이 같은 `macrodash_test`를 쓰고 여러 세션이 같은 PC에서 동시에 `make test`를 돌려 다른 스위트의 스키마가 판정에 섞입니다(QA-275). 모듈 전역 래치를
  되돌리지 않아 순서에 기대는 시험이 생기고(QA-276), 수집기 시험은 기본 DATABASE_URL(5432/macrodash)로 실제 접속할 수 있습니다(QA-277). 그 밖에 회귀 영역이 찾은 공백 —
  모의 매매 `@Scheduled` 10개 중 5개는 `PAPER_ENABLED=false` 게이트 시험이 없음, 수집기 토큰 시험의 보호 경로 목록이 손으로 적은 것이라 `/collect/task`·`/live/*` 6경로가 빠짐,
  되돌릴 수 없는 누적 이력을 지키는 태스크 가드(`task_radar_rankings`의 isHistorical, `task_fed_liquidity`의 isEstimated)가 시험되지 않음, 백업·복원 시험 12건이 이 PC에서 늘 건너뜀,
  커버리지 도구가 없어 '시험 없는 중요한 경로'를 매번 손으로 찾음.
- **제안**: 카탈로그 질의는 늘 `current_schema()`로, 스위트별 시험 DB 이름(백엔드 `macrodash_test`, 수집기 `macrodash_collector_test` — Makefile·CI·DEVELOPMENT 함께). conftest의 autouse
  fixture에서 알려진 전역 래치를 한곳에서 비우고 CI에 순서 섞기(seed 고정) 실행 하나(수집기는 15줄짜리 플러그인으로도 됨, vitest `--sequence.shuffle`, JUnit `MethodOrderer$Random`).
  수집기 conftest에서 DATABASE_URL을 닿지 않는 주소로 정하고 dbname이 `_test`로 끝나지 않으면 실패하는 가드. 리플렉션으로 `feature.paper`의 모든 `@Scheduled`를 `enabled=false`로 불러
  의존성 호출 0을 보는 시험 하나. `app.routes`를 돌며 공개 경로를 뺀 모든 경로가 토큰 없이 401인지 보는 시험. 누적 이력 가드 태스크 시험 두 개. psql·pg_dump가 없고 docker가 있으면
  postgres:16-alpine 대역을 PATH 앞에 두는 conftest(이번에 12/12 통과 확인). CI에 JaCoCo(0.8.16)·pytest-cov를 보고서 전용으로(문턱 없이, 이번 줄 91%·문장 87%가 기준선).
- **기대 효과**: 동시 실행 거짓 실패·순서 의존·운영 DB 접촉을 커밋 단계에서 막고, 새 정기 작업이 게이트 없이 들어오는 것과 누적 이력 오염 회귀를 잡음.
- **위험·비용**: 작음~중간(Makefile·CI 두 잡·문서). 두 `make test`가 동시에 돌 때 백엔드끼리의 간섭은 DB 이름을 나눠도 남음(미검증).
- **승인**: 시험 코드만 바꾸는 것은 불필요. 시험 DB 이름 분리(Makefile·CI·문서)와 커버리지 도구(프로젝트 의존성)·순서 섞기 플러그인(새 의존성일 때)은 필요.

## 5. 배포·종료·복구 절차 보강

- **문제**: backend 컨테이너에 `stop_grace_period`가 없어 compose 기본(이 PC는 약 3초) 뒤 SIGKILL되고 Spring 정상 종료 단계 상한(30초)보다 짧습니다 — SSE나 수집기를 기다리는 요청이 있으면
  종료 정리가 안 돎(QA-257), 정기 작업의 Claude 호출 중 배포 때 동작은 미확인. `deploy.sh`는 `up --wait`가 실패하면 exit 1만 하고 방금 뜬 배포 전 덤프 경로·되돌리는 절차를 알려 주지 않음.
  QA 도구 `qa-stack.sh backup`이 접두어를 넘기지 않아 배포 직전 덤프 되돌리기 연습 때 `COMPOSE_*`·`ENV_FILE`·`BACKUP_DIR`을 손으로 맞춰야 하고, 잘못 맞추면 로컬 스택 DB를 건드릴 위험.
  복원 전 백업은 정리되지 않는데 주석은 정리된다고 적음(QA-280).
- **제안**: `docker-compose.yml`·`compose.vultr.yml` backend에 `stop_grace_period`(예: 30초), `application.yml`에 `spring.lifecycle.timeout-per-shutdown-phase`(예: 20초)를 명시하고
  CI에서 '유예 > phase'를 대조(`ci.yml`이 postgres 유예를 보듯). SSE는 `ContextClosedEvent`로 먼저 닫음(코드). 정기 작업 스케줄러의 종료 대기도 함께 정함. `deploy.sh` 기동 단계를 감싸
  실패 시 '✗ 기동 실패 — 되돌리려면: git revert 후 deploy.sh, 데이터는 make restore F=<방금 덤프>'. `qa-stack.sh backup [접두어]`. pre-restore 정리 정책(정리할지·남길지)을 정해 주석·문서를 맞춤.
- **기대 효과**: 배포·재시작 때 정리 훅이 실행되고, 배포 실패 때 복구 시간이 짧아지며, 복원 연습이 안전해짐.
- **위험·비용**: 작음(설정 두세 줄·스크립트). 최악 정지 시간이 유예만큼 늘 수 있음.
- **승인**: 배포 설정(유예·phase)과 백업 보존 정책은 필요, 스크립트 안내·QA 도구는 불필요.

## 6. 백엔드 메모리 여유와 목적별 가벼운 조회

- **문제**: 백엔드 1GiB에 `MaxRAMPercentage=70`이라 힙 718MiB, 메모리가 1792MB 미만이라 JVM이 SerialGC를 고릅니다. 무거운 응답 몇 개가 겹치면 힙이 바로 고갈되고
  `ExitOnOutOfMemoryError`로 재기동합니다(QA-253 — 지난 회차 O-5와 같은 여유 부족). 여러 경로가 작은 칸 하나 때문에 결정 전체(패킷 60~165KB)를 읽습니다 — 실행 감사(QA-253),
  상태의 존재 확인(`decisionFor().isPresent()`), 개요의 노출 추이(결정 요약 500건 + 주문 COUNT — QA-282), 정기 작업·패킷 조립의 kind·response만 쓰는 곳. 홈이 1분마다 부르는
  `/api/status`·`/api/status/issues`는 수집기 `/status`를 거쳐 매번 `timeseries`(152만 행)·`observations`(80만 행)를 `COUNT(*)`로 셈(각 55~62ms, 혼합 부하에서 50ms 넘는 질의의 대부분).
- **제안**: PaperStore에 목적별 질의 — `targetExposureByDate(book)`, `decisionExists(book, date, kind)`, `decisionKind(id)`·`decisionResponse(id)`, 실행 감사용 묶음 질의. 큰 JSON 칸은
  실제로 그리는 경로(`/api/paper/decisions/{id}`)에서만 읽음. `paper_orders.decision_id`(+ `paper_checkpoints` 두 외래 키) 색인 마이그레이션. 무거운 paper 조회(execution·decisions
  limit 500)는 `ComputedCache`의 비싼 계산 자리 제한(QA-131)처럼 동시 실행 수를 묶음. 수집기 `store_stats`의 행 수는 `pg_class.reltuples` 추정치나 짧은 TTL 캐시로, 백엔드
  `DataStatusService.issues()`는 행 수가 없는 가벼운 경로를 씀. 그래도 여유가 필요하면 Vultr 4GB 기준 백엔드 `mem_limit` 1.25~1.5g이나 GC 명시를 정해 기록.
- **기대 효과**: 동시 요청 몇 건으로 백엔드 전체가 재기동하는 갈래를 줄이고, 홈 1분 주기 경로의 DB 전송량·CPU가 누적과 무관해짐(status/issues p50 70.6ms → 10ms대 추정).
- **위험·비용**: 작음~중간. 응답 모양은 그대로 두어야 함(시험으로 대조).

## 7. 수집기 요청 단위 시간 예산(yfinance 포함)

## 9. 오류 응답·입력 검증 일원화

- **문제**: 입력 오류가 운영 오류처럼 보입니다 — 깨진 퍼센트 인코딩·NUL·null 필드가 500 + ERROR 스택(QA-259·260·261), Tomcat 단계 HTML 400·CORS 평문 403·수집기 평문 500
  (QA-262), SSE에서 4xx가 500(QA-266), SessionFilter가 직접 쓰는 오류 응답에 CORS 머리글이 없음(QA-265). 배포 확인의 '백엔드 ERROR 0' 기준이 흐려지고 로그 위조 틈도 생김.
- **제안**: `ApiExceptionHandler`에 입력 계열 → 400·WARN 매핑(`InvalidParameterException`, 원인 SQLState 22021·22P05인 `DataIntegrityViolationException` — 23xxx 제약 위반은 가리지 않게),
  예외 원문은 응답·로그에 싣지 않음. 요청 Accept에 JSON이 없으면 본문 없이 상태만. JSON을 쓰는 ErrorReportValve와 CorsProcessor, 수집기 `Exception` 처리기. SessionFilter 오류 응답의
  공용 `writeError`(허용 출처면 ACAO·ACAC·Vary). 열거형 쿼리는 `Params.oneOf`로(레이더 consensus·history 등), `Set.of`·`List.of` 상수의 contains에 외부 값을 넣을 때 null을 먼저 거름을 리뷰 점검 항목으로.
- **기대 효과**: 'ERROR 0' 기준이 다시 의미를 가지고, 오류 형식이 문서(`docs/API.md` — 4xx·5xx 같은 모양)와 맞으며, 교차 출처 로그인 모드에서 만료가 /login으로 감.
- **위험·비용**: 중간. 처리기 순서·Spring Boot 기본 valve 대체 여부를 실제 판에서 확인해야 함.
- **승인**: 처리기·검증은 불필요. CORS·인증 처리 순서를 바꾸는 부분(CorsFilter로 옮기기 등)은 필요.

- **문제**: 모든 화면이 JS 약 505~534KB(gzip 전송)를 받고 미사용 JS가 188~213KiB로 추정됩니다. 가장 큰 청크(435KB, recharts 포함)가 차트 없는 화면에도 실림. 모바일 시뮬레이션 TBT

- **제안**: 차트 컴포넌트를 `next/dynamic`으로 늦게 불러오고, 화면별 청크 구성을 번들 분석 도구로 확인.
- **기대 효과**: 휴대폰 첫 화면 LCP·TBT 개선.
- **위험·비용**: 중간. 차트 자리 높이를 잡지 않으면 레이아웃 이동(QA-283)이 늘 수 있음.
- **승인**: 분석 도구(`@next/bundle-analyzer` 등)는 새 개발 의존성이라 필요, 동적 불러오기 자체는 불필요.

## 16. 작은 운영·화면 편의 묶음

각각 작고 독립적입니다. 결함이 아니라 설계·사용성 제안이라 묶어 둡니다.

- **벤치마크 리셋**: 리셋하면 출발일 종가로 같은 수량을 다시 사지만 출발일~지금 사이 순자산 줄은 돌아오지 않아 초과수익·베타 비교 표본이 줄어듦 — 확인 문구나 응답에 '순자산 이력은
  되살리지 않음'을 적거나(작음) 10년 이력 종가로 다시 씀(중간). 승인 불필요(문구) / 장부 데이터 재구성은 필요.
- **규칙 계좌 일시정지 중 수동 결정**: SKIPPED 행이 남아 재개 뒤 그날 다시 낼 수 없는데 Claude 계좌는 행을 남기지 않음(문서에 적힌 동작이지만 두 계좌가 다름) — 행 없이 400으로 맞추거나
  단추에 안내. 동작을 바꾸면 명세 확인 필요.
- **프레임 수동 편집**: 본문이 같아도 새 판이 생김(v1 본문 그대로 저장해 v2) — 바뀐 것이 없으면 400이나 `changed:false`. 패킷 `framework_version`이 의미 없이 바뀌지 않음. 승인 불필요.
- **추적하지 않는 CIK 화면**: 400(영구 실패)인데 '다시 시도'와 개발자용 안내 '(/api/sec13f/institutions 목록의 cik를 쓰세요)'·AI 요약 단추가 보임 — '추적하는 기관 목록으로' 링크. 승인 불필요.
- **오류 경계**: `error.tsx`·`global-error.tsx`가 없어 렌더 예외 때 Next 기본 화면(QA-270과 함께). 승인 불필요.
- **DonutChart 경고**: 시험마다 React 'key prop is being spread into JSX' 경고 — `components/charts/index.tsx:808`의 `<Sector {...props} />`에서 key를 떼어 넘김. 승인 불필요.
- **같은 사이트의 Origin 없는 GET**: 쿠키 없는 운영자(로컬 무로그인·Tailscale 신원)의 Origin 없는 GET이 `Sec-Fetch-Site: same-site`면 통과 — 같은 PC의 v1·v3 화면이나 같은 tailnet의 다른
  기기 페이지가 `<img>`·no-cors로 운영자 GET(수집 유발·SSE 열기)을 일으킬 수 있음(응답은 읽히지 않고 쓰기는 막힘). 수집기 webguard처럼 none·same-origin만 통과. 인증 경로라 승인 필요.
- **커밋 메일**: 공개 저장소의 커밋 작성자 메일이 운영자 로그인 ID와 같음 — 앞으로의 커밋은 GitHub noreply 메일로(`git config user.email`, 지난 이력은 바꾸지 않음 — 히스토리 변경은 승인 사항).
  사용자 결정.
- **한국 단일 계좌 리셋 뒤 재출발 불가**(명세 §K28 설계)에 화면·API 경고가 없음 — 리셋 확인 대화상자에 한 줄. 승인 불필요.

## 17. 한국 종목 검색 로컬 색인

- **문제**: 한국 개별 종목은 통합 검색의 로컬 색인(스코어카드 유니버스 — 미국 티커만)에 없어 외부 자동완성(네이버·Yahoo)에만 기대고, 출처 장애 때 찾을 수 없습니다(QA-256의 바탕).
- **제안**: 모의 매매 한국 종목 이름 표(`/api/paper/names?market=KR`)나 KRX 종목 목록을 검색 색인에 더함.
- **기대 효과**: 외부 장애와 무관하게 자주 보는 한국 종목으로 바로 감.
- **위험·비용**: 작음~중간. `/api/paper/names`는 운영자 전용(`AccessPolicy`)이라 '검색은 회원 경로만 읽음'(`SearchCommand.tsx:42-43`) 설계와 부딪힘 — 운영자에게만 읽게 하고 주석·시험도 바꿔야 함.
- **승인**: 의견 필요(검색이 운영자 전용 자료를 읽게 되는 설계 변경).
