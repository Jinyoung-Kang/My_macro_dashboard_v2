# 아키텍처

## 1. 왜 세 개의 프로세스인가

**사용자가 화면을 열 때 수집을 시작**하면, 캐시가 만료된 순간 접속한 사람이 전체
수집 시간(메뉴당 수십 초)을 그대로 기다립니다. 그래서 수집과 화면을 **서비스
경계**로 나눴습니다.

| 프로세스 | 언어 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| Collector | Python | 외부 소스 수집·파싱·적재, 키가 필요한 실시간 조회 | 분석, 화면용 가공 |
| Backend | Java | 저장본 읽기, 분석·판정, 인증, 캐시 | 외부 시장 데이터 직접 수집 |
| Frontend | TypeScript | 표시, 입력 | 계산 |

이 경계 덕분에:

- 수집기가 죽어도 **화면은 저장본으로 뜹니다.**
- 백엔드가 재시작돼도 수집은 계속됩니다.
- 키는 수집기 한 곳에만 있습니다(AI 키만 백엔드).

## 2. 데이터 흐름

```
외부 소스 ──▶ Collector ──▶ PostgreSQL ──▶ Backend ──▶ Frontend
                  ▲                           │
                  └───── 수집 요청 (auto 모드) ─┘
```

`auto` 모드에서 백엔드는 저장본이 오래됐다고 판단하면 수집기에 **해당 태스크만**
실행을 요청하고 다시 읽습니다. 수집이 실패하면 오래된 저장본이라도 돌려줍니다 —
외부 장애 때 화면이 비는 것보다 낫고, 화면에는 수집 시각이 함께 표시되므로
오해의 여지가 없습니다.

저장본이 **아예 없을 때**는 수집이 끝나기를 기다립니다. 다만 기다린 뒤에도 없던
태스크는 10분 동안 다시 기다리지 않고, 같은 태스크를 동시에 기다리는 요청은 한 번의
수집에 합류합니다(`StoreReader`). 추적하지 않는 13F CIK·FRED 시계열은 기다리지 않고
바로 400입니다. 이 제한이 없으면 없는 CIK 3개를 넣은 요청 하나가 13F 수집을 6번
붙잡습니다(재현: 수집 지연 5초에서 30초).

**데이터셋 이름은 두 언어에 같은 문자열로 존재합니다** — `collector/app/catalog.py`와
`backend/.../store/Datasets.java`. `DatasetsParityTest`가 실제로 `catalog.py`를
읽어 대조하므로 한쪽만 고치면 빌드가 깨집니다. "수집은 되는데 화면에 안 보이는"
버그를 막기 위한 장치입니다.

`refresh_requests`를 테이블로 두는 이유: 수동 새로고침 기준 시각은 화면·백엔드·수집기가
함께 봐야 하는 값이라, 한 프로세스의 메모리에 둘 수 없습니다.

### 왜 JSONB인가

pandas DataFrame을 JSON 문자열로 저장하면 **dtype을 따로 실어야** 합니다. 그러지
않으면 `"069500"` 같은 종목코드가 int로 추론돼 앞자리 0이 사라집니다. 그래서
데이터셋마다 **명시적 JSON 계약**을 두고 종목코드를 처음부터 문자열 필드로
정의합니다. 그 위험 자체가 생기지 않습니다.

### 3-1. 종목별 대량 데이터는 스냅샷이 아니라 `observations`에

금융위 공식 시세는 하루 약 3천 종목입니다. 한 스냅샷(JSONB 한 행)에 넣으면 화면이
종목 30개를 볼 때도 3천 행을 통째로 읽고 파싱해야 합니다. 그래서 종목코드를
`entity`로 `observations`에 쌓고, 백엔드는 기본키 `(dataset, obs_date, entity)`
인덱스로 **요청한 종목만** 읽습니다(`StoreRepository.readObservationsFor`).
날짜별로 쌓이므로 공식 종가 이력도 덤으로 남습니다(400일 보존).

🧪 모의 매매 미국 종목 재무(`us.fundamentals`, D28)도 같은 표에 쌓습니다 — entity = 티커, **obs_date = 공시일**, payload = 그날 처음
낸(또는 값이 바뀐) XBRL 사실 묶음이고 지우지 않습니다(티커의 CIK가 다른 회사로 바뀌면 옛 CIK만의 행은 수집기가 지움). 백엔드는 패킷의 종목만 `obs_date ≤ 기준일`로 읽어
(`StoreRepository.readObservationsUntil`) 그날 몰랐던 정정값이 섞이지 않게 합니다.

🧪 모의 매매 사건 뉴스(`news_headline`, 2단계 B)도 같은 표입니다 — entity = 정규화한 제목의 해시, obs_date = 발행 시각의 UTC 날짜, payload =
제목·링크·출처·피드·시각이고, 수집기가 7일이 지난 행을 지웁니다(같은 제목은 날짜가 달라도 다시 넣지 않고, 다른 피드가 실으면 그 행의
`feeds`에 피드 키만 더함 — 이 표를 쓰는 것은 수집기뿐). entity로 고를 수 없어 백엔드는
결정 창이 덮는 날짜부터 읽고(`StoreRepository.readObservationsBetween`) 거르기는 `analytics.NewsEvents`가 합니다.

🧪 모의 매매 어닝 서프라이즈(`us.earnings_surprise`, 2단계 C)도 같은 표입니다 — entity = 티커, **obs_date = 실제 발표 시각의 미국 동부
날짜**, payload = 분기 말·EPS 실제치·컨센서스·서프라이즈율·통화·작은 추정치 표시·발표 시각이고, 수집기가 (날짜, 티커)마다 덮어쓰며 지우지
않습니다(출처가 최근 4분기만 줘 쌓아야 8분기가 됨). 백엔드는 재무와 같이 패킷의 종목만 `obs_date ≤ 기준일`로 읽고
(`readObservationsUntil`), 결정 시각 전 발표만 고르는 것은 `analytics.EarningsHistory`가 합니다.

### 3-2. 스키마 변경은 번호 붙은 파일로

`db/migrations/V{번호}__{설명}.sql`을 **수집기가 기동할 때** 번호 순서로 한 번씩 적용하고
`schema_migrations`에 기록합니다(`collector/app/migrations.py`). 백엔드가 쓰는 테이블(`regime_log` 등)도
같은 폴더·같은 번호 체계를 씁니다 — 백엔드에는 마이그레이션 도구를 두지 않고, 자기 테이블이 아직 없으면
그 기능만 "준비 중"으로 둡니다([ADR 0008](adr/0008-backend-owned-tables-and-scheduled-jobs.md)).
초기 스키마를 기동할 때마다 다시 실행하는 방식으로는 이미 있는 DB를 바꾸는 변경(예: 인덱스 삭제)을
넣을 수 없기 때문입니다.

- 스키마를 바꿀 때는 **새 번호 파일을 추가**합니다. 이미 적용한 파일을 고치면 경고가 남습니다.
- 모든 파일은 여러 번 실행해도 안전하게 씁니다(`IF EXISTS` / `IF NOT EXISTS`). 새 DB는
  postgres 컨테이너가 V1을 먼저 만들고, 테스트 DB(`make db-test`·CI)는 psql로 번호 순서대로
  적용합니다.
- 대기 중인 파일을 한 트랜잭션으로 적용합니다. 하나라도 실패하면 전부 되돌리고 수집기
  기동이 멈춥니다 — 절반만 바뀐 스키마로 도는 것보다 낫습니다.

## 4. 계산은 어디서 하는가

| 계산 | 위치 | 이유 |
|---|---|---|
| 파싱·정규화·단위 환산 | Collector | 원본 형식을 아는 곳에서 한 번만 |
| 등락률·국면·COT Index | Collector | 시계열 전체가 필요하고 적재 시점에 확정됩니다 |
| 수익률 매트릭스·모멘텀 순위 | Backend | 화면이 기간을 바꿔 가며 요청합니다 |
| 13F 분기 대비 액션·교집합 | Backend | 기관 조합이 요청마다 달라집니다 |
| 스프레드·백분위·해석 임계치 | Backend | 화면과 AI 리포트가 **같은 값**을 봐야 합니다 |
| 상관·국면·위험·백테스트·스코어 | Backend (`analytics/`) | 순수 함수로 두고 테스트로 규칙을 고정합니다 |
| 재무 비율·PER/PBR | Backend (`analytics/`) | 수집기는 DART 계정·금액을 그대로 저장하고, 비율은 백엔드가 계산합니다 |
| 표시 서식·거래소 달력 | Frontend | 로케일·색상·개장 여부는 표시의 문제입니다 |

화면 코드가 직접 계산하면 같은 수치를 AI 리포트가 다르게 말할 여지가 생깁니다.
계산을 백엔드로 모아 그 여지를 없앴습니다.

### 4-1. 패키지 — 기능 모듈과 저장소를 모르는 순수 계산

백엔드는 **기능(메뉴) 단위**로 나누고, 그 안쪽에 저장소를 모르는 계산 계층을 둡니다.

```
feature/<기능>/  기능 하나의 컨트롤러(HTTP 경계) + 서비스(저장본을 읽어 analytics에 넘기고
                 화면용 응답으로 조립). auth · macro · institution · insight · positioning ·
                 publicdata · status · snapshot(전체 원본 텍스트) · ai · toss · alert ·
                 paper(🧪 모의 매매, 운영자 전용)
analytics/       스프링도 DB도 모릅니다. 입력은 숫자와 날짜, 출력도 숫자입니다.
read/            읽기 정책(StoreReader) — 저장본이 오래됐으면 읽기 모드에 따라 수집을 요청하고 다시 읽음
store/           저장소 접근 · 데이터셋 이름 · 신선도 (외부 호출 없음)
collector/       수집기 호출
support/         공통 도구(저장본 JSON 읽기, 파라미터 해석, 비밀값 가림, 공통 예외)
web/             인증 필터 · CORS(WebConfig) · 공통 오류 응답 — 가장 바깥, 기능까지 씀
config/          설정 값(AppProperties) · 정기 작업 켜기 — 여러 패키지가 읽고, 우리 패키지는 아무것도 쓰지 않음
```

한 기능을 고칠 때 볼 파일이 한 폴더에 모이고, 기능 사이 의존이 import로 드러납니다.
의존 규칙(바깥 → 안쪽)과 그 이유는 [ADR 0001](adr/0001-feature-modules-and-dependency-rules.md)에 있고,
`ArchitectureRulesTest`가 빌드마다 확인합니다(기반 패키지까지 포함한 패키지 순환 0). 화면 쪽 층 나누기는 [ADR 0004](adr/0004-frontend-layering.md)입니다.

## 5. 응답 캐시 (측정 기반)

처음에는 응답 캐시를 두지 않았습니다. 2026-09 로컬 측정(두 번째 호출 기준)에서 화면 API가 5~126ms였고,
지연의 대부분이 계산이 아니라 **전송량**이어서 응답 압축(`server.compression`, 2KB 이상 JSON)만 켰습니다.
그때 정한 재검토 조건이 "화면 API p95 300ms 초과"였습니다.

2026-10-03 동시 50명 부하 시험(k6, 16경로)에서 p95가 528ms, 전체 요약 텍스트는 992ms로 그 조건을 넘었습니다.
저장본은 수집 주기(5분~하루)로만 바뀌는데 요청마다 수 MB 저장본을 다시 훑어 계산하고 있었습니다. 그래서 두 가지를 넣었습니다.

- **계산 결과 캐시 `read.ComputedCache`** — 같은 저장본이면 다시 계산하지 않습니다. Redis 같은 별도 계층이 아니라 백엔드
  메모리 안에 둡니다(기동 의존성·열린 포트를 늘리지 않음).
  - 버릴 때: 저장본 전체의 최신 수집 시각(`StoreRepository.latestCollectedAt()`)이 바뀌면 모든 항목을 버립니다.
    어느 계산이 어느 저장본에 의존하는지 적지 않아도 "새 데이터를 옛 계산으로" 보여 주지 않습니다. 시간 기반 TTL만
    쓰면 수집 직후에도 지난 값을 보여 줄 수 있어 버전을 키로 씁니다.
  - 그래도 60초가 지나면 다시 계산합니다. 응답에 `ageSeconds`·`stale` 같은 '지금 기준' 값이 들어 있기 때문입니다.
  - 항목은 256개까지(가장 오래 안 쓴 것부터 버림), 계산이 예외를 던지면 저장하지 않습니다.
    Δ초마다 읽히는 항목이 밀려나려면 그 Δ초 안에 다른 키 256개가 새로 들어와야 합니다(Δ≤60이면 초당 4.3개 이상).
    서로 다른 키가 몰릴 때 자주 쓰는 항목이 밀려나는지는 QA 스택에서 `scripts/qa/k6/cache-churn.js`로 잽니다(절차는 파일 머리말).
  - 쓰는 곳은 컨트롤러뿐입니다(ADR 0001 예외). 서비스는 캐시를 모른 채 계산만 합니다. 대상은 무거운 계산 경로
    (전체 요약 텍스트, 기관 프로필·유사도·위험, 보유 기관 검색의 보유 목록, 13F 포트폴리오·교집합·신규 편입, 국면·판정 성과,
    스코어카드)입니다. 캐시 밖 경로(상관 분석, 수급 이력, AI 리포트)는 요청 하나의 크기를 파라미터 상한으로 묶습니다(QA-133).
  - **동시 실행 상한**(QA-131): 캐시를 놓쳐 다시 계산하는 요청은 동시에 N개까지만 돕니다(`.env`의
    `COMPUTE_MAX_CONCURRENT`, 비우거나 0이면 자동 = 코어 수의 절반·최소 1, AWS 2 vCPU면 1). 상한이 없을 때 QA 스택에서
    캐시에 없는 서로 다른 조합을 초당 50건 부르자 `/api/health`까지 20초 안에 답하지 못했습니다.
    - 자리가 없으면 먼저 온 순서로 2초 기다리고, 그래도 없거나 이미 32건이 기다리고 있으면 429 + `Retry-After: 2`로
      거절합니다(아무것도 저장하지 않음). 그래서 자리를 기다리거나 계산하는 요청 스레드는 N+32개 안팎으로 묶입니다.
    - **같은 키는 한 번만 계산**합니다. 같은 키·같은 저장본 버전을 놓친 요청이 겹치면 먼저 온 하나만 자리를 잡아
      계산하고, 나머지는 자리도 대기열 자리도 잡지 않고 그 계산을 최대 30초 기다려 같은 결과를 받습니다. 그 계산이 던진
      예외도 같이 받고, 아무것도 저장하지 않았으니 다음 요청은 다시 계산합니다. 30초 안에 끝나지 않으면 429입니다.
      이것이 없을 때 QA 스택에서 재기동 직후 5명이 무거운 화면을 한꺼번에 열자(요청 45건, 키 9개) 같은 키 요청이 각자
      대기열에 서서 14–37건이 429였고, 캐시에 없는 서로 다른 키를 초당 50건 섞어 보내는 동안 자주 읽는 키 5개를 읽는
      요청도 항목이 60초로 만료될 때마다 각자 줄을 서 3–6%(상한 1개면 12%)가 429였습니다. 버전이 다르면 따로
      계산합니다 — 새 저장본을 본 요청이 옛 버전 계산의 결과를 받지 않습니다.
    - 그 계산이 자리를 얻지 못해 429가 되면, 자기 자리 대기 한도(도착 뒤 2초)가 남은 따르는 요청은 그 429를 받지 않고
      다시 시도합니다 — 계산을 새로 맡아 남은 시간만 자리를 기다리거나(대기열 끝에 서므로 도착 순서보다 뒤로 밀림)
      그사이 다른 요청이 맡은 계산을 따릅니다. 한도가 끝났으면 같은 429입니다. 그래서 앞선 계산에 남은 대기 시간 때문에
      자기 한도보다 먼저 거절되지는 않지만, 한도는 요청마다 2초 그대로라 재기동 직후처럼 키가 그 안에 끝낼 수 있는 계산
      수(N × 2초 ÷ 계산 시간)보다 많으면 남는 키의 요청은 여전히 429입니다.
    - 같은 키 묶기를 넣고 다시 잰 결과: 재기동 직후 묶음의 429는 9회 중 1회 5건(상한 1개)으로 줄었지만, 초당 50건 공격
      중 자주 읽는 키의 429는 4–8%(상한 1개 6%, 2개 3%) 그대로입니다 — 만료된 항목의 다시 계산이 공격 요청 뒤에 줄을
      서기 때문입니다. 화면은 이전 값을 두고 '새로 읽지 못함'만 보입니다. 바쁠 때 만료된 직전 값을 돌려주는 방법은 보류했습니다
      ([decisions.md](decisions.md) 2026-10-19, [측정](qa/evidence/2026-10-18/compute-limit.md)).
    - 그 계산을 따르며 기다리는 요청은 N+32에 들지 않는 대신 모든 키를 합쳐 64건까지만 기다리고, 넘으면 바로 429입니다.
      그래서 계산 경로가 쥐는 요청 스레드는 N+32+64개 안팎이고, Tomcat 기본 200개의 절반가량이 캐시 적중·health·로그인
      몫으로 남습니다. 이 상한이 없을 때는 캐시에 없는 키마다 같은 요청을 몇 건씩 겹쳐 보내 요청 스레드를 모두 묶을 수
      있었습니다(자리 1·대기열 32에서 키 33개×6건을 보내자 198개가 멈추고 429는 0건). 재기동 직후 묶음(따르는 요청 36건)과
      항목이 만료되는 순간의 자주 읽는 키는 64건 안에 듭니다.
    - 캐시 적중은 자리를 잡지 않고 진행 중인 계산도 기다리지 않습니다. 버전이 없는 경로(DB 장애·저장본 0개)도 상한
      밖입니다 — DB 장애 때 계산이 자리를 쥔 채 연결을 기다리면, 다른 요청이 503 'DB 연결 불가' 대신 429 '몰려 있음'을
      받아 원인을 잘못 알게 됩니다.
    - 놓친 뒤 앞선 계산이 막 끝나 같은 키·같은 버전이 채워졌으면 자리를 잡지 않고 그 값을 씁니다. 저장 시각은 자리를
      얻은 때입니다.
    - 한계(고치지 않음): auto·live_only 모드에서 저장본이 일부만 있으면(버전은 있으므로 상한 안), 계산이 읽는 데이터셋 중
      저장본이 아예 없는 것은 계산 안에서 수집을 기다립니다(수집기 대기 한도, 기본 90초). 그동안 자리를 쥐어, 상한이
      1개면 그사이 다른 새 계산은 2초 뒤 429입니다. 그 계산을 기다리는 같은 키 요청은 상한과 상관없이 30초 뒤 429입니다
      — 같은 키를 한 번만 계산하기 전에는 상한이 2개 이상이면 각자 자리에서 같은 수집에 합류해 값을 받았으므로, 이
      경우는 그때보다 나빠졌습니다. 첫 기동처럼 저장본이 일부만 있을 때만 겪고(같은 태스크는 10분 동안 다시 기다리지
      않음). v3의 AWS 데모(`store_only`)는 수집을 기다리지 않아 해당 없었고, 이 저장소의 AWS 서버는 로컬과 같은 `auto`입니다.
    - 503이 아니라 429인 이유는 [결정 기록](decisions.md)에 있습니다. 거절은 60초에 한 번 WARN 로그로 묶어 남깁니다.
- **차트 구간 솎기 `SeriesMath.thinOlderThan`** — 1년보다 오래된 구간은 주 단위(그 주의 마지막 행)로 줄입니다
  (매크로 개요·유동성·환율). 최신값과 4주·12주 변화는 솎기 전 자료로 계산합니다.

## 6. 인증·보안

계정(이메일 + Argon2id 비밀번호 해시)과 **DB 세션**을 씁니다([ADR 0010](adr/0010-accounts-and-db-sessions.md)).
쿠키에는 무작위 토큰, DB에는 그 SHA-256만 둡니다. 경로마다 누가 부를 수 있는지는 표 하나(`AccessPolicy`)가
정하고, 컨트롤러가 여는 모든 경로가 그 표에 있어야 빌드가 통과합니다. 처음 기동할 때 계정이 없으면
`OWNER_EMAIL`·`APP_PASSWORD`로 운영자 계정을 만듭니다.

| 위협 | 대응 | 위치 |
|---|---|---|
| XSS로 토큰 탈취 | 쿠키 `HttpOnly` (스크립트가 읽지 못함) | `AuthController` |
| CSRF | 쿠키 `SameSite=Strict`. 화면(:3000)과 API(:8080)는 포트만 달라 같은 사이트. 쿠키가 없는 로컬 무로그인은 아래 'Origin·Sec-Fetch-Site' 검사(ADR 0016) | `AuthController`, `SessionFilter` |
| 비밀번호 대입 | (접속 주소, 이메일)마다 연속 5회 실패 뒤에는 시도를 **느리게**(전역 1초에 1건, 겹치면 즉시 429) 처리. 잠금이 아니라 지연이라 맞는 비밀번호가 **잠기지는 않지만**, 공격자가 느린 차선을 계속 차지하는 순간에는 주인도 429를 받을 수 있고 1초 뒤 다시 시도하면 통과(Docker에서는 모든 접속이 같은 주소라 잠금은 주인까지 영구히 막았음). 429 + `Retry-After`는 안내. 15분 조용하면 기록 삭제. 기억하는 기록은 1만 건까지(꽉 찬 동안 처음 보는 키는 기록하지 않고 바로 느린 차선 — 맵을 채워 지연을 끄지 못하게). 비밀번호 변경·탈퇴의 '지금 비밀번호' 재확인도 사용자마다 같은 지연(느린 차선은 로그인과 따로) | `LoginThrottle`, `AuthController` |
| 인증 없이 감사 기록 채우기 | 로그인 실패는 표본만 남김(QA-125). 메일 인증을 마친 계정은 사용자 번호마다(주소를 바꿔도 한 묶음, 하루 조용해야 끝 — 15분씩 끊어 시도해도 이어짐) 연속 실패의 1·5·2^k번째와 한 시간에 한 번을 누적 실패 수와 함께, 성공 기록에 직전 실패 수. 없는 계정과 메일 인증 전 계정(가입으로 누구나 만듦)은 합쳐 한 시간에 30건 + 넘친 개수 요약 한 줄(종료 때는 웹 서버가 멈춘 뒤 씀) — 쓰레기 요청이 인증을 마친 계정의 몫을 쓰지 못하고, 만든 계정 수만큼 행이 늘지 않음 | `LoginFailureAudit`, `AuthService.recordFailure` |
| 컨테이너 안 코드가 뚫림 | 앱 컨테이너 셋(수집기·백엔드·화면)은 root가 아닌 사용자로 돌고, 커널 권한을 모두 버리며(`cap_drop: ALL`) 권한 상승을 막음(`no-new-privileges`). postgres는 기동 때 사용자 전환이 필요해 제외 | `docker-compose.yml`의 `x-hardening` |
| 해시로 메모리 고갈 | Argon2 해시(한 번 16MB)는 동시에 코어 수(최소 2)까지만. 3초 안에 자리가 나지 않으면 429 — 이메일을 바꿔 가며 보내는 인증 없는 로그인도 막힘 | `PasswordHasher` |
| 서로 다른 조합으로 비싼 계산 폭주 | 캐시에 없는 계산은 동시에 코어 수의 절반(최소 1, 설정으로 조정)까지만. 2초 안에 자리가 나지 않거나 이미 32건이 기다리고 있으면 429 + `Retry-After`. 같은 키·같은 버전은 한 번만 계산하고 나머지는 자리 없이 그 결과를 기다림(최대 30초. 그 계산이 자리를 얻지 못하면 자기 2초 한도 안에서 다시 시도). 그렇게 기다리는 요청도 모든 키를 합쳐 64건까지(넘으면 바로 429) — 같은 키를 겹쳐 보내도 계산 경로가 쥐는 요청 스레드는 상한+32+64개 안팎이라, 요청 스레드(Tomcat 기본 200개)가 계산에 묶여 캐시 적중·health·로그인까지 답하지 못하는 일을 막음(QA-131). 캐시 적중과 DB 장애 경로는 상한 밖. 사용자·주소별 공정성은 다루지 않음(한 사람이 자리를 다 쓰는 동안 다른 사람의 새 계산도 429). 캐시 밖 경로는 요청 하나의 크기를 묶음 — 상관 창 250·10년, 수급 이력 전 기간 최신 5,000행, 보유 검색 200행(보유 목록은 캐시 안), AI 리포트는 못 쓰는 엔진이면 한도·원본 텍스트 전에 끝(QA-133, [측정](qa/evidence/2026-10-19/uncached-load.md)) | `ComputedCache`, `ApiExceptionHandler`, `AnalyticsService`, `RadarService`, `GuruService`, `AiReportService` |
| 큰 본문으로 메모리 고갈 | 로그인 없이 받는 POST는 4KB, 로그인한(데모 포함) 쓰기 요청은 64KB에서 파싱 전에 413. 인증보다 먼저 모든 경로(`/api` 밖 포함)에서 PUT·PATCH·DELETE의 form 본문을 상한 없이 읽던 Spring 기본 필터(`FormContentFilter`)는 끔(QA-069) | `SessionFilter.capBody`, `application.yml`(`spring.mvc.formcontent.filter.enabled`) |
| 비밀번호 유출 | Argon2id 해시만 저장. 세션 토큰은 SHA-256만 저장(DB가 새어도 쿠키를 만들 수 없음) | `PasswordHasher`, `SessionStore` |
| 계정 존재 여부 탐색 | 없는 이메일도 가짜 해시와 비교해 같은 시간·같은 401. 다만 실패를 감사 표본으로 쓰는지(DB INSERT 한 번, ms 안팎으로 추정·측정 안 함)는 요청마다 달라(없는 계정 한 시간 몫이 찼는지, 계정 묶음의 표본 차례인지) Argon2 시간 옆에 그만큼의 차이는 남음 | `AuthService.verify`, `AuthService.recordFailure` |
| 타이밍 공격 | 수집기 토큰 `hmac.compare_digest` | `collector/app/main.py` |
| 로그아웃·비밀번호 변경 뒤 토큰 재사용 | DB 세션이라 다음 요청부터 거부, 재시작 후에도 유지(예전 JWT는 메모리 차단 목록이라 재시작 때 사라짐). 비밀번호 변경·재설정은 저장·다른 세션 해지·감사 기록이 한 트랜잭션이라, 중간에 실패해도 '바뀐 비밀번호 + 살아 있는 옛 세션'이 남지 않음(QA-128) | `SessionStore`, `UserStore.atomically` |
| 권한 밖 기능 호출 | 경로별 접근 정책(공개·회원·유료·운영자). 미분류 경로는 빌드 실패 | `AccessPolicy`, `AccessPolicyTest` |
| 다른 출처의 상태 변경 요청 | POST·PUT·DELETE의 `Origin`이 CORS 허용 목록에 없으면 403 | `SessionFilter.foreignOrigin` |
| 인증 우회 경로 | 공개 경로는 정규화된 경로와 **정확히 일치**할 때만 (`/api/healthx`, `/api/health/../x` 차단). 정규화가 필요한 경로(`.`·`..` 조각, 인코딩된 점·슬래시, `//`, `;`)는 정책 검사 전에 400 — 정책(정규화 경로)과 처리기 매칭(날것 경로)이 다른 경로를 보지 않게 | `WebConfig.SessionFilter` |

| 헤더로 로그인 건너뛰기(데모 열람, v3 AWS 데모만 — 이 저장소의 어느 배포도 켜지 않음) | 기본 꺼짐. 켜려면 32자 이상 토큰(짧으면 기동 실패), 해시를 상수 시간 비교, 세션이 먼저, GET만(쓰기·HEAD 403 — AI 리포트 생성 POST 하나만 예외, ADR 0014), 운영 경로 403. 백엔드는 루프백에만 열고 앞단이 헤더를 붙이거나 지움(ADR 0013) | `DemoViewer`, `SessionFilter.demoForbidden` |
| 응답 가로채기·끼워 넣기 | `nosniff`, `no-store`, `X-Frame-Options: DENY`, `frame-ancestors 'none'` | `SessionFilter`, `next.config.mjs` |
| 유료 AI API 비용 폭주 | 사용자 입력 2,000자 상한(400). 하루 한도(유료 회원은 사용자별 DB, 데모 방문자는 공용 메모리). 배포별 엔진 허용 목록(v3 AWS 데모는 Haiku 하나, ADR 0014 — 이 저장소의 AWS 서버는 `.env`대로). 못 쓰는 엔진(AI 꺼짐·모르는 ID·허용 목록 밖·키 없음)은 한도를 쓰기 전·원본 텍스트를 만들기 전에 끝(QA-133). 그 밖의 실패는 모델에 닿지 않았을 때만 한도를 되돌림(거절·빈 응답·대기 시간 초과는 과금됐을 수 있어 그대로) | `AiController`, `UsageService`, `AiService`, `AiReportService` |
| 로그로 API 키 유출 | 로깅 계층에서 키 파라미터 가림(`serviceKey`·`crtfc_key`·`key` 등 포함) | `collector/app/logredact.py` |

**주의** — 실패 횟수는 (접속 주소, 이메일) 기준입니다. X-Forwarded-For는 위조할 수
있어 믿지 않습니다(AWS 서버만 앞단 caddy가 덮어쓴 값을 믿음 — 9절). 도커 포트 포워딩·SSM 터널에서는 모든 접속이 같은 주소로 보여
사실상 이메일별 지연이 됩니다. 공격이 계속되는 동안 그 계정 주인이 429를 받을 수 있는 것은
남은 위험이며, 재시도로 풀립니다.

## 7. 장애 시 동작

| 장애 | 결과 |
|---|---|
| 수집기 다운 | 화면은 저장본으로 동작. 상태 화면에 "수집기에 연결하지 못했습니다". 연결만 받고 응답을 못 해도 제어용 호출(상태·백그라운드 실행 요청)은 3초 안에 포기하고, 저장본이 있는 화면은 수집기를 기다리지 않습니다 |

| 외부 소스 다운 | 수집 태스크가 `empty`/`error`로 기록되고 **기존 저장본은 유지** |
| 모든 수급 소스 다운 | 누적 이력으로 대체 + 화면에 날짜와 경고 표시 |
| 인터넷 전체 차단 | 화면·시계·거래소 개장 판정까지 정상 동작. 브라우저는 우리 백엔드 외에 아무 데도 호출하지 않습니다 |

## 8. 시간대

서버가 어느 시간대에서 돌든 **날짜 기준은 한국(KST)** 입니다. 컨테이너 기본은
UTC라서 `LocalDate.now()`를 그대로 쓰면 한국 시각 00:00~09:00 사이에 날짜가 하루
어긋납니다(실제로 연초 대비 수익률이 1월 1일 오전에 전년도 기준으로 계산됐습니다).

- 백엔드: `com.macrodash.Kst.today()` / `Kst.ZONE`
- 수집기: `ZoneInfo("Asia/Seoul")`
- 화면: 표시 시각은 백엔드가 KST 문자열로 내려보낸 것을 그대로 씁니다

거래소 개장 여부는 화면이 계산합니다(`lib/marketCalendar.ts`). 🧪 모의 매매 장부가 세는 미국 거래일만 백엔드
`analytics.UsMarketCalendar`가 같은 휴장일 규칙으로 셉니다. 공휴일 API를 쓰지
않는 이유는 [PRINCIPLES.md](PRINCIPLES.md)를 보세요 — **공휴일과 거래소 휴장일은
다릅니다.**

## 9. 배포 (AWS 개인용 서버)

🧪 모의 매매가 미국 장·결정 시각에 돌아야 해서 운영본은 AWS 서울의 EC2 한 대에 둡니다([ADR 0019](adr/0019-aws-personal-deployment.md)).
서버는 매일 KST 21:55에 켜지고 08:00(토 10:00)에 꺼집니다 — EventBridge Scheduler가 EC2 API를 바로 부릅니다.
로컬과 같은 compose 스택에 덧붙임 `compose.aws.yml`(앞단 caddy 추가, 로그인·쿠키·출처 고정)을 얹은 것입니다.

```
[PC — 관리용]                                   [어디서나 — 공개 주소, ADR 0019 결정 16]
 브라우저 http://localhost:8201                    브라우저 https://dXXXX.cloudfront.net
    │ 루프백                                          │ HTTPS
 scripts/aws/tunnel.sh (aws ssm 포트 포워딩)        CloudFront(캐시 끔 · 비밀 헤더 X-Origin-Verify · 꺼진 시간엔 S3 안내 페이지)
    ║ SSM 세션 — 암호화(인바운드 없음)                 │ HTTP :8301 — 보안 그룹은 CloudFront 원본용 prefix list만
    ▼                                                 ▼
[EC2 my-macro-app · t4g.medium · 인바운드는 CloudFront → 8301 한 줄 · 나머지 포트는 127.0.0.1]
 SSM 에이전트 ──▶ 127.0.0.1:8201 caddy :8301 ◀─(비밀 헤더 확인 → 잠금화면 gate:8100 → /api/admin 닫음)
                                 caddy ─┬─ /api/* ──▶ backend:8080 ──JDBC──▶ postgres:5432 ◀──적재── collector:8000
                                       └─ 나머지 ──▶ frontend:3000
 나가는 통신(공인 IPv4): collector ──▶ 외부 시장 데이터 · backend ──▶ Anthropic API
 cron 06:10 KST: make backup ──▶ S3 my-macro-backups-…/db/ (60일 만료)

[EventBridge Scheduler, Asia/Seoul] 21:55 ec2:StartInstances · 08:00(일~금)·10:00(토) ec2:StopInstances
```

- **들어오는 길은 둘**입니다(2026-10-29 결정 16). 관리용은 SSM, 공개 주소는 CloudFront → caddy :8301(보안 그룹 인바운드는 CloudFront 원본용
  prefix list 한 줄, caddy가 비밀 헤더 확인 → 잠금화면). 그 밖의 서버 포트(caddy 8201 · 화면 3000 · API 8080 · 수집기 8000 · DB 5432)는
  `127.0.0.1`에만 열립니다. 세션은 서버의 SSM 에이전트가 AWS로 먼저 나가 연결을 열어 두는 방식이라 인바운드가 필요 없습니다. 접속 권한은 PC의 IAM 로그인(`aws login`)입니다.
- **TLS는 없습니다.** 평문은 PC의 루프백(브라우저 ↔ session-manager-plugin)과 서버의 루프백·도커 네트워크에만 있고, 그 사이는 SSM이 암호화합니다.
  Chrome·Firefox는 `http://localhost`를 안전한 출처로 봐서 `Secure` 세션 쿠키(`COOKIE_SECURE=true`)를 그대로 받습니다(Safari는 받지 않아
  Safari로 열 때만 서버 `.env`에 `COOKIE_SECURE=false`).
- **같은 출처**: 화면은 `NEXT_PUBLIC_API_BASE=/`로 빌드돼 `/api/...`를 상대 경로로 부르고, caddy가 백엔드로 보냅니다(ADR 0012의 정의).
  허용 출처(`FRONTEND_ORIGIN`)는 터널 주소 `http://localhost:8201`·`http://127.0.0.1:8201`과 공개 주소(서버 `.env`의 `PUBLIC_ORIGIN`)입니다.
- **접속 주소**: caddy가 `X-Forwarded-For`를 접속 주소로 채우고(들어온 값은 믿지 않음) Tomcat이 내부 대역에서 온 그 헤더만 믿습니다
  (`SERVER_FORWARDHEADERSSTRATEGY=native` — 내부 대역은 같은 compose 네트워크의 컨테이너·서버 안 프로세스. 바깥에서 닿는 길은 caddy뿐). 터널로 들어온 요청은 모두 같은 주소로 보여, 위 6절의 로그인 지연은 서버에서도 사실상 이메일별입니다.
- **모의 매매 상태는 서버 한 곳**에만 있습니다. 서버로 옮긴 뒤 로컬 v1은 `PAPER_ENABLED=false`로 띄워 정기 작업(리스크 점검·결정·체결)을 두 곳에서 돌리지 않습니다.
- **백업**: 매일 06:10 KST에 `scripts/aws/backup-s3.sh`가 `make backup`(ADR 0003)의 새 파일 하나를 S3로 올립니다. 버킷은 퍼블릭 차단·SSE-S3·60일 만료이고,
  서버의 IAM 역할은 그 버킷 하나에만 쓸 수 있습니다.
