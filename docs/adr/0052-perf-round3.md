# 0052. 성능 3차: 화면 조회의 외부 예산을 차트 시계열·종목 찾기·실시간 시세·수급 랭킹까지, 차트 시계열은 짧게 기억(QA-1039)

- 상태: 채택 (2026-11-27, 사용자 결정 — 성능 개선 3차 실행 승인. D-3 '차트 시계열의 외부 대기 예산은 다른 화면 조회와 같은 10초, 받은 결과는 일봉(1개월 이상) 5분·분봉(1일·5일) 60초
  기억, 받지 못한 결과는 기억하지 않음' · D-6 '새 의존성·스키마 변경·백엔드 새 경로 없음'). 지시문
  [2026-11-27-perf-round3-exec-instructions.md](../specs/2026-11-27-perf-round3-exec-instructions.md), 진행 기록

  [ADR 0041](0041-info-search-watch.md)(검색의 15초·30초 상한 — 그대로), [ADR 0024](0024-live-prices-sse.md)(화면 실시간 시세).

  `CollectorClientLiveFetchTimeoutTest`.

## 배경

2026-11-27 재측정(배포본 `main@c167f149`)에서 2차의 개선은 유지되고 있었고, 새로 네 가지가 보였다(지시문 §2). 이 문서는 그 가운데 차트 시계열 조회(작업 A)의 결정이다 — 나머지
(계산 결과 기억·검색 피드·레이아웃 밀림)는 그 단계에서 아래에 덧붙인다.

- QA 프록시 hang에서 **기억과 호스트 잠금을 비우고** 수집기를 바로 부르니 2차의 예산(10초)에 든 셋(시세·뉴스·다음 장중)은 4.8~10초였지만, 빠져 있던 넷이 길었다: `/live/symbols` 120초 넘음 ·
  `/live/prices` 100초 · `/live/ticker` 70초(백엔드 `/api/macro/ticker` 60초) · `/live/radar` 62초. 2026-11-24의 측정이 못 본 까닭은 앞선 호출이 Yahoo를 잠가 바로 실패로 끝났기 때문이다.
- 차트 시계열은 저장본으로 답하는 `^VIX`·`^MOVE` 말고는 화면을 열 때마다 Yahoo를 새로 불렀다(운영 100~180 ms, 가끔 0.8~1.3초).

## 결정

1. **화면 조회의 외부 예산을 넷 더(QA-1039)**: 수집기 `/live/ticker`·`/live/symbols`·`/live/prices`·`/live/radar`도 요청 하나에 `app.http.LIVE_BUDGET_SECONDS`(10초)를 건다(2차의
   `http.run_with_budget` 그대로 — 공용 세션은 요청 timeout을 남은 예산에 맞춰 줄이고 예산 안에 끝나지 않을 재시도를 보내지 않으며, yfinance는 `app.yahoo`의 예산 세션이 같은 가드를 봄).
   예산이 끝나면 지금의 '받지 못함' 꼴 그대로다: 차트 시계열은 빈 `points`와 `error`, 종목 찾기는 출처별 `errors`, 실시간 시세는 못 받은 종목이 `missing`, 수급 랭킹은 누적 이력 대체
   (그것도 없으면 `rows` 빈 목록과 `reasons`). 재시도를 줄이는 쪽이라 출처에 보내는 요청은 늘지 않고, 호스트 간격·래치와 정기 수집 태스크는 그대로다.
   증권사 API 세션(KIS 장중 가집계·토스 1분봉)은 그 가드 밖이라, 그 대체 경로를 타는 수급 랭킹·실시간 시세는 예산을 넘겨 답할 수 있다.
2. **백엔드 → 수집기 읽기 한도**: 차트 시계열·종목 찾기는 15초(`CollectorClient.LIVE_FETCH_READ_TIMEOUT` — 예산 + 여유, 2차의 셋과 같은 클라이언트). 수급 랭킹·실시간 시세는
   결정 1의 가드 밖 경로 때문에 일반 한도 그대로 둔다(수집기가 답을 줄 수 있는데 백엔드가 먼저 끊지 않게).
3. **검색 넷은 그대로**: `/live/search/feed`·`links` 45초와 `resolve`·`entity` 15초는 ADR 0041의 설계 값(대상 풀기·Wikidata 15초 + 출처 30초)이다.
4. **차트 시계열의 짧은 기억(QA-1039)**: 수집기 `services.market.live_ticker`가 같은 심볼·기간의 받은 결과를 일봉(1개월 이상) 5분, 분봉(1일·5일) 60초 동안 기억한다(D-3).
   - **자리는 수집기의 화면 조회 경로**: Yahoo를 부르는 쪽이라 백엔드가 몇 벌이든 한 곳에서 줄어든다. 다만 `collect_ticker` 자체에는 두지 않는다 — 정기 수집(시계열 태스크·매크로 카드·
     교차 검증)이 같은 함수를 쓰므로, 거기에 두면 5분 주기 태스크가 5분 묵은 값을 받는다. 태스크의 Yahoo 호출·잠금·간격은 바뀌지 않는다.
   - **받지 못한 결과는 기억하지 않는다**(빈 `points`·자리표시 값) — 출처가 돌아오면 다음 요청이 바로 받는다. Yahoo가 닫혀 있는 동안은 지금처럼 래치가 보내지 않는다.
   - **크기 상한 64 조합**: 한 항목이 1년 일봉이면 약 250점, 5년이면 약 1,250점이라 심볼·기간 조합이 끝없이 늘지 않게 한다. 넘으면 기한이 지난 것부터, 그래도 넘으면 가장 먼저 끝나는 것부터 버린다.
   - 같은 심볼·기간을 함께 묻는 요청(한 화면의 차트 둘)은 먼저 온 하나만 Yahoo를 부르고 나머지는 그 결과를 쓴다(기다림은 그 요청의 남은 예산까지).
   - 응답 모양은 그대로다. 장중의 마지막 일봉은 최대 5분, 분봉은 최대 60초 늦을 수 있다(상세 시세의 5분 캐시와 같은 수준 — 장부·판단은 이 경로를 쓰지 않음).

## 결과

- QA 프록시 hang(기억과 잠금을 비운 상태, 경로마다 다시 띄움): 수집기 `/live/ticker` 70 → 9.5초 · `/live/symbols` 120초 넘음 → 9.5초 · `/live/prices` 100 → 8.9초 · `/live/radar` 62 → 7.2초,
  백엔드 `/api/macro/ticker` 70 → 9.6초 · `/api/detail/symbols` 90(읽기 상한) → 9.6초 · `/api/radar/ranking` 62 → 7.2초. 차단(block) 모드의 응답 9개는 고치기 전과 같다(시각 칸 제외).
  운영 배포 뒤 값은 진행 기록에 적는다.
- 화면 조회는 출처가 느리지만 결국 답하는 경우(10초 넘게 걸리는 정상 응답)도 '받지 못함'이 된다(ADR 0049와 같은 값) — 차트 시계열은 받지 못한 결과를 기억하지 않으므로 다음 조회가 다시 묻는다.
- 수집기 메모리: 차트 시계열 기억 최대 64 조합(1년 일봉 기준 조합마다 수백 kB). 수집기가 다시 뜨면 비고 처음 한 번 다시 받는다.
