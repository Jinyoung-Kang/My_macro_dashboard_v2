  ③ 상주 우회 서버(헤드리스 REST) 금지, 필요할 때만 뜨는 방식 ④ 서버 크기 결정(V2) 뒤 5단계에서. 2026-11-01 재개정은 robots.txt가 막는 출처를 허용하면서
  "모의매매 패킷의 사건 헤드라인 출처는 바꾸지 않는다(실험 조건)"를 남겼습니다.
- 사용자 요청(2026-11-05): Cloudflare 403 같은 봇 차단을 지나가는 기능을 수집기에 더하고, 출처에 부담을 주지 않으면서 기계적 주기가 아니라 사람처럼 비주기로 받는다.
- 확인한 사실(조사 2026-11-05, 코드·문서 기준):
  - 인베스팅닷컴은 지금 RSS 네 피드를 공용 세션으로 받습니다(Claude 계좌 패킷 `11b_events` 입력). 403 기록은 `/news/…` HTML 페이지와 robots.txt이고 2026-10-25 개발 PC에서 한 번 잰 것입니다.
  - 공용 세션의 거부 래치는 프로세스 전역·호스트 단위(5분)라, 같은 호스트의 다른 수집이 거부당하면 RSS도 함께 닫힙니다.
  - `curl_cffi`(브라우저 TLS 흉내)는 yfinance 간접 의존성으로 이미 이미지에 있고 Yahoo 세션이 씁니다. 새로 필요한 것은 헤드리스 브라우저뿐입니다.
  - 태스크 시간 상한은 fast 120초·slow 600초이고 그룹 안은 순차라, 기존 태스크 안에 초 단위 지연을 넣으면 상한에 걸리고 한국 장부 입력이 밀립니다.
  - Cloudflare 문서는 자동화 브라우저를 지원하지 않는다고 적고, 통과 쿠키는 방문자·기기에 묶입니다. UA만 바꾸면 TLS 지문과 어긋납니다.
  - 운영 서버는 Vultr 4 GB(2 vCPU, 스왑 8 GB)이고 컨테이너 메모리 상한 합은 2,944 MiB입니다.

## 결정

1. **계층**: 계층 0(간격·하루 예산·비주기 일정 — 모든 요청에 적용) → 계층 1(브라우저와 같은 TLS·HTTP/2 지문과 헤더, `curl_cffi`) → 계층 2(실제 브라우저).
   거부되면 지연 뒤 **한 번만** 위 계층으로 올라가고, 통과한 계층을 기억해 다음에는 그 계층부터 시작합니다. 브라우저 없이 되는 출처는 계층 1에서 끝납니다(D29 ①).
2. **닫힘 상태는 새 계층의 표에만**: 새 계층은 공용 세션의 5분 호스트 래치를 쓰지 않습니다. 거부·물러남·예산·다음 실행 시각은 수집기 소유 표
   `fetch_hosts`·`fetch_schedule`에 두어 재기동해도 이어지고, 같은 호스트의 기존 수집(인베스팅 RSS)은 닫히지 않습니다.
3. **고정 프로필**: 호스트마다 브라우저 프로필 하나를 뽑아 표에 고정하고 요청마다 바꾸지 않습니다(User-Agent 무작위화는 하지 않음). 다시 뽑는 때는 `curl_cffi` 판이
   바뀔 때뿐입니다. SEC(연락처 UA 의무)·BLS(설명형 UA)·증권사 API 세션은 이 계층을 쓰지 않습니다.
4. **프록시·자택 회선·IP 돌려쓰기 없음**: 출구는 운영 서버의 IP 하나입니다. 서버 IP로 지나가지 못하는 출처는 **포기**합니다(사용자 결정) — 연속으로 실패하면 그 출처를
   '포기'로 닫고 운영자가 풀기 전에는 다시 시도하지 않습니다. 프록시 주소를 읽는 자리도 만들지 않습니다.
5. **사람 확인은 풀지 않음**: CAPTCHA 퍼즐과 "사람입니다" 체크박스처럼 사람 입력을 요구하는 화면은 풀거나 누르지 않습니다. 그 출처를 12~24시간 닫고 직전 저장본을
   유지하며 알립니다(텔레그램 한 통 + 상태 화면). 풀이 서비스는 붙이지 않습니다. 입력 없이 지나가는 JS 검사는 실제 브라우저가 기다려서 지나갑니다.
6. **물러남**: 거부 1회 30~60분, 2회 3~6시간, 3회 이상 12~24시간(구간 안 무작위), 성공하면 0으로. 5회 연속이면 결정 4의 '포기'.
7. **비주기 일정**: 새 속도군 `polite`. 기동 직후 실행하지 않고, 실행이 끝날 때 다음 시각을 출처별 구간 안에서 무작위로 정해 저장합니다. 때가 아니거나 닫혀 있으면
   태스크가 외부를 부르지 않고 끝납니다(수동 실행·전체 수집도 같음). 요청 사이에는 4~15초의 불규칙한 지연(ms 단위 잡음, 가끔 긴 멈춤)을 두고, 호스트별 하루 요청
   예산을 넘기지 않습니다. 기존 fast·slow 태스크에는 지연을 넣지 않습니다.
8. **브라우저 컨테이너**(D29 ③ 개정 — '상주 우회 서버 금지'를 '상주 브라우저 금지'로): 작은 내부 서비스가 요청이 올 때만 브라우저를 띄우고 끝나면 닫습니다.
   Vultr 덧붙임 compose에만 정의하고(로컬·QA에는 서비스가 없음) 포트를 게시하지 않습니다. 수집기와만 통하는 별도 망, 공유 비밀, 허용 호스트 목록(최상위 이동),
   전역 주소가 아닌 목적지 차단(리다이렉트·하위 요청 포함), 동시 1건, 요청당 시간 상한, 메모리 상한을 둡니다. 서버 `.env`의 `BROWSER_FETCH_URL` 한 줄로 켜고 끕니다.
9. **서버 크기**(D29 ④ 닫음): Vultr 4 GB 그대로 진행합니다(사용자 결정). 브라우저 컨테이너의 첫 기동과 메모리 측정은 운영 서버에서 하고, 수집기·백엔드가 밀리면 끕니다.
10. **새 자료는 운영자 화면 전용**: 저장본에 출처·수집 시각·통과 계층을 싣고 화면에 '우회 수집'으로 표시합니다(D29 ②). 읽기 경로는 운영자 전용이고 저장본만 읽어
    수집을 일으키지 않습니다. Claude 결정 패킷의 입력(`news_headline` RSS, `calendar.us_consensus`, 한국 `consensus: null`)과 한국 규칙 계좌의 수급 입력은 바꾸지 않습니다.
11. **기존 RSS 보호**: 인베스팅닷컴 HTML 수집은 같은 호스트·같은 IP 평판을 RSS와 나눠 씁니다. 인베스팅닷컴은 연결 순서의 마지막에 두고, RSS 피드가 거부당하기 시작하면
    인베스팅닷컴의 새 수집을 스스로 멈춥니다.
12. **시험 자료**: 실제 응답 원문(헤드라인·쿠키·계정 정보가 섞일 수 있음)은 저장소에 넣지 않습니다. 구조만 남긴 최소 합성 표본을 씁니다(공개 저장소).
13. **대상과 순서**: TradingView 경제 캘린더(계층 1) → 인베스팅닷컴 경제 캘린더 → 인베스팅닷컴 뉴스 HTML → KRX 정보데이터시스템(전 종목 투자자별 수급 — 먼저 KRX 계정
    로그인이라는 공식 경로를 확인, 공매도는 범위 밖).

## 이유

- 닫힘 상태를 나누지 않으면 새 수집의 거부가 패킷 입력인 RSS를 5분씩 닫아 "패킷 불변"이 깨집니다.
- 프로필을 고정하는 쪽이 통과에 유리하고(지문과 UA가 맞음, 쿠키가 방문자에 묶임), 요청마다 정체를 바꾸는 것은 출처가 보기에 더 기계적입니다.
- 사용자가 출구를 서버 IP로 한정했습니다. 통과하지 못하는 출처를 계속 두드리면 차단이 길어지고 같은 IP의 다른 수집(RSS·TradingView scanner)까지 위험해지므로 포기 규칙을 둡니다.
- 사람 확인은 출처가 "사람만"이라고 밝힌 자리입니다. 하루 몇 번 받는 빈도에서는 드물고, 풀이 서비스는 대상 주소를 제3자에게 넘깁니다.
- 일정과 물러남을 DB에 두지 않으면 배포로 수집기가 다시 뜰 때마다 모든 출처를 한꺼번에 두드립니다.
- 상주 금지의 이유는 메모리와 '인증·SSRF 보호 없음'이었습니다. 브라우저를 요청 때만 띄우고 내부 망·비밀·허용 목록·목적지 차단을 두면 그 이유가 풀립니다.

## 대안과 버린 이유

- **공용 세션에 계층을 끼움(`_GuardedAdapter` 판정 뒤 승격)**: 래치·실행 기록이 기존 수집과 섞이고, 403·429를 다시 보내지 않는다는 기존 시험과 부딪힙니다.
- **User-Agent 무작위화·요청마다 IP 교체**: 결정 3·4의 이유. SEC·BLS에는 쓸 수 없고 토스는 허용 IP 때문에 프록시를 거치면 막힙니다.
- **CAPTCHA 풀이 서비스**: 결정 5의 이유.
- **브라우저를 수집기 이미지 안에**: 수집기는 이미 메모리 상한 1 GB의 60~90%를 쓰고, 브라우저가 수집기 권한·망에서 제3자 스크립트를 실행하게 됩니다.
- **compose `profiles`로 서비스를 가림**: 지금의 배포 명령과 CI 해석이 그 서비스를 보지 않습니다(빌드·기동·단언에서 빠짐).
- **기존 slow 태스크 안에 지연을 넣음**: 시간 상한과 한국 장부 입력 순서 때문에 안 됩니다.

## 결과와 남은 위험

- 서버 IP에서 어느 계층이 통과하는지는 배포 뒤 실행 기록으로만 압니다. 통과하지 못하는 출처는 포기로 끝납니다(결정 4).
- 이 저장소의 자동 작업은 실제 사이트를 상대로 한 통과 시험을 직접 돌리지 않았습니다. 구현 검증은 가짜 서버·가짜 브라우저 드라이버 시험이고, 실제 응답 모양은
  배포 뒤 확인하거나 운영자가 저장해 준 페이지로 맞춥니다.
- 인베스팅닷컴 HTML 수집이 RSS의 IP 평판에 영향을 줄 수 있습니다(결정 11이 줄이지만 없애지는 못함).
- 대상 사이트의 이용 조건은 자동 수집을 막을 가능성이 높고, 차단을 지나가는 수집은 그 위반 소지가 더 큽니다. 개인·비상업·운영자 한 명만 보는 화면이라는 조건
  ([DATA_SOURCES](../DATA_SOURCES.md) §5)은 그대로입니다.
- 브라우저가 실행하는 제3자 스크립트는 Chrome 샌드박스와 컨테이너 격리(비root·권한 제거·별도 망·목적지 차단)에 기댑니다. Chrome 샌드박스를 켜려고 seccomp에
  사용자 네임스페이스와 `chroot`를 열었습니다(도커 기본은 권한을 뺀 컨테이너에서 막음) — 그만큼 그 컨테이너가 커널에 닿는 면이 넓어집니다. 웹소켓은 요청 가로채기를
  지나지 않아 목적지 검사가 걸리지 않고, 이름을 푸는 시점과 Chrome이 붙는 시점 사이의 주소 바뀜(DNS 재결합)은 막지 못합니다.
  (웹소켓·재결합·리다이렉트 홉은 2026-11-12 덧붙임 '브라우저의 나가는 길'이 닫았습니다 — 거기의 남은 위험을 보세요.)
- 2026-11-06 개발 PC와 운영 서버(Ubuntu 24.04 — 호스트가 사용자 네임스페이스를 제한하는 설정에서도) 둘 다에서 같은 굳히기 설정으로 Chrome이 샌드박스를 켠 채
  뜨는 것을 확인했습니다(컨테이너 안 로컬 페이지 — [명세](../specs/2026-11-05-polite-fetch.md) §11). 실제 페이지를 열 때의 메모리는 출처를 계층 2에 연결할 때 잽니다.
- KRX 정보데이터시스템은 계정 로그인(`KRX_ID`·`KRX_PW`)으로 기존 pykrx 경로가 풀려 이 계층을 쓰지 않습니다(결정 13의 '먼저 공식 경로'가 답이었음).
- 2026-11-06 02:20 KST 서버 첫 실행에서 TradingView 경제 캘린더가 계층 1로 통과했습니다(323건, 요청 1건 — 명세 §11). 서버 IP로 지나가므로 이 출처에는
  브라우저 계층도 포기 규칙도 쓰이지 않았습니다. 인베스팅닷컴 두 출처는 실제 페이지 모양을 본 뒤 연결합니다.

## 덧붙임 — 리다이렉트 규칙(2026-11-12, QA-388)

결정 8은 브라우저 컨테이너의 '리다이렉트·하위 요청 포함' 차단만 적었고, 계층 1의 리다이렉트는 정하지 않았습니다. 구현은 `curl_cffi` 세션의 기본값(따라가기, 최대 30번)
그대로여서, 등록 출처(또는 그 CDN)가 302로 내부 주소를 주면 수집기가 그대로 따라가 받은 본문을 글로 저장했습니다. 호스트 검사·닫힘·간격·하루 예산은 처음 주소에만
걸렸습니다. 아래를 결정에 더합니다.

- **계층 1은 리다이렉트를 따라가지 않습니다**(`fetch/impersonate.py` — 3xx를 그대로 돌려줌). 따라갈지는 받기 계층 한 곳(`fetch/ladder.py`)이 정합니다 — 출처별 코드는
  판단하지 않습니다.
- **따라가는 조건**: GET의 301·302·303·307·308이고, 목적지가 **https**이고, 목적지 호스트가 **정책 표에 있을 때**만. 최대 3번이고, 홉마다 그 호스트의 닫힘·간격·하루
  예산을 보통 요청처럼 지납니다(그 호스트의 세션 — 다른 호스트로 가는 홉에는 요청 문맥 머리글을 싣지 않음). 조건 밖이면 요청을 보내지 않고 그 실행만 실패입니다
  ('정책 표 밖으로 리다이렉트 — 따라가지 않음: 호스트'). 출처의 거부가 아니라 물러나지 않습니다. POST(KRX 로그인·자료)의 3xx는 따라가지 않고 그 답을 그대로 돌려줍니다.
- **사후 방어(두 계층 공통)**: 통과로 판정한 답의 최종 주소가 정책 표 밖이면 본문을 버립니다(첫 계층이면 그 실행만 실패, 올라간 계층이면 아래 계층의 거부가 최종).
  계층 2(실제 브라우저)는 스스로 리다이렉트를 따라가므로, 이것이 그 계층에서 저장·전파를 막는 수단입니다. 거부·사람 확인 판정은 본문을 쓰지 않아 그대로입니다.
- **글 페이지**: 블로그 피드 항목의 링크는 그 블로그 자신의 호스트(사이트·피드 주소의 호스트)일 때만 글 페이지로 엽니다. 정책 표의 다른 호스트를 가리키는 링크는
  피드 요약으로만 둡니다(그 호스트의 세션 쿠키가 붙은 요청이 나가지 않게).
- 버린 대안: 최종 주소의 사후 확인만 하기(요청은 이미 나감), scheme만 https로 좁히기(호스트를 못 가림), 같은 호스트로의 리다이렉트만 허용(피드 주소가 `www` 유무나
  CDN 호스트로 정규화되는 출처가 한꺼번에 끊길 수 있음).
- **남은 위험**:
  - 정책 표 **안의** 다른 호스트로 돌리는 리다이렉트는 따라갑니다(그 호스트의 예산·간격·닫힘은 지남). 표의 호스트 하나가 침해되면 다른 표 호스트로 요청을 보내게 할 수 있습니다.
  - 계층 2의 리다이렉트 홉: 브라우저 컨테이너의 목적지 검사(요청 가로채기)가 리다이렉트로 이어진 요청에도 불리는지는 이미지의 드라이버에서 확인하지 못했습니다
    (QA-414 — 결정 대기). 불리지 않는다면 허용 호스트의 페이지가 내부 주소로 돌릴 때 요청 자체는 나갑니다. 위의 사후 방어는 그 답의 저장·전파만 막습니다.
    → 같은 날 이미지에서 확인했고(불리지 않음) 아래 덧붙임 '브라우저의 나가는 길'로 닫았습니다.
  - 어느 출처가 정책 표 밖으로의 리다이렉트에 기대는지는 운영 서버의 실행 기록으로만 압니다. 그런 출처는 배포 뒤 '받지 못함'으로 실패하고(연속 3회면 끊김 알림),
    그 호스트를 정책 표와 `compose.vultr.yml`의 `BROWSER_ALLOWED_HOSTS`에 넣을지는 운영자가 정합니다.

## 덧붙임 — 본문 상한(2026-11-12, QA-389)

본문 상한(8MB)은 계층 1에서 다 받아 압축을 푼 뒤에야 길이를 쟀고, 계층 2에는 상한이 없었습니다. 등록 출처(또는 리다이렉트 목적지)가 압축 폭탄이나 아주 큰 응답을
주면 길이를 재기 전에 수집기(메모리 상한 1g — 실제 매매 주문 길과 같은 프로세스)가 죽을 수 있었습니다.

- **계층 1**: 본문을 조각마다 받아(압축을 푼 뒤의 바이트) 세다가 상한을 넘는 순간 전송을 끊습니다(`curl_cffi`의 조각 콜백 — 같은 핸들·같은 연결).
  그 실행만 실패이고 물러나지 않습니다. 스트리밍 응답(`stream=True`)은 쓰지 않았습니다 — 설치된 `curl_cffi` 0.16.3에서는 요청마다 핸들을 복제하고 별도 스레드와
  크기 제한 없는 큐를 거쳐, 연결 재사용이 달라지고 끊는 시점이 정확하지 않습니다.
- **계층 2**: 브라우저 컨테이너가 본문이 상한(수집기와 같은 값 — 시험이 대조)을 넘으면 싣지 않고 502로 답합니다. 수집기 쪽 호출은 답을 통째로 읽지 않고, 알린 길이
  (`Content-Length`)가 상한을 넘으면 읽지 않으며, 길이를 알리지 않으면 조각을 세다가 멈춥니다. JSON 봉투는 이스케이프로 본문보다 길 수 있어 본문 상한의 2배 + 64KB까지
  읽고, 풀어 낸 본문을 본문 상한으로 다시 봅니다.
- **남은 위험**: 브라우저 컨테이너 안에서는 브라우저가 페이지를 이미 메모리에 올린 뒤에 길이를 잽니다(그 컨테이너의 메모리 상한 1g과 요청당 시간 상한에 기댐).
  요청 전체의 시간 상한(계층 1 연결 10초·읽기 30초)은 그대로라, 상한 아래 크기를 아주 느리게 주는 응답은 시간 상한으로만 끊깁니다.

## 덧붙임 — 브라우저의 나가는 길(2026-11-12, QA-414)

결정 8은 브라우저 컨테이너에서 '전역 주소가 아닌 목적지 차단(리다이렉트·하위 요청 포함)'을 약속했지만, 구현(요청 가로채기 — `context.route` 처리기)은 리다이렉트로
이어진 요청을 보지 못했습니다. 등록 출처나 그 페이지의 제3자 스크립트가 `허용·전역 주소 → 302 → 내부 주소`로 브라우저 컨테이너에서 내부 망(수집기, 도커 게이트웨이,
클라우드 메타데이터, tailnet)에 요청을 보내게 할 수 있었습니다. 답의 저장·전파는 리다이렉트 덧붙임의 사후 방어가 막지만 요청이 나가는 것은 막지 못했습니다.

**확인한 사실**(2026-11-12 — 이 저장소의 이미지, patchright 1.64.4 + Chrome 157, 망 없는 컨테이너에서 운영과 같은 권한 제거·seccomp, 그 안의 루프백 서버 A·B):

- 처리기는 리다이렉트 홉에 불리지 않습니다. 최상위 `A/redirect → 302 → B/secret`에서 처리기가 받은 요청은 `A/redirect` 하나인데 B가 `/secret`을 받았고, 하위 요청
  (이미지)도 처리기는 `A/img-redirect`까지만 받았는데 B가 `/img-secret`을 받았습니다(request 이벤트는 홉을 알려 주지만 그 자리에서는 끊을 수 없음).
- 드라이버에 `proxy`를 주면 Chrome은 `--proxy-server=…`와 `--proxy-bypass-list=<-loopback>`으로 뜹니다(실제 명령줄 확인). `<-loopback>`이 없으면 Chrome은 루프백·
  링크 로컬행 요청을 **프록시 없이 직접** 붙습니다 — 드라이버 패키지가 기본으로 더하지만 환경변수 `PLAYWRIGHT_DISABLE_FORCED_CHROMIUM_PROXIED_LOOPBACK` 하나로 꺼지고,
  그때 B가 모든 요청을 받는 것을 확인했습니다. 직접 `bypass="<-loopback>"`를 넘기면 그 환경변수와 무관합니다.
- **프록시로 가는 요청의 이름**은 Chrome이 스스로 풀지 않습니다(컨테이너의 53번 포트를 들어 확인 — 프록시가 없을 때는 dns-prefetch·preconnect·이미지·fetch의
  이름을 직접 물었고, 프록시가 있으면 그 이름들의 질문이 0건). 웹소켓(`ws://`)은 `CONNECT`로 프록시에 옵니다.
- 그러나 **WebRTC의 TURN(TCP·TLS) 서버 이름은 Chrome이 프록시 없이 직접 DNS로 묻습니다**(독립 보안 검토가 찾아 이미지에서 다시 확인 — 53번이 그 이름의 질문을
  4건씩 받고 넷로그에 `DNS_TRANSACTION`이 남음. 연결 자체는 이름째로 프록시에 와서 막힘). `--host-resolver-rules=MAP * ~NOTFOUND, EXCLUDE 127.0.0.1`을 주면
  질문이 0건이고 프록시 경유 요청·웹소켓·TURN TCP의 `CONNECT`는 그대로입니다. `EXCLUDE`가 없으면 프록시 연결 자체가 실패합니다(`ERR_PROXY_CONNECTION_FAILED`).
  처음 이 덧붙임에 적었던 '프록시가 있으면 Chrome은 이름을 스스로 풀지 않는다'는 이 길을 빠뜨린 것이었습니다.
- WebRTC의 TCP 길(TURN TCP 서버, 원격 후보로 붙는 ICE-TCP)은 `CONNECT`로 프록시에 옵니다(금지 주소의 TCP 포트는 연결을 받지 않고, 프록시가 전부 허용하게
  바꾼 변이에서는 받음).
- 프록시가 보지 못하는 UDP: WebRTC는 프록시가 있어도 STUN 요청을 UDP로 직접 보냅니다. `--webrtc-ip-handling-policy=disable_non_proxied_udp`면 나가지 않습니다.
  널리 알려진 옛 이름 `--force-webrtc-ip-handling-policy`는 Chrome 157 바이너리에 없고 아무 효과가 없었습니다. WebTransport(QUIC)는 프록시가 없으면 UDP로 직접 나가고,
  프록시가 있으면 나가지 않습니다.
- 프록시가 막은 최상위 이동은 Chrome이 오류로 끝냅니다(평문 http는 `ERR_HTTP_RESPONSE_CODE_FAILURE`, https는 `ERR_TUNNEL_CONNECTION_FAILED` — 금지 주소는 TCP 연결조차
  받지 않음). 프록시가 닫혀 있으면 `ERR_PROXY_CONNECTION_FAILED`로 끝납니다(직접 나가지 않음).
- 프록시를 둔 Chrome은 호스트 60개에 동시에 60개 연결을 열었습니다(프록시 때문에 줄 서지 않음).

**결정**:

- **Chrome의 나가는 길은 컨테이너 루프백의 필터 프록시 하나**입니다(`collector/sidecar/egress.py`, 표준 라이브러리만). 드라이버가 요청마다 프록시를 먼저 열고(127.0.0.1의
  빈 포트) Chrome을 그 주소로만 내보낸 뒤, 브라우저를 닫고 나서 프록시를 닫습니다. 프록시는 연결마다(https·웹소켓은 `CONNECT`, 평문 http는 절대 주소 요청) 목적지 이름을
  스스로 풀고, 풀린 주소가 **전부 전역 주소일 때만**(가로채기와 같은 함수 — `guard.checked_addresses`) **그 검사한 주소로** 붙습니다. 이름을 다시 풀지 않습니다.
- 기존 방어는 그대로 둡니다(겹겹이): 가로채기의 최상위 허용 호스트·하위 요청 검사, 리다이렉트 덧붙임의 사후 방어(최종 주소가 정책 표 밖이면 본문을 버림).
- **차단을 지나가려는 수단이 아닙니다.** 결정 4(프록시·자택 회선·IP 돌려쓰기 없음, 프록시 주소를 읽는 자리도 만들지 않음)는 그대로입니다 — 이 프록시는 같은 컨테이너의
  루프백에 있고 나가는 IP는 서버의 그 IP이며, 주소는 설정으로 받지 않고 코드가 그때그때 받은 포트뿐입니다. `CONNECT` 터널은 바이트를 그대로 넘겨 TLS는 Chrome과 원 서버
  사이 그대로이고, 평문 http 전달에 `Via`·`X-Forwarded-*`를 더하지 않습니다. 계층 1의 '프록시 인자를 넘기지 않는다' 시험도 그대로입니다.
- **프록시를 건너뛰는 길을 닫는 인자**: `<-loopback>`(직접 넘김), `--webrtc-ip-handling-policy=disable_non_proxied_udp`, `--disable-quic`,
  `--host-resolver-rules=MAP * ~NOTFOUND, EXCLUDE 127.0.0.1`(Chrome 자신의 이름 풀이를 전부 '없음'으로 — 프록시 주소만 빼고). 마지막 것이 **페이지가 볼 수 있는
  것을 바꾸는가**: 프록시로 가는 요청의 이름은 원래 프록시가 풀므로 그대로이고(같은 실험에서 페이지의 fetch·웹소켓·WebRTC 결과가 스위치 전후로 같음), 달라지는
  것은 Chrome이 직접 이름을 풀어야 하는 기능뿐입니다 — WebRTC의 STUN·TURN(UDP) 서버 이름과 `.local`(mDNS) 원격 후보. 둘 다 위 정책으로 이미 UDP를 쓰지 못합니다.
  TURN(TCP)은 이름째로 프록시에 가므로 풀이가 없어도 연결을 시도합니다. 덤으로 Chrome이 프록시 없이 직접 붙으려는 127.0.0.1 밖의 목적지는 이름 풀이에서
  실패합니다(루프백 우회를 끄지 않은 변이에서 금지 주소가 요청을 받지 않음 — 겹 하나 더).
- **닫힌 쪽으로 실패**: 프록시를 열지 못하면 브라우저를 띄우지 않습니다. 프록시가 닫히면 Chrome의 요청은 실패합니다. 막힌 최상위 홉은 브라우저 오류 → 브라우저 컨테이너의
  502 → 수집기에서는 출처의 거부가 아니라 '그 실행만 실패'입니다(물러나지 않음, 직전 저장본 유지). 꺼짐 스위치는 두지 않았습니다.
- 평문 http는 연결 하나에 요청 하나만 넘깁니다(`Connection: close`, 본문은 `Content-Length`만큼). 같은 연결에 다른 호스트의 요청이 검사 없이 이어 실리는 길을 두지 않으려는
  것입니다. 등록 출처는 모두 https라 이 길은 리다이렉트·하위 요청의 드문 평문 주소에만 쓰입니다.
- 자원: 한꺼번에 여는 연결 256개(넘으면 503), 프록시 수명 120초(요청 상한 90초 + 여유 — 닫히지 못했을 때의 안전망), 브라우저가 닫히면 열린 터널도 끊습니다.
  (요청이 이 수명 전에 반드시 끝나게 하는 강제 상한 100초는 2026-11-13 덧붙임 '요청 하나의 강제 상한'.)
- **이미지 안 확인**(`python -m sidecar.selfcheck`): 실제 Chrome으로 위 사실들을 다시 봅니다. CI가 이미지를 빌드한 바로 뒤 망 없는 컨테이너에서 돌립니다. Chrome은 판을
  고정하지 않으므로(빌드 시점의 안정판) 스위치 이름이 또 바뀌면 여기서 걸립니다 — 정책 스위치와 이름 풀이 규칙을 뺀 대조 실행에서 STUN이 실제로 나가고 TURN 이름을
  DNS로 묻는 것까지 봅니다. Chrome이 스스로 이름을 풀었는지는 넷로그로 봅니다(이름 풀이 이벤트 0건).

**덮는 범위**: 최상위·하위 요청의 리다이렉트 홉, fetch·XHR, 웹소켓, 이름을 검사한 뒤의 주소 바뀜(DNS 재결합), 루프백·링크 로컬(클라우드 메타데이터)·사설·CGNAT(tailnet)·
IPv4를 감싼 IPv6(매핑·호환·NAT64·6to4·Teredo)·폐기된 site-local(`fec0::/10`), 숫자로 쓴 주소(`2130706433` 등 — 풀린 주소로 검사), WebRTC의 UDP와 TCP 길(TURN TCP·ICE-TCP),
QUIC, Chrome 자신의 DNS 질문.

**검토한 대안**:

- **서버 방화벽(`DOCKER-USER` 사슬에서 `fetchnet`의 사설·링크 로컬·tailnet행을 막음 — 계획서 D-11의 (가))**: 망 수준이라 가장 굵고 Chrome이 장악된 경우까지 덮습니다.
  대신 서버 설정이 바뀌고 배포 스크립트가 규칙을 관리해야 하며, 같은 브리지 안의 트래픽(브라우저 → 수집기)과 호스트 자신으로 가는 트래픽(INPUT 사슬)은 `DOCKER-USER`를
  지나지 않아 따로 손봐야 하고, 저장소의 시험으로 고정하기 어렵습니다. 이번에는 하지 않았습니다 — 아래 남은 위험의 마지막 항목 때문에 선택지로 남깁니다.
- **기록만(D-11의 (나))**: 요청이 나가는 것을 그대로 둡니다.
- **가로채기에서 드라이버가 요청을 대신 보내며 리다이렉트를 직접 따라감(`route.fetch(max_redirects=0)`)**: 요청을 Chrome이 아니라 드라이버 프로세스가 보내게 되어
  브라우저의 겉모습(TLS·HTTP 지문)이 바뀌고, 웹소켓과 재결합은 여전히 못 덮습니다.
- **PAC·호스트 규칙 같은 Chrome 설정만으로**: 이름이 풀린 주소를 보고 정할 수 없습니다.

**남은 위험**(정직하게):

- 최상위 리다이렉트가 허용 호스트 목록 밖의 **전역** 호스트로 가는 요청은 여전히 나갑니다. 허용 호스트 규칙은 가로채기에만 있고(홉에는 불리지 않음) 프록시는 전역 여부만
  봅니다. 하위 요청은 원래 아무 전역 호스트에나 갈 수 있으므로 새 노출은 아니고, 그 답의 저장·전파는 리다이렉트 덧붙임의 사후 방어가 막습니다.
- WebRTC의 UDP와 Chrome의 직접 DNS는 Chrome 스위치에 기댑니다. WebRTC 스위치의 이름은 이미 한 번 바뀌었습니다. CI의 이미지 안 확인이 잡지만, 서버는 배포할 때 Chrome
  안정판을 새로 받으므로 CI가 본 판과 다를 수 있습니다 — 배포 뒤 서버에서 같은 확인을 돌립니다([DEVELOPMENT §7](../DEVELOPMENT.md)). WebRTC가 원격 후보로 보내는
  **UDP** 연결 확인은 실험에서 일으키지 못해 따로 확인하지 못했습니다(그 정책이 UDP 포트 할당을 끄는 것으로 알려져 있음 — 추정). TCP 쪽(TURN TCP·ICE-TCP)은
  프록시로 오는 것을 확인했습니다.
- HTTP/3이 프록시가 있을 때 직접 UDP로 나가는지는 확인할 서버가 없어 보지 못했습니다. `--disable-quic`으로 꺼 두었고, WebTransport가 UDP를 보내지 않는 것까지 확인했습니다.
- **프록시의** 이름 풀이는 컨테이너의 풀이 서버(도커 내장 DNS)로 갑니다. 페이지가 내부 이름을 대면 그 질문은 나갑니다(주소가 사설이라 연결은 하지 않음). Chrome
  자신의 질문은 이름 풀이 규칙으로 막았지만, 넷로그에 남지 않는 다른 풀이 길이 Chrome에 더 있는지는 알지 못합니다(본 것은 위 실험의 요청 종류까지).
- 목적지 포트는 가리지 않습니다(전역 주소면 어느 포트든 — 가로채기의 기존 규칙과 같음).
- **서버 자신의 공인 주소는 '전역'이라 프록시가 막지 않습니다**(보안 검토 지적 — 추정, 서버에서 실험하지 않음). 그 주소로 가는 트래픽은 인스턴스 밖으로 나가지
  않아 클라우드 방화벽을 지나지 않고, 호스트에서 모든 주소(`0.0.0.0`·`[::]`)로 듣는 서비스(sshd 등)에 브라우저 컨테이너에서 TCP가 닿습니다. 앱 포트는 모두
  루프백에만 열려 있어([ADR 0023](0023-vultr-deployment.md)) 해당하지 않고, Chrome이 그런 포트로 낼 수 있는 바이트는 제한적입니다(HTTP·TLS·웹소켓 모양). 가로채기의
  기존 규칙도 같았으므로 새 노출은 아닙니다. 코드로 닫지 않았습니다 — 서버 주소를 이 컨테이너에 알려 주는 설정을 새로 만들어야 하고, 닫는 제자리는 망 수준
  방화벽(D-11의 (가) — `fetchnet` 브리지에서 호스트로 들어오는 INPUT)입니다. 그때까지는 서버에서 루프백·tailnet 밖으로 듣는 것이 무엇인지 확인해 둡니다
  ([DEVELOPMENT §7](../DEVELOPMENT.md)의 `ss -ltn` 줄).
- 프록시는 Chrome과 같은 컨테이너에 있습니다. Chrome의 샌드박스가 뚫려 임의 코드가 그 컨테이너에서 돌면 프록시를 거치지 않고 직접 소켓을 열 수 있습니다. 그때 남는 것은
  컨테이너 격리(별도 망·권한 제거)뿐이고, 내부 주소행을 막는 것은 망 수준 방화벽만 할 수 있습니다.
- **2026-11-13 사용자 결정 — 위 둘은 그대로 둡니다**: (1) 망 수준 방화벽(D-11의 (가))은 넣지 않습니다 — 배포 때 확인하니 서버에서 루프백·tailnet 밖으로 듣는 TCP는
  sshd(22) 하나라 실익이 작고, 배포 뒤 `ss -ltnH` 확인을 계속합니다. (2) 가로채기의 '최상위 허용 호스트' 규칙이 리다이렉트 홉에는 걸리지 않아 허용 호스트 → 목록 밖
  전역 호스트의 요청이 나가는 것도 그대로 둡니다(프록시에 허용 목록을 넘기지 않음) — 내부 망 노출이 아니고, 최종 주소가 정책 표 밖이면 본문을 버리며(QA-388), 하위
  요청은 원래 호스트를 가리지 않습니다. 듣는 포트가 늘거나 계층 2 출처가 목록 밖으로 자주 넘기는 것이 보이면 다시 올립니다.

**감수한 단점**:

- HTTP/3을 쓰지 않고(프록시를 둔 Chrome의 보통 모습 — TCP 위의 HTTP/2) WebRTC가 UDP를 쓰지 못합니다. 출처가 보는 IP·TLS는 그대로지만, 이것이 사람 확인 통과에 영향을
  주는지는 서버의 실행 기록으로만 압니다.
- 평문 http 요청에는 연결 재사용이 없고, 원 서버가 보는 `Connection` 머리글이 `close`입니다(직접 붙을 때는 `keep-alive`).
- 이름 풀이가 호스트마다 두 번 일어납니다(가로채기 한 번, 프록시 한 번).
- 프록시를 둔 Chrome은 목적지 이름을 스스로 풀지 않으므로 DNS의 HTTPS 레코드를 받지 못합니다 — 그 레코드로만 오는 ECH(암호화된 ClientHello) 설정과 HTTP/3 알림을
  쓰지 않을 것입니다(이름 질문이 0건인 것까지 본 추론 — TLS 핸드셰이크에서 ECH가 빠지는 것을 직접 보지는 않았습니다). 프록시를 쓰는 보통 Chrome과 같은 모습입니다.
- Chrome 자신의 이름 풀이가 전부 실패하므로, 프록시를 거치지 않고 이름을 풀어야 하는 Chrome 기능(WebRTC의 UDP 서버 이름, mDNS 후보)은 동작하지 않습니다.
- 프록시가 막은 평문 하위 요청은 페이지에 빈 403으로 보여 원 서버의 403과 구분되지 않습니다(브라우저 컨테이너의 로그 '막은 목적지: 호스트'로 구분). 풀리지 않는 이름도
  같은 로그로 남습니다(Chrome 자신의 배경 요청 포함).
- Chrome 안정판이 위 스위치의 이름을 바꾸면 CI의 이미지 잡이 실패합니다(의도한 것 — 고칠 때까지 UDP·DNS 길이 열린 이미지를 배포하지 않게).

## 덧붙임 — 요청 하나의 강제 상한(2026-11-13, QA-416)

결정 8은 브라우저 컨테이너에 '요청당 시간 상한'을 약속했지만, 구현의 상한(`REQUEST_SECONDS` 90초)은 페이지 받기의 반복문이 도는 사이에만 검사됐습니다. 등록 출처나
그 페이지의 제3자 스크립트가 DOMContentLoaded 뒤에 메인 스레드를 붙잡으면(고의든 버그든) 드라이버의 호출이 돌아오지 않아 `/fetch`가 '한 번에 한 건' 잠금을 쥔 채
끝나지 않았습니다. 그 뒤의 모든 요청은 429로 거절되고 `/health`는 ok라 컨테이너도 다시 뜨지 않아, 계층 2 전체가 사람이 컨테이너를 다시 띄울 때까지 멈춥니다(수집기는
110초 뒤 그 실행만 실패로 끝내고 직전 저장본을 유지 — 값이 틀리는 결함은 아님). 2026-11-12 보안 검토가 '범위 밖 관찰(추정, 실행 안 함)'로 남긴 것이고, 사용자가
'상한을 둔다'로 정했습니다(2026-11-13).

**확인한 사실**(2026-11-13 — 이 저장소의 이미지, patchright 1.64.4 + Chrome 157.0.8103.38, 망 없는 컨테이너에서 운영과 같은 권한 제거·seccomp·init, 그 안의 루프백 서버):

- 페이지가 DOMContentLoaded 뒤에 메인 스레드를 붙잡으면(`setTimeout(() => { for (;;) {} }, 0)`) **돌아오지 않는 호출**: `page.evaluate`, `page.content()`,
  `page.title()`, `page.mouse.wheel`·`move`·`click`, `frame.frame_element().bounding_box()`. 드라이버의 기본 시간 상한(`set_default_timeout`)은 `evaluate`에 먹지 않습니다.
  **돌아오는 호출**: `page.wait_for_timeout`(드라이버 쪽 타이머), `page.url`·`page.frames`(드라이버가 들고 있는 값), 그리고 `context.close()`(0.1초)·
  `page.close()`(0.5초)·드라이버 닫기(0.08초) — 보안 검토의 추정 가운데 '닫기도 붙잡힌다'는 틀렸고 나머지는 맞았습니다.
  시간 상한이 먹는 호출도 있습니다(`page.wait_for_function`·`locator.evaluate`·`page.inner_html`의 `timeout` — 3초에 TimeoutError). 마우스 호출에는 그런 인자가 없습니다.
- 운영 경로(`_load`) 그대로 열면 끝나지 않는 페이지: DOMContentLoaded 뒤 끝나지 않는 스크립트(`_blocked`의 `evaluate`에서), 0.9초 뒤에 붙잡는 스크립트(첫 `evaluate`는
  지나가고 읽기 전 머무는 `mouse.wheel`에서), 답 없는 주소를 기다리는 동기 XHR, `confirm()`을 되풀이하는 스크립트, `window.print()`. 끝나는 페이지: `alert()` 한 번(드라이버가
  대화상자를 닫음), `beforeunload`에서 붙잡는 페이지(닫기 0.12초), 끝없는 `document.write`(6.7초에 렌더러가 죽어 `Target crashed` 오류), 파싱 중의 무한 루프
  (DOMContentLoaded가 오지 않아 첫 이동의 상한 45초에 오류).
- 프로세스 나무는 `이 프로세스(uvicorn) → 드라이버(node) → Chrome 브라우저 프로세스 → zygote·렌더러·GPU·망 서비스`입니다. **명령줄에 그 요청의 프록시 주소
  (`--proxy-server=http://127.0.0.1:<포트>`)를 인자 하나로 가진 것은 브라우저 프로세스 하나뿐**이고(자식의 명령줄에는 없음), 브라우저 프로세스는 자기 세션·그룹의
  머리입니다. crashpad 처리기 둘은 init의 자식으로 떨어져 나가 있습니다.
- **그 브라우저 프로세스 하나를 다른 스레드에서 끝내면(SIGKILL) 붙잡혀 있던 호출이 0.02초 안에 `TargetClosedError`로 돌아옵니다.** 이어지는 `context.close()`는 0.00초
  (오류 없음), 드라이버 닫기는 0.01~0.04초이고, 0.2초 뒤에는 Chrome의 자식·crashpad까지 남은 프로세스가 없습니다(좀비는 `init: true`가 거둠). 프로세스 그룹에 보내도
  같았습니다. seccomp 프로필은 `kill`을 원래 허용합니다(프로필을 넓히지 않음).
- 강제로 끝난 Chrome은 프로필 폴더에 잠금 링크 셋(`SingletonLock` → `호스트이름-pid`, `SingletonSocket`, `SingletonCookie`)을 남깁니다. 같은 컨테이너에서는 다음 Chrome이
  죽은 pid의 잠금을 스스로 치우고 0.2초에 뜹니다(열린 페이지는 `about:blank`뿐 — 붙잡던 페이지를 다시 열지 않음). **잠금의 호스트 이름이 다르면 다음 Chrome은 뜨지 않습니다**
  (50초 가까이 기다려도 띄우기가 돌아오지 않음 — 화면에 '다른 컴퓨터에서 쓰는 프로필' 창이 뜬 것으로 추정). 컨테이너를 다시 만들면 호스트 이름이 바뀌고 프로필은
  볼륨에 남으므로, 끝낸 뒤 잠금을 치우지 않으면 다음 배포 뒤부터 계층 2가 멈춥니다.
- 드라이버(node)가 멎어 있으면(SIGSTOP으로 흉내) 브라우저를 끝내도 호출이 돌아오지 않고, 드라이버를 끝내면 0.01초 안에 `Connection closed while reading from the driver`로
  돌아옵니다(남는 것 없음). 드라이버 패키지의 Chrome 띄우기 기본 시간 상한은 180초로, 수집기가 기다리는 110초보다 깁니다(이미지의 드라이버 코드에서 확인).

**결정**:

- **요청 하나는 강제 상한 100초(`driver.HARD_SECONDS` = 반복문의 상한 90초 + 10초) 안에 끝납니다.** 드라이버는 띄우기부터 닫기까지를 작업 스레드에서 돌리고, 부른
  스레드는 요청이 시작된 때부터 100초까지만 기다립니다. 넘기면 **그 요청의 Chrome**을 끝냅니다 — 프로세스 표(`/proc`)에서 명령줄에 그 요청의 프록시 주소를 인자 하나로
  가진 프로세스와 그 자손(`collector/sidecar/reap.py`, 표준 라이브러리만). 프록시는 요청마다 새 포트로 열리므로 그 인자가 요청의 표지입니다. 인자는 통째로 같아야 하고,
  이 프로세스·그 조상(xvfb-run·init)·형제(Xvfb)·다른 포트의 프록시 인자를 가진 프로세스는 대상이 아닙니다(시험으로 고정). 붙잡혀 있던 호출이 오류로 돌아오면 작업 스레드가
  문맥·드라이버를 평소 길로 닫습니다.
- 끝낸 뒤 **정리를 4초(`CLEANUP_SECONDS`)까지** 기다립니다(잰 값은 0.05초 안쪽). 절반(2초)이 지나도 작업 스레드가 끝나지 않으면 브라우저를 한 번 더 찾아 끝내고, 그
  브라우저를 띄운 **드라이버 프로세스**(브라우저의 부모가 이 프로세스의 직접 자식일 때만 — 끝내기 직전에 다시 확인)도 끝냅니다. 그래도 끝나지 않으면 더 기다리지 않고
  답합니다(오류 로그 한 줄 — 작업 스레드 하나가 남음). 어느 경우에도 필터 프록시는 닫습니다.
- **답과 로그**: 502(`DriverError` — '요청 상한(100초)을 넘겨 브라우저를 끝냄: 호스트'). 로그는 기존의 '받지 못함' 경고 한 줄이고 주소는 호스트만 남습니다(경로·쿼리 없음).
  그 요청의 본문은 버립니다(정리하는 사이에 페이지 받기가 끝났더라도 쓰지 않음). 수집기 쪽 동작은 지금의 502와 같습니다(`fetch/browser_client.py`·`fetch/ladder.py` —
  고치지 않음): 그 호스트가 계층 2부터 시작하는 상태면 그 실행만 실패하고(물러나지 않음, 직전 저장본 유지), 계층 1의 거부 뒤에 올라온 요청이면 아래 계층의 거부로 닫습니다.
- **프로필 잠금**: 끝낸 뒤 주인 없는 잠금 링크 셋을 치웁니다. 주인이 방금 끝낸 프로세스거나, 이미 없거나, 다른 호스트 이름이면 지우고, 이 컨테이너에서 살아 있는 프로세스의
  잠금이면 손대지 않습니다. 프로필의 다른 것(쿠키)은 그대로입니다.
- 평소 요청은 바뀌지 않습니다 — 페이지 받기(`_load`)·Chrome 인자·체크박스 누르기·읽기 전 머무는 동작·시간이 그대로이고, 프로세스 표를 보지도 프로필에 손대지도 않습니다
  (달라지는 것은 그 일이 작업 스레드에서 돈다는 것뿐). 격리 설정(포트 없음·망 하나·권한 제거·seccomp)과 의존성은 그대로이고, 꺼짐 스위치는 두지 않았습니다.
- **값의 선후**(시험 `test_QA416_상한들의_선후`가 고정): 반복문의 상한 90초 < 강제 상한 100초 < 정리 대기까지 104초 < 수집기가 이 컨테이너의 답을 기다리는 110초 <
  필터 프록시의 수명 120초. 10초는 가장 긴 정상 경로(90초 직전에 시작한 반복 한 바퀴 — 체크박스를 누르면 약 5.5초 — 와 본문 읽기·닫기, 합쳐 96초쯤)를 끊지 않는 값이고,
  104초는 수집기가 포기하기 전에 502로 답할 수 있는 값입니다. 프록시 닫기는 보통 수 ms이고, 프록시의 연결 스레드가 끝나지 않는 최악에는 5초까지 걸릴 수 있습니다
  (그때는 수집기가 먼저 포기할 수 있지만 결과는 같은 '그 실행만 실패'이고, 잠금은 그 뒤에 풀립니다).
- **이미지 안 확인 9번**: 메인 스레드를 붙잡는 페이지를 운영 경로(`ChromeDriver.fetch`) 그대로 열어, 짧게 준 상한(4초)에 오류로 돌아오고, Chrome 프로세스와 프로필 잠금이
  남지 않고, 바로 이어 연 평소 페이지가 같은 프로필로 뜨는지 봅니다. 방어를 뺀 변이 셋에서 이 항목이 실패하는 것을 확인했습니다 — 상한 없이 기다리면 18초에 '돌아오지
  않음'으로 끝내고(붙잡힌 브라우저가 떠 있어 뒤의 확인은 하지 않음), 끝내지 않으면 8.0초에 돌아오고 Chrome이 남아 다음 요청이 '프로필 사용 중'으로 실패하고, 잠금을
  치우지 않으면 링크 셋이 남습니다.
- 고친 이미지에서 실제 내부 서비스(uvicorn)와 Chrome으로 본 것(상한 5초): 위의 붙잡는 페이지 다섯 꼴(과 체크박스 누르기 길에서 붙잡는 페이지) 모두 5.0초에 502, 도는 동안 둘째 요청은 429·`/health`는 ok,
  끝난 뒤 프로세스는 넷(init·xvfb-run·Xvfb·이 프로세스)·좀비 0·남은 스레드 0·잠금 없음, 바로 다음 요청은 200. 연달아 여섯 번 끝내도 쌓이는 프로세스가 없습니다.
  다른 호스트 이름의 잠금을 둔 프로필에서는 첫 요청이 5.0초에 502로 끝나며 잠금이 치워지고 다음 요청부터 200입니다. 드라이버를 멈춰 두면 7.0초에 502(드라이버까지 끝남).

**검토한 대안**:

- **호출마다 시간 상한이 있는 API로 바꿈**: `evaluate`·`content()`는 상한이 먹는 다른 호출로 바꿀 수 있지만 마우스 호출(스크롤·체크박스 누르기)에는 그런 인자가 없고,
  호출을 바꾸면 평소 요청의 동작이 달라지며, 뒤에 더하는 호출마다 빠뜨릴 수 있습니다. 어디서 붙잡히든 끝나야 한다는 요구에 맞지 않습니다.
- **같은 스레드에서 돌리고 감시 타이머가 Chrome을 끝냄**: 변경이 가장 작지만, 브라우저를 끝내도 호출이 돌아오지 않는 경우(드라이버가 멎음 — 위 실험)에는 여전히
  끝나지 않습니다. 부른 스레드가 기다리는 시간을 스스로 끊는 쪽이 '반드시 돌아온다'를 구조로 보장합니다.
- **요청마다 하위 프로세스에서 돌리고 부모가 끝냄**: 가장 굵은 격리지만, 드라이버가 Chrome을 자기 세션으로 떼어 띄우므로 부모가 그룹으로 끝낼 수 없어 어차피 프로세스
  표에서 찾아야 하고, 본문(8MB까지)을 프로세스 사이로 넘겨야 하며, 요청마다 파이썬 기동 비용이 붙습니다.
- **프로세스 그룹에 신호 하나로**: 실험에서 결과는 같았습니다. 다만 '브라우저 프로세스가 그룹의 머리'라는 드라이버 패키지의 띄우는 방식에 기대게 되어, 명령줄로 확인한
  프로세스와 그 자손을 하나씩 끝내는 쪽을 골랐습니다.
- **`/health`가 오래 붙잡힌 요청을 알려 컨테이너를 다시 띄우게 함**: 도커는 unhealthy가 된 컨테이너를 스스로 다시 띄우지 않아(알려진 동작 — 여기서 실험하지 않음) 따로
  감시 도구가 필요하고, 다시 뜨는 동안 계층 2가 비며, 잠금 링크 문제는 그대로 남습니다.

**감수한 단점**:

- 상한으로 끝난 요청의 본문은 버립니다. 정상인데 100초를 넘기는 요청이 있다면 그것도 끝납니다(가장 긴 정상 경로는 96초쯤으로 계산 — 재 본 값은 아님).
- 붙잡는 페이지 하나가 최대 100초 동안 계층 2를 차지합니다(그동안 다른 요청은 429 — 수집기에서는 그 실행만 실패). 출처가 매번 붙잡으면 그 출처의 요청마다 되풀이됩니다.
  계층 2부터 시작하는 호스트의 전송 실패는 물러남에 세지 않으므로(결정 6은 출처의 거부만) 다음 일정에 다시 열고, 빈도는 비주기 일정과 하루 예산이 묶습니다.
- 강제로 끝난 Chrome은 프로필을 깨끗이 닫지 못합니다. 끝나기 직전에 받은 쿠키가 디스크에 닿지 않았을 수 있고(추정 — 확인하지 않음), 컨테이너의 `/tmp`에 빈 폴더
  (`com.google.Chrome.*` 소켓 폴더 — 끝낼 때마다 하나, 드물게 드라이버의 임시 폴더)가 남습니다. 컨테이너를 다시 만들면(배포) 사라집니다.
- 찾기는 리눅스의 `/proc`에 기댑니다(브라우저 컨테이너는 리눅스). 프로세스 표를 읽은 때와 신호를 보내는 때 사이(수 ms)에 번호가 다른 프로세스의 것이 되는 경합은
  막지 않았습니다(같은 컨테이너 안의 일이고, 그 사이에 뜨는 것은 그 요청의 Chrome뿐).
- 브라우저도 드라이버도 찾지 못한 채 작업 스레드가 붙잡혀 있는 경우(재현한 적 없음 — 예: 드라이버가 Chrome을 띄우기도 전에 멎음)에는 104초에 답하되 스레드 하나와
  드라이버 프로세스가 남을 수 있습니다. 오류 로그('정리가 끝나지 않음')가 남고, 그때는 컨테이너를 다시 띄웁니다([DEVELOPMENT §7](../DEVELOPMENT.md)).
- 이미지 안 확인이 10초쯤에서 17초쯤으로 늘었습니다.

**남은 위험**:

- 드라이버 패키지나 Chrome이 프록시 주소를 명령줄 인자로 넘기지 않게 바뀌면 그 요청의 Chrome을 찾지 못합니다. 그때 요청은 104초에 답하지만 Chrome이 남아 다음 요청이
  '프로필 사용 중'으로 실패합니다(위 변이와 같은 모양). 이미지 안 확인 9번이 잡고, 0번도 그 인자를 봅니다. 서버는 배포할 때 Chrome 안정판을 새로 받으므로 배포 뒤 서버에서
  같은 확인을 돌립니다.
- 프로필 잠금의 호스트 이름 문제는 이 결함과 따로도 생깁니다 — 요청 도중에 컨테이너가 강제로 내려가고(배포·메모리 상한) 다시 만들어지면 옛 호스트 이름의 잠금이 볼륨에
  남습니다. 이번 수정 뒤에는 첫 요청이 100초에 실패하면서 잠금이 치워져 다음 요청부터 풀립니다(실험으로 확인). Chrome을 띄우기 전에 미리 치우는 것은 하지 않았습니다
  (다른 결함 — 한 번의 실패를 없애려면 기동 전 정리를 더하면 됨).
