# 0003. 백업·복원: 끝 표시 확인과 한 트랜잭션 통째 교체

- 상태: 채택 (2026-09)
- 지키는 방법: `collector/tests/test_db_scripts.py`(실제 PostgreSQL로 7가지 상황), 스크립트
  `scripts/db-backup.sh`·`scripts/db-restore.sh`·`scripts/db-common.sh`

## 배경

재현해 보니 두 명령이 모두 **실패를 성공으로 알렸습니다.**

- `make backup`: DB에 닿지 못해도 종료 코드 0, 0바이트 백업 파일을 남김
- `make restore`: 데이터가 있는 DB에 덤프를 그대로 부어 CREATE·COPY가 오류 21건으로 실패했는데도
  종료 코드 0, 값은 백업 시점으로 돌아오지 않음

백업이 조용히 비어 있거나 복원이 조용히 반만 되면, 가장 필요할 때 데이터를 잃습니다.

## 결정

**백업**
1. `.partial` 파일에 쓰고, 덤프 끝 표시(`PostgreSQL database dump complete`)가 있을 때만 이름을 바꿉니다.
2. 실패하면 파일을 지우고 0이 아닌 코드로 끝납니다.

**복원 = "DB를 백업 시점으로 통째 교체"**
1. 백업 파일이 끝까지 기록된 것인지 먼저 확인합니다(끊긴 파일이면 시작하지 않음).
2. 확인을 받습니다(`--yes` 없이 터미널이 아니면 거부).
3. 쓰기가 겹치지 않게 수집기·백엔드를 잠시 멈춥니다(끝나면 실패해도·터미널이 닫혀도 다시 켬).
4. 지금 DB를 `backups/pre-restore-….sql`로 백업합니다 — 잘못 복원해도 되돌릴 수 있게. 서비스를 멈춘 **뒤에** 뜹니다
   (2026-11-12 개정 — 아래 '개정').
5. **한 트랜잭션 안에서** public 스키마를 지우고 덤프를 적재합니다. 트랜잭션은 psql 옵션
   (`--single-transaction`)이 아니라 입력 안의 `BEGIN` … `COMMIT`으로 엽니다 — psql 옵션은 입력이 오류 없이
   끝나기만 하면(EOF) COMMIT을 보내, 복원 중에 창을 닫거나 Ctrl-C를 누르면 반쯤 적재된 상태가 확정됐습니다.
   이제 COMMIT은 덤프를 끝까지 보낸 뒤에만 있고, 그 전에 끊기면 연결이 닫히면서 서버가 되돌립니다.
   성공 여부는 psql 종료 코드가 아니라 COMMIT 뒤에 찍는 표시로 판단합니다.
   한 문장이라도 실패하거나 입력이 끊기면 스키마 삭제까지 전부 되돌아가 DB는 4번 시점 그대로입니다.

## 이유

- "합치기" 복원(기존 행 위에 덮어쓰기)은 덤프 형식상 충돌이 나고, 어떤 행이 어느 시점 것인지 알 수 없습니다.
  복원을 쓰는 상황(잘못된 수집·마이그레이션 사고)에서는 "그 시점으로 되돌리기"가 기대 동작입니다.
- 되돌릴 수 없는 작업(스키마 삭제)을 하므로, 직전 상태 백업 + 한 트랜잭션 + 확인 세 겹으로 막습니다.

## 대안과 버린 이유

- `pg_restore --clean` + custom 형식 덤프: 기존 백업 파일(평문 SQL)과 호환되지 않고, 여러 트랜잭션으로 나뉩니다.
- 새 DB를 만들어 적재 후 이름 바꾸기: DB 이름 변경에는 모든 연결을 끊어야 해 결국 서비스를 멈춰야 하고, 절차가 길어집니다.

## 결과

| 상황 | 테스트가 확인하는 것 |
|---|---|
| 백업 실패 | 파일을 남기지 않고 실패 코드 |
| 백업 성공 | 끝 표시가 있는 덤프 |
| 복원 성공 | 값·행 수가 백업 시점과 같음 + 복원 전 상태 파일 1개 |
| 복원 도중 실패 | 아무것도 바뀌지 않음(스키마 삭제까지 되돌림) |
| 복원 입력이 중간에 끊김 | 반쯤 적재된 상태를 확정하지 않고 실패로 알림 |
| 끝까지 기록되지 않은 백업 | 시작하지 않음(안전 백업도 만들지 않음) |
| 확인 없음 | 거부 |

처음 스크립트로는 6개 중 5개가, 리뷰에서 찾은 "입력이 끊김" 상황은 `--single-transaction` 판에서도 실패했고
(종료 코드 0·성공 문구·반쯤 복원), 지금은 7개 모두 통과합니다. CI에서도 실행됩니다.

## 개정 (2026-11-12 — QA-370·QA-372)

- **순서를 정지 → 안전 백업 → 복원으로 바꿨습니다(QA-372).** 예전에는 안전 백업(3)을 서비스 정지(4)보다 먼저 떠, 덤프 시작부터 정지가
  끝날 때까지의 쓰기(수집·장부)가 안전 백업에 없었습니다 — 그 백업으로 되돌리면 그 구간이 사라집니다. 이유: 안전 백업은 '복원 직전
  상태'여야 하고, 멈춘 뒤의 DB만 그 뜻에 맞습니다. 버린 대안: 순서를 두고 안내만 고치기(되돌렸을 때 빠지는 구간이 남음).
  감수한 단점: 중단 시간이 덤프 시간만큼 늘어납니다(덤프 약 460MB). 안전 백업이 실패하면 복원하지 않고 멈춘 서비스를 다시 켭니다.
- **다시 켜기는 출력이 닫히거나 끊김 신호를 받아도 돕니다(QA-370).** 복원 중 터미널이 닫히면 EXIT trap의 안내 줄이 닫힌 출력에 쓰다
  실패해 `docker compose start`에 닿지 못했고, `compose stop`으로 멈춘 서비스는 자동으로 다시 뜨지 않습니다. trap 안에서 HUP·PIPE·INT·TERM을
  무시하고 `set -e`를 풀고 안내 줄의 실패를 넘깁니다. 세션에서 떼어 돌리는 것(nohup·tmux)은 넣지 않았습니다(제안으로 둠).
- 시험: `collector/tests/test_restore_interrupt.py`(가짜 docker의 호출 기록 — psql·pg_dump 클라이언트 없이 돎)가 순서, 끊김 뒤 다시 켜기,
  안전 백업 실패 뒤 다시 켜기를 봅니다.
