# 0011. 알림 파이프라인: 사건과 알림함을 나누고, 매번 전부 평가(멱등), 화면 알림함만으로 시작

- 상태: 채택 (2026-10)
- 지키는 방법:
  - `AlertRulesTest`: 국면 3일 확정, 판정 불가 무시, 연속 N일, 13F 신규
  - `AlertEvaluatorDbTest`: 한 번만, 규칙 끄기, 백필 금지, 지난 사건, 트리거 하나가 실패해도 다른 트리거는 배달(QA-129)
  - `AlertEvaluatorFailureTest`: 배달 단계 하나가 실패해도 나머지 배달·정리는 계속하고 단계 이름을 경고에 남김(코드 결함이면 스택 트레이스까지), 연결 문제가 아닌 DB 오류(SQL 문법·제약 위반)는 그 단계만 건너뜀, DB에 닿지 못하면(연결 시간 초과 포함) 그 주기를 한 번에 멈춤(QA-129)
  - `AlertServiceTest`: 등급별 상한, 수집 범위, 확정 기록만, 행동 지시 금지어
  - `AlertServiceConcurrencyTest`: 동시 요청에도 상한(QA-092)
  - `test_tasks.py`(관심 종목 수집 범위), `test_table_ownership.py`

## 배경

국면 전환·외국인 연속 순매수·관심 기관 신규 편입을 알려야 합니다([명세 C](../specs/2026-10-09-feature-spec.md)). 알림은 잘못 울리면 신뢰를 잃습니다. 위험은 세 가지입니다.
- 잠정치로 울림
- 같은 사건이 두 번 울림
- 처음 켤 때 과거 사건이 쏟아짐

외부 채널(메일·메신저)은 이번 범위에서 뺐습니다(D2).

## 결정

1. **사건(`alert_events`, 전역 사실)과 알림함 항목(`alert_deliveries`, 누구에게)을 나눕니다.**
   - 사건 키(`event_key`)가 유일하고, 알림함은 (사건, 사용자, 채널)이 유일합니다.
2. **새 데이터를 "알아내지" 않고 5분마다 전부 평가합니다.**
   - 같은 데이터면 같은 사건 키라, 몇 번 평가해도 결과는 한 번입니다.
   - 수집기 실행 번호를 이어 처리하는 방식은 놓치는 건이 생겨 버렸습니다. 시간 초과 후 늦게 쓰인 저장본이 있고, 8개 스레드가 따로 커밋하기 때문입니다.
   - 평가는 `StoreReader.quietly`로 읽어 수집을 일으키지 않습니다(ADR 0008).
   - **트리거마다 따로 실패합니다**(QA-129). 세 트리거·종류별 배달·알림함 정리 가운데 한 단계가 예외를 내면 단계 이름과 함께
     경고만 남기고 나머지는 계속합니다. 경고에는 코드 결함(NPE 등)일 때만 스택 트레이스를 붙이고, DB 오류는 고칠 때까지
     5분마다 되풀이되므로 한 줄만 남깁니다. 멱등이라 일부만 된 주기도 다음 주기에 맞춰집니다. DB를 쓸 수 없는 실패
     (`DataAccessResourceFailureException` — 연결을 얻지 못함·연결 끊김·DB 자원 부족)만 그 주기를 한 번에 멈춥니다.
     SQL 문법 오류·제약 위반 같은 다른 DB 오류는 그 단계만 건너뜁니다. DB 오류 전부로 넓히면 표 하나의 스키마가 바뀌거나
     평가 도중 규칙이 지워져(FK 위반) 다시 모든 알림이 멈춥니다.
3. **국면 전환은 새 판정이 판정 기록에서 연속 3일 이어질 때만 알립니다**(사용자 결정, 2026-10-09).
   - 3년 재현에서 국면이 약 58번 바뀌었기 때문입니다.
   - 화면의 판정 규칙은 그대로이고, 알림만 확정을 기다립니다.
   - "판정 불가" 날은 세지도 끊지도 않습니다. 기록의 첫 확정 국면은 직전을 모르므로 전환이 아닙니다.
   - **새 데이터인 기록만 셉니다**(사용자 결정, 2026-10-11, QA-054). 기록은 매일(토·일 포함) 남지만 주말 기록은 금요일과
     입력이 같아, 세면 새 데이터 하루로 '3일 확정'이 됐습니다. 입력 기준일(`asOf`)이 직전 기록과 모두 같으면 세지도 끊지도 않습니다.
4. **잠정치를 쓰지 않습니다.**
   - 투자자 매매는 오늘(KST) 기록을 뺍니다.
   - 종목 기록은 저녁 확정 칸이 모두 찬 경우만 오늘 기록도 씁니다. 지난 기록도 칸이 비었으면(장중에 받고 다시 받지 않음) 그날은 '모름'으로 연속을 끊습니다(QA-064).
   - 연속은 값을 모르는 날·0인 날에서 끊고, 정확히 N일이 된 날 한 번만 알립니다.
5. **규칙을 만든 날보다 앞선 사건은 보내지 않습니다.** 사건이 발생하고 3일 넘게 지나서 알림함에 들어가면 '지난 사건'으로 표시하고, 읽지 않은 수에 세지 않습니다.
6. **관심 기관·관심 종목은 규칙의 `params`(cik·code)로 둡니다.**
   - 설계 초안의 별도 목록 테이블은 두지 않았습니다. 규칙과 대상이 1:1이라 같은 정보를 두 번 저장하게 됩니다.
   - 수집기는 종목 규칙의 코드를 **읽어** 종목별 수급 수집 범위에 더합니다(레이더 40 + 관심 최대 60).
   - 이것이 테이블 소유 규칙의 유일한 교차 읽기입니다. 범위를 넘는 규칙은 만들 때 거절합니다.
7. **문구는 순수 함수(`AlertText`)로 만듭니다.**
   - 근거·기준일·출처 성격·한계를 담고, 행동 지시(매수·매도 등)는 금지어 테스트로 막습니다.

## 이유

- **사건과 알림함을 나누면** 사건 판정을 수신자 수만큼 반복하지 않고, 중복 방지를 DB 제약 두 개가 맡습니다. 외부 채널도 이 구조에 채널만 더하면 됩니다.
- **멱등 평가는** 정기 작업이 두 번 돌거나 재시작이 겹쳐도 결과가 같습니다. 별도 상태(이어 처리 지점)가 없어 틀릴 곳이 줄어듭니다.

## 대안과 버린 이유

- **판정 규칙에 완충(hysteresis) 추가:** 화면 판정·판정 성과까지 바뀌어 규칙 v2가 됩니다. 사용자는 알림만 확정을 기다리는 쪽을 골랐습니다.
- **수집기가 끝날 때 백엔드를 호출:** 수집기가 백엔드를 알게 되어 의존 방향이 뒤집힙니다.
- **메일 알림:** D2에서 화면 알림함만 고름. 붙일 때의 방식은 설계 §4-4에 있습니다(발송 상태 열, `AlertSender`, 재시도·조용한 시간·수신 거부).

## 결과

- V7: `alert_rules`·`alert_events`·`alert_deliveries`.
- 경로: `/api/alerts/rules`·`inbox`·`unread-count`·`inbox/read`.
- 화면:
  - 알림(알림함·규칙)
  - 사이드바 뱃지와 탭 제목 앞의 읽지 않은 수
- 등급(D5):
  - 무료는 국면 전환 1개, 유료는 20개, 운영자는 50개입니다.
  - 관심 종목은 사용자당 20개, 전체 60개입니다.
  - 상한 검사부터 저장(만들기·켜기)까지는 서비스 안의 잠금 하나로 한 줄로 세웁니다(QA-092). 백엔드가 한 프로세스라는 전제이고,
    여러 대로 늘리면 `AlertStore` 안에서 트랜잭션 + `pg_advisory_xact_lock`으로 옮겨야 합니다.
  - 등급은 **지금 등급**으로 봅니다(QA-091·115).
    - 무료 회원은 국면 전환 밖의 규칙을 만들거나 켤 수 없습니다(403).
    - 운영자가 무료로 저장하면 그 회원의 유료 종류 규칙을 끕니다(지우지 않음, 다시 올려도 저절로 켜지지 않음).
    - 정기 평가는 지금 유료인 회원(운영자 또는 PRO)의 유료 종류 규칙만 읽습니다(`AlertStore.enabledRules`, `CurrentUser.isPro`와
      같은 규칙). 그래서 등급을 내리기 전부터 켜져 있던 규칙이나 하향과 경합해 켜진 규칙도 배달되지 않습니다.
    - 수집기의 관심 종목 범위(`watched_stock_codes`)는 등급을 보지 않습니다(교차 읽기를 늘리지 않으려고). 그런 규칙의 종목은
      운영자가 FREE로 다시 저장할 때까지 수집 범위를 차지합니다.
