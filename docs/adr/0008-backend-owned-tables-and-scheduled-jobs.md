# 0008. 백엔드가 쓰는 테이블과 정기 작업

- 상태: 채택 (2026-10)
- 지키는 방법:
  - `ArchitectureRulesTest`: `jdbcOnlyInStore`, `backendDoesNotWriteCollectorTables`
  - `StoreReaderNonBlockingTest.quietReadsNeverTriggerCollection`
  - `RegimeLogStoreDbTest`(하루 한 건, 동시 기록)
  - `RegimeLogServiceTest`

## 배경

지금까지 백엔드는 DB를 읽기만 했습니다. 쓰기와 스키마는 모두 수집기 몫이었고(ARCHITECTURE §3-2), 백엔드에는 정기 작업도
없었습니다. 판정 성과 공개·다중 사용자·알림([명세](../specs/2026-10-09-feature-spec.md))은 이 전제를 넘습니다.

- 국면 판정 기록: 그날의 판정은 백엔드가 계산합니다(`analytics.Regime`). 화면과 같은 값을 남기려면 백엔드가 써야 합니다.
- 계정·세션·알림: 수집과 무관한, 사용자가 만드는 상태입니다.

## 결정

1. **테이블마다 쓰는 프로세스는 하나입니다.**
   - 수집기: `snapshots`·`timeseries`·`observations`·`collector_*`·`refresh_requests`·`schema_migrations`
   - 백엔드: `regime_log`부터, 이후 계정·알림 테이블
   - 반대쪽은 읽기만 합니다.
2. **스키마 파일은 지금처럼 `db/migrations/` 한 곳**에 번호를 매기고, 수집기가 기동할 때 적용합니다.
   - 백엔드에 Flyway를 따로 두면 번호 체계가 둘이 됩니다.
3. **백엔드는 자기 테이블이 아직 없으면 기동을 멈추지 않고, 그 기능만 "준비 중"으로 둡니다**(`store.SchemaCheck`).
   - 백엔드는 postgres에만 기동 의존을 둡니다. 그래서 수집기가 V3을 적용하기 전에 백엔드가 먼저 뜰 수 있습니다.
   - 이때 기동을 멈추면 수집기가 내려가 있을 때 화면 전체가 뜨지 않습니다.
4. **DB 접근은 백엔드가 쓰는 테이블도 `store`에서만 합니다**(ADR 0001 개정). 스프링 JDBC가 `store` 밖에 나타나면 빌드가 실패합니다.
5. **정기 작업은 수집을 일으키지 않습니다.**
   - `auto` 읽기 모드에서는 저장본이 오래됐으면 읽기만 해도 수집을 요청합니다.
   - 그래서 정기 작업은 `StoreReader.quietly(…)` 안에서 읽고, 오래된 값을 어떻게 다룰지는 작업이 정합니다.
     판정 기록은 "판정 불가(입력 오래됨)"로 남깁니다.
6. **정기 작업은 두 번 돌아도 결과가 한 번입니다.**
   - DB 유일 제약으로 막습니다(`regime_log` 기본키 + `ON CONFLICT DO NOTHING`).
   - 그래서 재시작이 겹쳐도 중복 기록이 생기지 않습니다.
   - `@EnableScheduling`은 `dashboard.scheduler.enabled`로 끌 수 있고, 통합 테스트는 끕니다.

## 이유

- **테이블별 쓰기 주체가 하나면** 동시 쓰기 경합과 "누가 이 값을 바꿨나"를 따질 일이 없습니다. 지키는 것도 소스 검사 한 줄입니다.
- **번호 체계가 하나면** 새 DB·테스트 DB·CI가 같은 순서로 같은 스키마를 갖습니다.
- **수집을 일으키지 않는 읽기가 따로 있어야** 하는 이유: 5분마다 도는 작업이 보통 경로로 읽으면, 아무도 화면을 보지 않을 때도
  수집기를 깨웁니다. PRINCIPLES "아무도 보지 않는 화면이 수집기를 깨우지 않게"와 같은 원칙입니다.

## 대안과 버린 이유

- **판정 기록도 수집기가 쓴다:** 판정 규칙은 백엔드 `analytics.Regime`에 있습니다.
  - 수집기가 쓰려면 같은 규칙을 Python으로 한 번 더 구현해야 합니다.
  - 그러면 화면과 기록이 갈라질 여지가 생깁니다.
- **백엔드에 Flyway:** 마이그레이션 번호 체계가 둘이 되고, 같은 DB에 두 도구가 각자 이력 테이블을 둡니다.
- **기동할 때 최소 스키마 버전 확인(설계 계획서 초안):** 두 가지 문제로 테이블 존재 확인으로 바꿨습니다.
  - 테스트 DB·CI는 psql로 파일을 적용만 하고 `schema_migrations`를 남기지 않아, 그대로면 테스트가 깨집니다.
  - 기동을 멈추면 수집기가 늦게 뜰 때 백엔드가 재시작을 반복합니다.
- **수집기가 끝날 때 백엔드를 불러 알림:** 수집기가 백엔드를 알게 되어 의존 방향이 뒤집힙니다. 백엔드가 저장본을 읽는 쪽에 둡니다.

## 결과

- 백엔드가 쓰는 첫 테이블은 `regime_log`(V3)입니다.
  - 하루 한 건, KST 18시 이후에 씁니다. 기록 시각은 `dashboard.scheduler.regime-record-hour-kst`(기본 18)로 바꿀 수
    있고, AWS 데모(ADR 0012)는 17시로 둡니다 — 평일 08:50–18:00 켜기·끄기 일정으로 돌 때 18시 뒤 실행이 오지 않아 기록이
    쌓이지 않았습니다(QA-093). 일정은 2026-10-18부터 꺼 두었지만, 다시 켜도 기록이 남도록 17시를 유지합니다.
    → 이 저장소의 AWS 개인용 서버([ADR 0019](0019-aws-personal-deployment.md))는 정해진 가동 창(평일 밤은 미국 개장 10분 전~07:00 KST)에만 켜져 있어 23시로 둡니다(첫 실행은 기동 15분 뒤 — 수집기의 기동 수집 뒤).
  - 추가만 하고 고치거나 지우는 경로가 없습니다.
- **수집기는 기동할 때만 스키마를 적용합니다.** 그래서 `make up`이 기동 직후 `make migrate`(수집기 안에서
  `store.init_schema()`)를 부릅니다. 이것이 없으면 백엔드만 바뀐 배포에서 새 테이블이 생기지 않았습니다(QA-016).
- 새 테이블을 더할 때 할 일:
  1. 이 폴더에 다음 번호 파일을 둡니다.
  2. `store`에 저장소 클래스를 둡니다.
  3. 기능 서비스가 `SchemaCheck`로 준비 여부를 봅니다.
