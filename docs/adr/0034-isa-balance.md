# 0034. ISA 계좌를 장부(거래 누적)에서 잔고(현재 상태가 정답)로 — 지시 '확인'이 잔고에 바로 반영

- 상태: 채택 (2026-11-09, 사용자 결정 — 수동 입력 계좌라 시간순 재계산·검사 구조에서 오류가 반복됨(QA-337 등)). 구현은 브랜치 `claude/isa-balance-2026-11`.
- 바꾸는 결정: [ADR 0029](0029-isa-manual-account.md) 결정 3(지시대로 자동 기록 + 다르면 장부에서 고침)·결정 1의 알림 시각(밤·아침)과 정본(장부 행 → 잔고 행), [ADR 0033](0033-real-isa-open-offset-and-stops.md)의 ISA 쪽 자동 기록(시각 맞추기·스탑 지시의 1분봉 사다리 자동 기록·종가 어림). 지시 계산([명세](../specs/2026-11-06-isa-manual-account.md) §2 규칙 계좌 목표 맞추기·시각 맞추기·dueOrders 게이트)·장중 스탑 지시 감지·즉시 알림·주문 없음·텔레그램 종목·수량만은 그대로.
- 지키는 방법: 백엔드 `ManualAccountBalanceTest`(잔고 계산)·`ManualAccountPlannerTest`(음수 현금이면 계산하지 않음)·`ManualAccountServiceDbTest`·`ManualAccountJobDbTest`·`ManualAccountNoticesTest`·`ManualAccountStopStoreDbTest`, `AccessPolicyTest`·`RouteInventoryTest`(경로), 수집기 `test_table_ownership`(새 표), 화면 `isaScreen`·`isa.test`·`isaBoundary`.

## 배경

미래에셋증권 ISA(중개형)는 API가 없어 입력이 모두 수동이다. 지금까지는 입출금·매수·매도·조정 행을 시간순으로 쌓아 현금·보유를 다시 계산했는데, 행 하나를 잘못 적거나 순서가 어긋나면 어느 시점에서 현금·보유가 음수가 되는지부터 따져야 해서 고치기·지우기가 자꾸 막혔다(QA-337). 실제 계좌의 진실은 증권사 앱의 잔고 화면 하나이고, 장부를 맞추는 일 자체가 비용이었다.

## 결정

1. **정답은 지금 잔고** — `manual_balance`(현금·수수료율)와 `manual_positions`(종목·수량·매입 금액) 행. 거래를 다시 쌓아 계산하지 않는다. 이 행이 있으면 시작한 것이다.
2. **시작** — 총평가금액(현금 + 주식)과 줄마다 종목·수량·매입 금액. 현금 = 총평가금액 − Σ(수량 × 가격), 가격은 화면이 보낸 실시간 가격 → 서버 직전 종가 → 매입 금액 어림(메모). 시작하면 옛 PLANNED 지시·스탑 지시는 SKIPPED(`restart`)로 닫고, 아직 열리지 않은 세션은 지워 새 잔고로 다시 만든다(같은 (세션, 종목) 유일 제약 때문에 그 세션 지시는 지움).
3. **지시 '확인'** — 입력 없이 누른 순간의 가격(화면 가격, 없으면 서버 직전 종가)으로 잔고에 바로 반영하고 `manual_trades`에 남긴다. 매수는 현금 −(금액 + 수수료)·매입 금액 +금액, 매도는 현금 +(금액 − 수수료 − 세금)·보유까지만 팔고·매입 금액은 판 비율만큼 줄이고·실현 손익을 적는다. 실제 체결가와 다르면 사용자가 잔고에서 가격을 고친다.
4. **비용** — 수수료율 기본 0.015%(화면에서 바꿈), 세금은 설정 `kr.tax.*`(코스피 거래세 + 농특세, 코스닥, ETF 0, 매도만, 원 미만 절사 — `analytics/KrxCosts`). 시장 구분을 모르는 종목은 코스피 세율로 어림하고 표시한다.
5. **막지 않고 경고** — 잔고 편집·확인은 현금이 음수가 되어도 저장하고 요약에 경고 배너를 띄운다(수동 입력이라 틀린 값은 고치면 된다는 사용자 결정). **현금이 음수인 동안에는 다음 매매 지시를 만들지 않고 사유(`cash-negative`)를 화면과 텔레그램에 남긴다**(2026-11-12 개정, QA-381 — 아래 개정 절). 장중 스탑 지시는 그대로 만든다.
6. **되돌리기** — `manual_trades` 행을 지우면서 잔고를 정확히 되돌리고 지시는 PLANNED로(그 세션 마감이 지났으면 SKIPPED).
7. **자동 기록 없음** — 정기 작업은 잔고를 쓰지 않는다. 세션 마감이 지난 PLANNED 지시·스탑 지시는 SKIPPED(`expired`)로 닫는다. '앞 지시가 적혀야 다음 지시' 게이트를 없앤다. 다음 지시는 지금 잔고로 계산한다.
8. **알림** — ① 개장 전 08:00 지시 한 통(밤 알림·'다시 계산' 머리 제거) ② 장 중반 ③ 마감 30분 전(장 시간 변경일은 그날 기준) — ②③은 그날 미확인 지시·스탑 지시를 종류별 시각 칸으로 각각 한 번, 없으면 보내지 않음. 장중 스탑 즉시 알림은 그대로.

## 개정 — 2026-11-09 (사용자 결정 "'확인' 창에 수량·체결 금액·평균 단가·수수료를 입력")

결정 3의 '입력 없이 누른 순간의 가격으로 반영'을 바꾼다. 잔고 표의 가격 고치기로는 현금·매도 금액·실현 손익을 맞출 수 없어(전량 매도면 고칠 줄도 없음) 실제 체결을 적는 길이 필요했다. '확인'은 수량·체결 금액(총액)·평균 단가·수수료 칸이 있는 창을 열고(실시간 가격으로 채움), 적은 값으로 바로 반영한다. 체결 금액은 `manual_trades.amount`(V32)에 그대로 두고 평균 단가는 금액 ÷ 수량이다. 평균 단가가 직전 종가 ±40% 밖이면 거절해 총액·단가를 바꿔 적는 실수를 막는다. 세금은 자동 계산이다. 매매 내역에 '고치기'(`POST /api/manual/isa/trades/{id}`)를 더해 이미 확인한 건을 실제 값으로 고칠 수 있다.

## 개정 — 2026-11-12 (QA-339: 매수 내역의 고치기·되돌리기가 그 뒤에 판 수량을 되살리지 않게)

매수 내역을 '옛 값을 통째로 되돌린 뒤 새 값으로 다시 반영'하면, 그 매수 뒤에 판 수량이 보유로 되살아났다(4주 매수 → 1주 매도 → 그 매수의 수수료만 고침 → 보유 4). 음수가 된 수량을 0으로 올린 것이 원인이다. 내역 전체를 다시 계산하는 구조는 결정 1이 버렸으므로, 고치는 행 하나의 차이만 옮긴다(`ManualAccountBalance.editBuy`).

- **매수 고치기**: 남는 수량 = 보유 − 옛 수량 + 새 수량. 음수면 400(뒤에 판 수량보다 적게 고칠 수 없음), 0이면 보유 줄을 없앤다. 매입 금액 = 지금 매입 금액 + 새 체결 금액 × r′ − 옛 체결 금액 × r(0 아래로 내리지 않음, 소수 둘째 자리). r = min(1, 보유 ÷ 옛 수량)은 옛 매수 가운데 아직 보유에 남아 있다고 보는 몫, r′ = min(1, 남는 수량 ÷ 새 수량)은 새 매수 가운데 남는 몫이다. 수량·금액을 바꾸지 않은 고치기는 보유 수량과 매입 금액을 바꾸지 않는다. 현금 식은 그대로다(옛 금액 + 수수료를 돌려받고 새 금액 + 수수료를 냄).
- **매수 되돌리기**: 보유 − 그 매수 수량이 음수면 400(매도 내역을 먼저 되돌림). 그 밖의 식은 결정 6 그대로다.
- 매도 고치기·되돌리기는 바꾸지 않는다.
- 검토한 대안: 같은 종목의 뒤 매매가 있으면 고치기 거절(고칠 길을 막음), 내역 전체 다시 계산(결정 1이 버린 구조), '되돌린 수량이 0 이상이면 지금 식 그대로'(보유가 그 매수 수량보다 많을 때 매입 금액이 부풀려지는 경우가 남음).
- 감수한 단점: 뒤 매도 행의 매입 금액 몫·실현 손익은 다시 세지 않는다. 보유 부족이 뒤 매도 때문인지 잔고 직접 고치기 때문인지 코드는 가리지 못해, 잔고를 직접 줄인 뒤 매수 내역을 고치거나 되돌려도 같은 식·같은 거절을 탄다. r·r′은 '판 것은 이 매수에서 나갔다'는 어림이다(매수가 여러 번이면 실제 몫과 다를 수 있음 — 평균 매입가로 세는 잔고 구조의 한계). 그 어림이 가장 크게 어긋나는 경계: 다른 매수와 섞인 보유에서 일부를 판 뒤 그 매수의 **수량을 줄여** 고치면 매입 금액이 0까지 깎일 수 있다(예: 10주·매입 100 → 4주 400 매수 → 9주 매도 → 5주·178.57 → 그 매수를 2주·200으로 고침 → 3주·매입 금액 0, 비례로 따지면 약 75). 그 뒤 실현 손익이 그만큼 커 보이므로, 그런 고치기 뒤에는 잔고의 매입 금액을 직접 확인한다(독립 검토에서 확인 — 식은 그대로 둠).

## 개정 — 2026-11-12 (QA-381: 현금이 음수인 동안 매매 지시를 만들지 않음 — 사용자 결정 D-4 (가))

결정 5는 음수 현금을 저장만 하고 경고했는데, 지시 계산은 평가액 = 현금 + 보유로 목표 수량을 세므로 음수만큼 목표가 줄어 **책에 있는 종목까지 매도 지시**가 나왔다. 평가액이 0 이하이면 목표 수량이 모두 0이라 **전 종목 전량 매도 지시**가 08:00 텔레그램으로 나갔다(시작 창이나 '총 잔고 다시 맞추기'에 자릿수를 잘못 넣으면 닿음). 화면 경고는 '매수가 줄어듭니다'라고만 했다. 주문은 사람이 내지만 실제 돈의 매도 지시다.

- **바꾼 것**: 정기 작업이 지시를 계산하기 직전(계좌 잠금 안)에 잔고 현금이 음수이면 세션 행·지시 행을 쓰지 않고 사유 `cash-negative`로 기다린다(`ManualAccountJob.plan`, 계산 함수 `ManualAccountPlanner.plan`도 음수 현금이면 빈 결과). 기준가를 모를 때 지시를 만들지 않는 것(`price-missing`)과 같은 결이다. 잔고를 고치면 다음 주기(10분)에 지시를 만들고, 개장까지 음수이면 그 세션은 `UNAVAILABLE`(사유 `cash-negative`)이다. 잔고 쓰기를 막지 않는 것(결정 5의 앞 문장)은 그대로다.
- **이미 만든 지시는 그대로**: 지시를 만든 뒤(그 세션 08:00 뒤 — 결정 3의 확인 등으로) 현금이 음수가 되어도 그 세션의 PLANNED 지시는 지우지 않는다(양수 현금으로 계산한 지시이고 이미 주문을 냈을 수 있음). 08:00 전에 잔고를 고쳐 음수가 되면 지시를 지우고 다시 만들 때 이 규칙에 걸린다.
- **장중 스탑 지시는 막지 않는다**: 스탑 지시는 보유를 파는 손절이라 현금과 무관하다(`stopScan` — 수량은 잔고 보유 + 지시 시각이 지난 미확인 지시 증감). 수정 전에는 음수 현금으로 만든 매도 지시가 스탑 수량에서 빠져 스탑 수량까지 줄었다.
- **알림**: 사유는 보기의 `waiting`(지시 카드)·안내 목록과, 그 세션 08:00부터 개장 전까지 텔레그램 '매매 지시 없음' 한 통으로 알린다(고정 문구와 날짜뿐 — 금액·평가액·종목 없음, ADR 0029 결정 4). 알리지 않으면 '오늘은 매매할 것이 없음'(NONE — 알림 없음)과 구분되지 않는다. 음수가 며칠 이어지면 거래일마다 한 통이다. 보낸 세션은 메모리에만 적어(표에 둘 칸이 없음 — 스키마를 바꾸지 않음) 08:00~개장 사이에 백엔드를 다시 띄우면 한 번 더 갈 수 있다.
- **검토한 대안**: (나) 평가액 계산에서 음수 현금을 0으로 봄 — 전량 매도는 막지만 틀린 잔고 위에서 매수·매도 지시를 계속 낸다(현금 확인이 음수 현금 + 매도 대금으로 매수만 줄임). (다) 계산은 두고 화면 경고 글만 고침 — 08:00 텔레그램의 매도 지시가 그대로 나간다. (라) 그대로.
- **감수한 단점**: 현금이 조금만 음수여도(확인한 체결가가 높아 몇 원 모자란 경우 등) 잔고를 고칠 때까지 지시가 멈춰 규칙 계좌를 따라가지 못한다 — 문턱(예: 평가액의 몇 %)을 두지 않은 것은 '얼마까지가 입력 실수가 아닌가'를 코드가 정할 근거가 없어서다. 사유는 정기 작업의 메모리에 있어 개장 직전에 백엔드를 다시 띄우면 못 만듦 기록의 사유가 `not-planned`로 남을 수 있다(다른 대기 사유와 같은 기존 한계).

## 옛 표를 남긴 이유

`manual_ledger`와 옛 칸(`confirmed_at` 등)은 DROP하지 않고 코드에서만 쓰지 않는다. 더하기만 하는 마이그레이션이면 코드를 되돌려도 깨지지 않고(V25·V28·V30과 같은 원칙), 기록이 지워지지 않는다. 기존 장부 값은 옮기지 않는다 — 어차피 행의 정확성이 문제의 원인이었고, 사용자가 배포 뒤 시작 창에 오늘 잔고를 넣어 새로 시작한다. 다음 시가 지시 삭제가 옛 표의 외래키에 걸리지 않게 확인하는 데는 계속 읽는다.

## 결과

- 고치기가 한 행의 값 고침으로 끝난다(순서 의존 없음). 잘못된 입력이 다른 행을 막지 않는다.
- 과거 잔고의 역사(시점별 현금 곡선)는 남지 않는다 — `manual_trades`는 확인 내역일 뿐 잔고를 다시 만들지 않는다.
- 실제 체결과의 차이는 사용자가 잔고에서 고칠 때까지 남는다(자동 기록 때도 비용 0 어림으로 같은 한계가 있었다).
