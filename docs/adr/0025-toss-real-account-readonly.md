## 배경

운영자는 대시보드에서 토스증권 실제 계좌를 함께 보고 싶어 했습니다 — 원화 자산(국내 주식·원화 매수 가능 금액)은 모의매매(한국) 화면에서, 달러 자산(미국 주식·달러
매수 가능 금액)은 모의매매(미국) 화면에서. 토스증권 Open API 공식 스펙 1.2.28(2026-11-05 다시 받음)에서 확인한 사실은 다음과 같습니다.

- 계좌 조회 API가 있습니다: `GET /api/v1/accounts`(ACCOUNT 초당 1회)·`/holdings`(ASSET 5회)·`/buying-power?currency=KRW|USD`(ORDER_INFO 6회, 09:00~09:10 KST 3회)·
  `/orders?status=OPEN|CLOSED`(ORDER_HISTORY 5회). 계좌 문맥 호출에는 헤더 `X-Tossinvest-Account: {accountSeq}`가 필요하고, `Account`에는 전체 계좌번호 `accountNo`가 들어 있습니다.
  예수금 엔드포인트는 없고 현금 쪽 수치는 `cashBuyingPower` 하나입니다. 보유 요약 금액은 통화별(`Price.krw`·`Price.usd`)로 오지만 요약 `rate`는 원화 환산 합산입니다.
- **토큰은 키(client) 하나에 1개**입니다 — 재발급하면 이전 토큰이 바로 무효가 됩니다. 운영 수집기는 같은 키로 레이더와 한국 책 1분봉(`kr_paper_timed`·`paper_watch_kr` —
  한국 Claude 계좌2의 체결·장중 확인)을 받습니다. 로컬 `.env`에도 같은 키가 있어 서버·로컬이 서로의 토큰을 무효화한 적이 있습니다([ADR 0019](0019-aws-personal-deployment.md)·[0023](0023-vultr-deployment.md)).
- 토스 개발자 콘솔의 **허용 IP**는 운영 서버(Vultr 공인 IP)입니다.
- **OAuth `scopes`가 비어 있습니다** — 시세용으로 받은 같은 키로 주문 POST(`/api/v1/orders`)가 나갈 수 있다고 봐야 합니다(실제로 보내 보지는 않음). 같은 경로에
  GET(목록)과 POST(주문)가 함께 있습니다. **샌드박스(모의 환경)는 없습니다.** 지금까지 수집기의 공유 `toss` requests 세션은 어떤 메서드든 보낼 수 있었습니다.
- 모의매매 명세들의 "실제 주문은 범위 아님 — 어떤 경로로도 주문이 밖으로 나가지 않는다"([모의매매 명세](../specs/2026-10-24-paper-trading-spec.md) §0과 화면 한계 1번,
  [v2 계획서](../specs/2026-10-26-v2-program-plan.md) '하지 않는다', [한국 명세](../specs/2026-10-26-v2-kr-paper-spec.md) 머리말, [ADR 0018](0018-paper-trading-guardrails.md) 배경)는 모의 책의
  약속이고 이 결정 뒤에도 그대로 참이어야 합니다. 프레임 v1은 사용자 투자 OS의 '현재 활성 컨텍스트(실제 계좌 상태)'를 일부러 뺐습니다
  ([설계](../specs/2026-10-24-paper-trading-design-plan.md)) — 실제 계좌 자료를 Claude 입력에 넣지 않는 선례입니다.

## 결정

1. **별개 기능**: 백엔드 새 패키지 `feature.brokerage`(이름은 2단계 자리를 위해 일반화), 수집기 `services/toss_account.py`, 화면 `components/screens/brokerage/*`.
   모의 매매 기능이 아니며 모의 장부·순자산·통계를 바꾸지 않습니다. 위 모의매매 명세들의 '실제 주문 없음'은 모의 책에 그대로 적용됩니다 — 이 기능도 주문을 내지 않습니다.
2. **읽기 전용**: 보유·매수 가능 금액(`cashBuyingPower`)·주문 내역(진행 중 전부, 끝난 주문은 최근 30일·최대 3쪽)만 읽습니다. 주문·정정·취소·조건주문·웹소켓
   `personal:order`·거래내역(`/api/v1/transactions`)은 범위 밖입니다. 화면에는 주문·취소 단추가 없고 brokerage 화면 모듈은 쓰기 API 함수를 가져오지 않습니다.
3. **저장하지 않습니다**: DB 표·스냅숏·수집 태스크·마이그레이션이 없습니다. 수집기 메모리 캐시(성공 60초, 실패하면 직전 성공값 전체를 `isStale`로 최대 30분, 실패 직후
   30초는 다시 부르지 않음, 기다리지 않는 single-flight)뿐이라 S3 백업·배포 전 덤프·QA 복원·태스크 기록·`/status`로 퍼지지 않습니다([ADR 0024](0024-live-prices-sse.md)의 '저장하지 않음' 선례).
4. **운영 서버에서만 켭니다**: 수집기 환경변수 `TOSS_ACCOUNT_ENABLED`가 정확히 `true`이고 서비스 토큰이 있을 때만. 기반 `docker-compose.yml`은 보간 없는 `"false"`라
   로컬 `.env`·셸 값이 끼어들 수 없고(QA 덧붙임은 그 위에 얹혀 그대로 `"false"`), `compose.vultr.yml`만 서버 `.env` 값을 넘깁니다(`TAILNET_OWNER_LOGIN` 선례).
   백엔드는 이 이름을 받지 않고 수집기 응답의 `enabled`로 압니다. 공개 데모 읽기 모드(`store_only`)는 수집기를 부르지 않고 `DISABLED`.
5. **쓰기 차단은 공유 `toss` 세션 자체에 겁니다**: 가드 어댑터를 `https://`·`http://` 둘 다에 붙여 scheme `https`·호스트 `openapi.tossinvest.com`이고 메서드가 GET이거나
   `POST /oauth2/token`일 때만 보내고, 나머지는 네트워크 전에 `TossReadOnlyViolation`으로 막습니다. 계좌 모듈도 이 세션을 씁니다 — 앞으로 누가 `toss._http().post(...)`를
   써도 나가지 않습니다. 키에 scope가 없어 막을 곳이 이 세션뿐이기 때문입니다.
6. **토큰을 지킵니다**: 계좌 경로는 401 가운데 `expired-token`·`token-revoked`·`invalid-token`일 때만 재발급하고, 그 재발급은 10분에 1회로 묶습니다(운영 1분봉 보호).
   그 밖의 401은 `auth-failed`로 끝내고 토큰을 버리지 않습니다. 429는 기다리지 않고 바로 `rate-limited`. 호출 하나 (3, 4)초, 새 호출은 갱신 시작 뒤 12초 안에서만(토큰 발급 뒤·401 재시도 직전에도 남은 시간을 다시 봄). 진행 중인 토큰 발급(최대 16초)은
   끊지 않으므로 최악은 약 28초이고, 백엔드는 35초·화면은 40초를 기다립니다. 다른 곳이 이미 새 토큰을 받아 둔 401은 발급 없이 그 토큰으로 다시 보내고 10분 한도에 세지 않습니다.
7. **최소 자료만 옮깁니다**: BROKERAGE 계좌가 정확히 1개일 때만 진행합니다(0개·여러 개는 개수만 알리고 `no-account`). 이름표는 고정 "토스증권 종합매매", 계좌번호·
   `accountSeq`는 어디에도 싣지 않고, 주문 번호는 진행 중·끝난 주문의 중복 제거에만 씁니다. 종목명은 보유 이름표에서만 채웁니다(`/stocks`를 부르지 않음). 수집기와
   백엔드가 허용한 칸만 하나씩 옮깁니다(통째 복사 금지). 토스 오류 `message`·본문은 싣지 않고 `error.code`는 `^[a-z0-9-]{1,40}$`일 때만, 예상 못 한 예외는 로그에 클래스 이름만.
8. **원화는 `/paper/kr`, 달러는 `/paper/us`**: 두 시장 화면의 탭 줄 끝에 '실제 계좌'(`/paper/kr/real`·`/paper/us/real`). 보유는 `marketCountry`·`currency`가 둘 다 그
   쪽일 때만(KR·KRW / US·USD), 주문은 `currency`로 나누고, 어느 쪽에도 맞지 않는 것은 개수만 알립니다(`unclassifiedCount`). 탭을 열 때만 읽습니다.
9. **분리**: 실제 계좌 자료는 모의 장부·순자산·Claude 패킷·프롬프트·주간 복기·텔레그램 알림·AI 리포트(전체 원본 텍스트)에 들어가지 않습니다 — 다른 백엔드 패키지는
   `feature.brokerage`를 참조하지 못하고, brokerage는 `store`를 쓰지 못하며(저장할 길이 없음), 모의·홈 화면 모듈은 brokerage 모듈을 가져오지 못합니다(시험이 막음).
   화면은 모의 계좌로 읽히지 않게 히어로·계좌 행·'출발 이후' 칩을 쓰지 않고, 맨 위에 "모의 장부와 별개 · 읽기 전용" 배너를 둡니다.
10. **정직한 숫자**: 모르는 값은 null → '—'(0으로 채우지 않음). 손익률은 같은 통화끼리만 대시보드가 계산하고(그렇게 적음) 일간 수익률과 원화 환산 합산 비율은 보이지
    않습니다. '예수금'·'총자산'이라 부르지 않고 매수 가능 금액에는 "통화별 현금 기반 — 두 화면의 금액을 더하지 마세요"를 적습니다. 이전 값은 '이전 값'과 받은 시각,
    끝난 주문을 3쪽에서 끊었으면 "일부만 받았습니다", 보유가 없으면 '보유 종목 없음'.
11. **검증 출력 규칙**: 에이전트(사람이 아닌 자동 작업)는 운영 응답의 금액·수량·개수·종목을 출력하거나 문서·커밋·QA 기록에 적지 않습니다. 서버 확인은 명세 §8의 한 줄
    (`ok`·`enabled`·`reason`·`isStale`과 각 쪽의 키 이름만 찍음)만 쓰고, 화면 숫자 확인은 운영자가 직접 합니다. 실제 응답은 시험 자료로도 커밋하지 않습니다(공개 저장소).

## 2단계 관문 — 주문

이 ADR은 주문을 허락하지 않습니다. 실제 계좌에서 주문을 내는 기능은 아래를 모두 갖춘 뒤에만 만듭니다.

- **새 ADR과 사용자의 명시적 승인**(이 ADR의 '권장안대로'는 1단계 승인입니다). 모의 책의 '실제 주문 없음'과 어떻게 나란히 서는지를 그 ADR이 적습니다.
- 이 플래그와 **다른 별도 플래그**(조회를 켰다고 주문이 켜지지 않음), 기본 꺼짐·운영 서버에서만.
- **화면에서 사람이 확인한 주문만**: 주문마다 `ConfirmDialog`의 `requireText`(정확히 쳐야 확인)로 사람이 확인하고, 서버가 같은 글자를 다시 검사합니다. 모델·정기 작업이
  스스로 주문하는 길은 없습니다.
- **`clientOrderId` 멱등**: 재시도가 두 번째 주문이 되지 않게 요청마다 고유 키를 두고 같은 키로만 다시 보냅니다.
- **`confirmHighValueOrder`를 자동으로 켜지 않습니다**: 1억 원 이상 주문의 확인 칸은 사람이 그 주문에서 따로 확인했을 때만 보냅니다.
- **쓰기를 여는 커밋이 곧 결정입니다**: 공유 `toss` 세션 가드를 넓히거나 쓰기 금지 시험(`test_toss_account.py`의 가드·AST 검사, `brokerageBoundary.test.ts`의 쓰기 API 금지,
  `AccessPolicyTest.brokerageRoutesAreOwnerOnlyAndGetOnly`)을 고치거나 지우는 커밋은 그 자체로 이 관문을 넘는 결정입니다 — 새 ADR과 승인 없이 그런 커밋을 만들지 않습니다.

## 이유

- 사용자가 고른 권장안이 '읽기 전용 먼저'였고, 돈이 움직이는 경로가 하나도 없으면 실수의 최악이 '잘못 보임'에서 끝납니다.
- 키에 scope가 없고 샌드박스도 없어 키 수준에서 읽기만 허락받을 방법이 없습니다. 그래서 차단을 계좌 모듈이 아니라 토스로 나가는 유일한 세션에 둬, 다른 코드가
  나중에 쓰기를 시도해도 같은 자리에서 막히게 했습니다.
- 저장하면 `pg_dump` 전체 덤프를 따라 S3(60일)·서버 덤프·QA 복원으로 실제 계좌 자료가 복제됩니다. 화면이 열려 있을 때만 필요한 값이라 저장할 이유가 없습니다.
- 토큰이 키 하나에 1개라 조회하는 곳이 늘수록 운영 1분봉의 401·재발급이 늘어납니다. 허용 IP도 서버라 로컬에서 켤 이유가 없습니다.
- 자료를 나누는 기준(시장 화면별 통화)이 모의 책의 두 책과 같아 운영자가 같은 자리에서 비교해 봅니다. 그래도 장부·Claude 입력과 섞이면 진행 중인 실험이 바뀌므로
  패키지 의존으로 길 자체를 없앴습니다.

## 대안과 버린 이유

- **스냅숏·DB에 저장**: 화면이 빨라지고 이력이 생기지만, 위 백업 확산과 표 소유·마이그레이션이 따릅니다. 이력이 필요해지면 그때 새 결정으로 정합니다.
- **백엔드가 토스를 직접 부름**: 토큰이 두 프로세스로 나뉘어 서로 무효화하고, QA 스택의 차단 프록시(수집기만 거침)를 우회합니다. 토스 호출은 수집기 한 곳(`toss.py`)입니다.
- **로컬에서도 켬**: 토큰 경합으로 서버의 한국 책 1분봉이 401·재발급을 더 자주 겪고, 허용 IP 밖이면 어차피 403입니다.
- **실제 계좌 전용 키를 따로 발급**: 토큰 경합은 줄지만 scope가 없어 주문 권한은 그대로이고, 같은 계정에서 키를 하나 더 받을 수 있는지도 확인하지 못했습니다.
- **모의매매 개요에 카드로 넣음**: 모의 순자산 히어로·합계 옆에 실제 금액이 놓여 모의 계좌로 읽히기 쉽고, 개요를 열 때마다 토스를 부릅니다. 탭으로 두면 열 때만 부르고
  화면 전체가 '모의 장부와 별개'라는 배너 아래에 있습니다.

## 결과와 남은 위험

- KRW·USD 매수 가능 금액이 통합증거금·자동 환전으로 서로 겹치는지는 스펙으로 확인하지 못했습니다 — 화면은 더하지 말라고만 적습니다.
- BROKERAGE 계좌가 둘 이상이면 고르지 않고 `NO_ACCOUNT`로 멈춥니다(계좌 선택은 필요해질 때).
- 모의 장부 개요를 못 읽으면 `PaperScreen`이 탭 줄을 그리지 않아 실제 계좌 탭에도 닿지 못합니다. 390px 화면에서는 마지막 탭(실제 계좌)이 가로 스크롤 밖에서 시작합니다.
- 수집기를 다시 띄우면 메모리 캐시가 비어 처음 한 번은 토스를 새로 부릅니다.
- 운영자 기기의 Tailscale 신원이면 로그인 없이 운영자로 열리므로([ADR 0023](0023-vultr-deployment.md) 결정 10), 기기를 잃으면 Tailscale 관리 화면에서 그 기기를 지우는 절차에 기댑니다.
- KIS·LS 키도 주문 권한이 있을 수 있는데(확인하지 않음) 그 세션에는 이번 가드가 없습니다. 같은 모양의 가드를 거는 것은 제안으로만 남깁니다(이번 범위 밖).
