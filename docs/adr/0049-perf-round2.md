  미국 시세(yfinance)도 예산 안에서 보내고 끝남, 출처가 바로 답하면 예산을 건 결과 = 걸지 않은 결과), 백엔드 읽기 한도 `CollectorClientSearchLogTest.liveFetchReadTimeoutIsBudgetPlusMargin`.

## 배경

2026-11-24 재측정(배포본 `main@119cfa4f`)에서 운영 `/api/security/notices`가 매번 1.65~1.75초, `/api/sec13f/institutions`가 매번 110~120 ms였다.

- 보안 공지 목록은 요청마다 공지·표 행·버전 목록(구성 1,712·변경 기록 CVE 11,340)을 모두 읽고 공지 135건 전부를 다시 판정한 뒤 20건을 잘라 줬다. 운영 규모 합성 씨앗의 QA에서
  나눠 재니 DB 읽기 약 15~70 ms·조립 3~5 ms·판정 약 550~600 ms였고, 판정 시간의 약 80%가 별칭 이름 찾기 정규식이었다(JFR 표본).
- 기관 목록은 즐겨찾기 24개 저장본(수 MB씩)의 첫 분기 기준일 한 칸을 꺼내려고 DB가 JSONB 전체를 풀었다(같은 질의에서 `name`·`collected_at`만이면 0.5 ms, 기준일까지 35 ms(QA 14 MB)).

## 결정

1. **판정 기억(QA-991)**: `SecurityService`가 공지 전부의 판정 한 벌(버전 목록 머리·판정 입력·판정 목록)을 입력 판과 함께 기억한다. 부를 때마다 판을 확인하고(집계 한 줄),
   같고 10분(`JUDGEMENT_MAX_AGE`) 안이면 기억한 것을, 아니면 새로 계산한다. 목록의 거르기·세기·자르기(`verdict`·`reason`·`q`·`page`·`size`)와 공지 상세는 그 한 벌 위에서
   지금처럼 한다 — 응답은 한 글자도 바뀌지 않는다(판정은 시각에 기대지 않음). 알림 작업(`SecurityAlertJob`, 15분)도 같은 한 벌을 쓰되 매번 판을 확인하므로 옛 판정으로 알리지 않는다.
2. **입력 판**(`SecurityStore.inputVersion`): (공지 수, 공지 `updated_at` 최댓값, 표 행 수, 버전 목록 `received_at`, 추적기 결과 수, 추적기 `checked_at` 최댓값) — 행을 내려받지 않는
   집계 하나. 수집기가 그 표들을 쓰는 방식(`collector/app/store.py`)에 기댄다: 공지는 넣거나 고칠 때마다 `updated_at = now()`(상세의 표 행은 같은 트랜잭션에서 통째로 바꿈),
   버전 목록 네 표는 한 트랜잭션으로 통째로 바꾸며 `received_at = now()`, 추적기 결과는 행마다 그 실행의 `checked_at`. 별칭 표는 코드라 프로세스 안에서 바뀌지 않는다.
   판을 놓치는 경우(수집기의 쓰기 방식이 바뀜 등)에 대비한 것이 10분 상한이다.
3. **기억은 서비스 안에**: 응답 캐시 `read.ComputedCache`는 저장본(`snapshots`)의 최신 수집 시각으로만 값을 버려 보안 표의 변경을 모르고(그대로 쓰면 옛 판정이 최대 60초 남음),
   서비스가 그것을 부르는 것은 ADR 0001에 어긋난다. 판 확인이 DB 읽기라 저장소(`store`)에 두고, 기억과 '같으면 다시 쓰기'는 그 판정을 만드는 서비스가 한다. 같은 때 여럿이 부르면
   계산은 한 번만 한다(잠금 안에서 다시 확인).
4. **판정 자체는 그대로**: 판이 바뀐 직후 첫 계산은 예전과 같은 비용이다(QA 약 0.55초, 운영 약 1.7초 추정). 지시문의 기준('첫 계산이 1초를 넘으면 원인을 줄임')은 QA 값으로
   재고 넘지 않아, 판정 규칙·정규식은 건드리지 않았다 — 운영에서 판이 바뀌는 때는 보안 공지 태스크(KST 6시간 구간마다 한 번)·버전 목록 받기·추적기 실행 뒤 첫 조회뿐이다.
5. **저장본 머리(QA-992)**: `StoreRepository.readSnapshotHeads`가 먼저 `name`·`collected_at`만 읽고, 기억과 수집 시각이 다른 이름만 기준일(`payload->'quarters'->0->>'reportDate'`)을
   다시 읽어 이름마다 기억한다. 수집기는 본문을 새로 쓸 때마다 수집 시각도 새로 적으므로(`put_snapshot` — 본문만 고치는 `update_snapshot_payload`는 뉴스·상태 저장본만 씀)
   수집 시각이 같으면 기준일도 같다. 보고 기준일을 따로 저장하는 스키마 변경은 하지 않는다(D-6). 같은 표에서 `payload->'quarters'`를 다루는 다른 두 질의
   (`readSnapshotFirstQuarters`·`readQuarterHoldings`)는 본문 자체를 쓰는 읽기라 같은 문제가 아니다(진행 기록에 잰 값).

6. **화면 조회의 외부 예산(QA-993)**: 수집기 `/live/quote`·`/live/news`·`/live/daum-intraday`는 요청 하나에 `app.http.LIVE_BUDGET_SECONDS`(10초)를 건다
   (`run_with_budget`). 새 장치가 아니라 태스크의 시간 상한에 쓰던 가드(`TaskGuard` — 공용 세션은 요청 timeout을 남은 예산에 맞춰 줄이고 예산 안에 끝나지 않을 재시도는
   보내지 않음, yfinance는 `app.yahoo`의 예산 세션이 같은 가드를 봄 — QA-255)를 그대로 쓰고, 끝난 뒤 남겨 둘 시간만 가드마다 정하게 했다(`http.reserve_seconds` —
   태스크 10초 그대로, 화면 조회 0.5초). 태스크 값을 그대로 두면 10초 예산에서 yfinance는 아예 보내지 않는다(고치는 중 QA에서 봄 — 시험으로 막음).
   출처가 여럿이면 앞에서부터 나눠 쓰고, 먼저 받은 것은 지금처럼 돌려주며, 예산이 끝나면 지금의 '받지 못함' 꼴(`_empty_quote`·출처별 `errors`·`available:false`) 그대로다.
   재시도를 줄이는 쪽이라 출처에 보내는 요청은 늘지 않고, 호스트 간격·래치는 그대로다. 백엔드 → 수집기 읽기 한도는 이 세 경로만 15초(`CollectorClient.LIVE_FETCH_READ_TIMEOUT`
   — 예산 + 여유). 정기 수집 태스크의 상한·재시도는 건드리지 않는다.
7. **검색 세 경로는 그대로**: `/api/search/feed`·`resolve`·`entity`의 15~18초는 ADR 0041의 '대상 풀기·resolve의 Wikidata 단계 15초(넘으면 로컬 결과만)'라는 설계 값이라 바꾸지 않는다(기록만).

## 결과

- QA(운영 규모 합성 씨앗): 보안 공지 목록 둘째 호출부터·기관 목록 둘째 호출부터의 값과 운영 배포 뒤 값은 진행 기록에 적는다.
- 백엔드 메모리: 판정 한 벌(공지 135건의 판정·버전 목록 입력 — 변경 기록 CVE 1만여 줄의 묶음)과 저장본 머리(이름마다 한 줄)를 들고 있다. 백엔드가 다시 뜨면 비고 처음 한 번 다시 계산한다.
- 남긴 것: 판이 바뀐 직후 첫 판정 비용(운영 약 1.7초 추정)은 그대로. 다음에 줄인다면 별칭 이름 찾기 정규식(공지마다 본문·제목에 별칭 수만큼 도는 것)부터.
- 화면 조회는 출처가 느리지만 결국 답하는 경우(10초 넘게 걸리는 정상 응답)도 '받지 못함'이 된다 — 실패 응답은 1분만 기억하므로 다음 조회가 다시 묻는다.
