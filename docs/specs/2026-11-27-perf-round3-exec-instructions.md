# 실행 세션 지시문 — 성능 개선 3차(차트 시계열 조회 · 계산 결과 기억 · 검색 피드 · 모바일 레이아웃 밀림) (2026-11-27)

## 1. 역할과 목표

너는 이 프로젝트를 넘겨받은 시니어 풀스택 엔지니어야. 이 작업은 두 세션으로 나뉘어 있어. 계획 세션(2026-11-27)이 배포본 `main@c167f149`를 QA 스택과
운영 서버(읽기만)에서 다시 재고 이 지시문을 썼고, 이 세션은 그 계획을 실행하는 세션이야. 너는 계획 세션의 대화를 볼 수 없어. 이 지시문, 프롬프트,
저장소의 문서와 코드가 네가 아는 전부야.

배경: 1차(2026-11-22, ADR 0047)와 2차(2026-11-24, ADR 0049 — [진행 기록](2026-11-24-perf-round2-progress.md))의 개선은 이번 재측정에서 그대로 유지되고 있었어
(회귀 없음). 대신 아래 네 가지를 새로 찾았어. 이 네 가지만 고쳐.

- 작업 A — 차트 시계열 조회(`/api/macro/ticker`): 외부가 응답하지 않으면 **60초** 붙잡혀(2차의 10초 예산에서 빠진 경로). 평소에도 매번 100~180 ms, 가끔 0.8~1.3초.
- 작업 B — 계산 결과 기억: 무거운 계산이 60초마다 다시 돌아, 혼자 쓰는 운영에서는 화면을 열 때 거의 매번 100~280 ms를 다시 써. 즐겨찾기가 늘면 같이 느려져.
- 작업 C — 검색 피드: 한 번에 2,756건·1.6 MB(gzip 428 KB)를 주고 매번 약 300 ms. 화면이 그리는 양은 아직 재지 못했어.
- 작업 D — 모바일 레이아웃 밀림: 띠와 무관하게 남은 일곱 화면.

원자료는 [docs/qa/evidence/2026-11-27-perf/baseline.txt](../qa/evidence/2026-11-27-perf/baseline.txt)에 있어.

## 2. 계획 세션이 확인한 사실 (2026-11-27, `main@c167f149` — 같은 날 19:46 KST 배포본, `main` 끝 `67924543`은 문서만 다름)

코드 위치는 파일과 심볼로 가리켜. 실행하기 전에 지금 코드에서 다시 확인해. '확인함'과 '추정'을 구분해 적었어.

### 측정 조건
- QA 스택(이 PC WSL2, 로그인 없는 모드, 외부 차단)은 배포본과 같은 코드였고, 2차의 합성 씨앗(`scripts/qa/perf-seed.py` — 보안 공지 140건·13F 즐겨찾기 19곳)이 들어 있어.
  **Vultr 값이 아니야.** 정보 검색의 모은 글은 QA에 없어(외부 차단).
- 운영 서버는 읽기만 했어: 조회 API 97개를 한 번에 하나씩(응답은 버림, 실제 계좌 경로 제외), DB는 통계 표와 크기만. 운영 값에는 왕복 약 10 ms가 들어 있어.

### 작업 A — 차트 시계열 조회 (확인함)
- QA 프록시 `hang`에서, **수집기·백엔드를 다시 띄운 뒤** 외부성 경로만 부른 값: `/api/macro/ticker?symbol=^TNX&period=1y` **59.98초**. 같은 판에서 `detail/news` 4.8~10.0초,
  `detail/quote` 4.8~9.5초, `krx/intraday` 4.8초, 검색 셋 15.0~17.7초.
- 2026-11-24의 hang 측정이 이것을 못 본 까닭: 앞선 호출로 Yahoo 호스트가 이미 잠겨(`http.active_rejection`) 바로 실패로 끝났어. **hang은 기억과 잠금을 비운 상태에서 재야 해.**
- 운영: `^TNX` 2번에 1,267·843 ms, 이어 165·100·103 ms. `NVDA` 175·100, 이어 182·104·103 ms. `005930.KS` 1,040·105 ms. 저장본으로 답하는 `^VIX`는 16~19 ms.
- 경로: 화면 `endpoints.macro.ticker`(`app/(dashboard)/macro/SingleChartSection.tsx`, `components/screens/detail/DetailParts.tsx` 두 곳) → 백엔드 `MacroService.tickerSeries`
  (`^VIX`·`^MOVE`만 저장본, 나머지는 `collector.liveTicker`) → 수집기 `main.live_ticker` → `services/market.collect_ticker` → `_download`(yfinance).
- 수집기의 화면 조회 예산 `http.run_with_budget(http.LIVE_BUDGET_SECONDS …)`(10초, QA-993)는 `/live/quote`·`/live/news`·`/live/daum-intraday` 셋에만 걸려 있어. `/live/ticker`에는 없어.
  `_download`는 Yahoo 공용 잠금과 `yahoo.unavailable_reason()`(무응답 잠금·예산 부족)을 보고, 2차 때 yfinance 예산 세션이 '남길 시간'을 잘못 읽어 Yahoo를 아예 부르지 않던
  회귀가 있었어(진행 기록 단계 2 — `reserve_seconds`).
- 백엔드 `CollectorClient.liveTicker`는 일반 클라이언트(읽기 상한 90초)를 써. `liveQuote`·`liveNews`·`daumIntraday`만 `liveFetchClient`(`LIVE_FETCH_READ_TIMEOUT` 15초)야.
- 수집기도 백엔드도 이 결과를 기억하지 않아 — 화면을 열 때마다 Yahoo를 새로 불러.
- 그 밖의 `/live/*` 경로(`/live/radar`·`/live/prices`·`/live/symbols`·검색 여섯)는 hang에서 따로 재지 않았어(검색 셋 15~17.7초만 봄 — ADR 0041의 설계 값인지는 2차가 확인).

### 작업 B — 계산 결과 기억 (확인함)
- `read.ComputedCache`는 값을 **60초**(`MAX_AGE_SECONDS`)만 들고, 저장본(`snapshots`) 어느 것이든 새로 수집되면 모두 버려. 쓰는 키: `guru.profiles`·`guru.similarity`·`guru.risk`·
  `guru.holders.index`·`sec13f.portfolio`·`sec13f.consensus`·`sec13f.newBuys`·`stock.scorecard`·`analytics.regime`·`analytics.regime.track`(그리고 스냅숏 글·검색 컨트롤러).
  60초인 까닭은 응답에 `ageSeconds`·`stale` 같은 '지금 기준' 값이 들어 있어서야(클래스 설명).
- 운영에서 같은 경로를 시간을 두고 부른 값(첫 바이트 ms):

| 경로 | 배포 2시간 뒤 첫 호출 | 약 80초 뒤(첫 · 바로 다음) | 약 5분 40초 뒤 |
|---|---|---|---|
| `/api/guru/similarity` | 345 | 247 · 10 | 276 |
| `/api/info/catalog` | 511 | 200 · 22 | 216 |
| `/api/stock/scorecard?symbol=AAPL…` | 124 | 9 · 9 | 143 |
| `/api/snapshot/text` | 161 | 9 · 10 | 144 |
| `/api/guru/profiles` | 1,824 | 102 · 9 | 100 |
| `/api/sec13f/consensus?…` | 92 | 9 · 10 | 57 |
| `/api/analytics/regime/track-record?asset=SPY` | 361 | 27 · 9 | 28 |

- QA(즐겨찾기 19곳)에서는 `/style` 화면을 몇 분 간격으로 네 번 열 때마다 `guru/profiles` 499~563 ms, `guru/similarity` 534~600 ms였어. SQL 기록으로는 한 번 계산에
  DB 시간이 약 415 ms이고, 거의 전부 `StoreRepository.readSnapshotFirstQuarters`(13F 저장본을 DB에서 다듬어 읽음 — 한 번에 33~131 ms)야.
- 그 읽기는 일부러 기억하지 않아: `readSnapshotMeta`의 설명대로, 큰 13F 트리를 기억하면 백엔드 힙(약 700 MB)을 위협해서야. 실제로 운영 백엔드는 이번 측정 전 275 MiB,
  13F 화면의 API를 부른 뒤 638.6 MiB였어(컨테이너 상한 1 GiB). **입력(저장본)을 기억하는 쪽으로 풀면 안 돼 — 결과(수 KB)를 더 오래 들고 있는 쪽이어야 해.**
- `/api/info/catalog`(정보 화면 일곱 곳이 부름)는 `ComputedCache`를 쓰지 않아. `InfoService.catalog`가 `collector.status()`(전체 보기 — 60초만 기억되는 행 수 세기 둘 포함)를
  불러 `taskSummary`만 써. 1차에서 만든 가벼운 보기(`/status?view=light`)에 무엇이 들어 있는지는 확인하지 않았어.
- `Sec13FFavoriteService.listEntries`는 즐겨찾기마다 `alert_rules`를 한 번씩 세(QA 19번·합 0.2 ms, 운영 12번). 지금은 작아.

### 작업 C — 검색 피드 (확인함 — 운영 응답을 한 번 받아 셈)
- `/api/search/feed?e=us:NVDA&tab=timeline`: 원본 1,630 KB(gzip 428 KB), `items` 2,756건, `rangeCounts` 7일 1,647 · 30일 2,079 · 1년 2,334 · 2년 2,756. 첫 바이트 301~343 ms(첫 호출 1,878).

- 대부분이 최근 글이라(30일 안이 75%) **기간으로 자르는 것은 효과가 작아.**
- 설계: 피드는 2년 묶음을 한 번에 주고 화면이 7일·30일·1년·2년으로 잘라(계약 `docs/specs/2026-11-14-info-search-contract.md` 3-4, `frontend/src/lib/endpoints.ts`의 주석, ADR 0041).

## 4. 작업별 명세

### 단계 0 — 측정 도구와 재현 자료
- `scripts/qa/hang-test.sh`: **기억과 잠금을 비운 상태로 재는 길**을 더해(예: QA 수집기·백엔드를 다시 띄우고 준비될 때까지 기다린 뒤 재는 인자). 머리 설명에 '화면 기록 직후에 재면
  앞선 호출의 기억·호스트 잠금 때문에 바로 끝난다'를 적어. `docker kill`은 쓰지 마(다시 뜨지 않음 — `CLAUDE.md`).
- `scripts/qa/sql-replay.sh`: 찍는 문장 수가 parse·bind 줄까지 세어 실행 문장의 약 2.4배야(예: `guru/profiles` 206 대 71). 실행 문장만 센 값을 함께 찍거나 그것으로 바꿔 —
  2026-11-24 기준선(653 · 417)과 견줄 수 있게.
- `scripts/qa/perf-seed.py`: **검색 피드 재현 자료**를 더해 — 관심 대상 한 곳에 모은 글 약 2,700건(합성 제목·요약·주소 `example.invalid`, 최근 30일에 75%)이 `/search?e=…` 화면에 나오게.
  지금 씨앗의 관례(QA 전용, 지어낸 값, 여러 번 넣어도 같음, 지우는 법)와 테이블 소유 규칙(ADR 0008)을 따라. 운영의 글을 가져오지 마.
- 모든 `/live/*` 경로를 hang(비운 상태)에서 한 번씩 재서 표로 만들어 — 무엇이 얼마나 붙잡히는지, 그 숫자가 설계 값인지(ADR·코드의 상한).
- 끝나면 기준선을 다시 재서 진행 기록에 적어(계획 세션의 값과 다르면 이유도).

### 작업 A — 차트 시계열 조회 (단계 1)
- **A1 예산.** `/live/ticker`도 화면 조회 예산 안에 끝나게 해(`http.run_with_budget` — 2차가 만든 길). yfinance 쪽 예산 세션과 '남길 시간' 처리(2차의 회귀)를 다시 확인해 —
  예산 10초에서 Yahoo를 정상으로 부르는지 QA `block`·정상 응답 모의로 봐. 백엔드 `liveTicker`도 예산 + 여유의 읽기 상한(`liveFetchClient` 관례)으로.
- 단계 0의 표에서 예산 + 2초를 넘는 다른 `/live/*` 경로가 있으면, 설계 값(문서로 확인되는 것)이 아닌 한 같은 방법으로 고쳐. 검색 셋은 2차의 판단을 따라.
- **A2 짧은 기억.** 같은 심볼·기간의 결과를 프롬프트 D-3의 시간만큼 기억해 Yahoo를 다시 부르지 않게 해. 받지 못한 결과(빈 `points`)는 기억하지 마.
  어디에 둘지(수집기 안 — Yahoo를 부르는 쪽, 다른 호출처도 덕을 봄)와 크기 상한(심볼·기간 조합이 끝없이 늘지 않게)을 정하고 이유를 기록해. 응답 모양은 바꾸지 마.
- 정기 수집(태스크)의 Yahoo 호출·잠금·간격은 건드리지 마. 요청이 늘지 않는 쪽이라 상대 부담 원칙에 맞아.
- 예산이 끝나면 지금의 '받지 못함' 응답 꼴 그대로(화면 문구·모양 그대로).
- 시험은 외부에 요청하지 마 — 응답하지 않는 루프백 임시 서버와 가짜 시계로.
- 받아들임 기준: QA `hang`(비운 상태)에서 `/api/macro/ticker`가 **예산 + 2초 안**, `block`·정상에서는 결과가 고치기 전과 같음, 같은 심볼·기간을 기억 시간 안에 다시 부르면
  수집기가 Yahoo를 부르지 않음(시험). 배포 뒤 운영에서 같은 경로를 여섯 번 안에서 불러 둘째부터 **30 ms 이하**(왕복 포함).

### 작업 B — 계산 결과 기억 (단계 2)
- **B1 13F 계열.** `guru.profiles`·`guru.similarity`·`guru.risk`·`guru.holders.index`·`sec13f.portfolio`·`sec13f.consensus`·`sec13f.newBuys`의 결과를, **그 계산이 기대는 입력이
  바뀔 때만** 다시 계산하게 해. 입력이 무엇인지(13F 저장본들의 수집 시각, 즐겨찾기 목록, 그 밖에 읽는 저장본)는 코드에서 하나씩 확인해 — 빠뜨리면 옛 결과가 남아.
  - 응답에 '지금 기준' 값(`ageSeconds`·`stale` 등)이 있으면 그 값은 지금처럼 60초 안에서 맞아야 해. 그 칸을 기억 밖에서 다시 매기든, 그 칸이 든 경로는 60초를 유지하든
    경로마다 정하고 이유를 기록해.
  - 저장본을 기억하는 쪽으로 풀지 마(§2 — 힙). 결과만.
  - `ComputedCache`의 다른 약속(같은 키는 한 번만 계산, 동시 실행 상한, 429 규칙, 서비스 안에서 부르지 않기 — ADR 0001)은 그대로 지켜.
  - 받아들임 기준: 씨앗을 넣은 QA에서 5분 넘게 쉬었다 불러도 `guru/profiles`·`guru/similarity`가 **30 ms 이하**(지금 500~600), 13F 저장본 하나의 수집 시각을 바꾸거나
    즐겨찾기를 더하고 빼면 다음 호출에 다시 계산됨(시험), 응답은 고치기 전과 같음(시각 칸 제외). 배포 뒤 운영에서 5분 쉬었다 한 번 불러 **50 ms 이하**.
- **B2 정보 목록.** `InfoService.catalog`가 행 수 세기를 일으키지 않게 해 — 태스크 요약만 받는 길(수집기의 가벼운 보기에 있으면 그것, 없으면 백엔드가 이미 가진
  `StoreRepository.readTaskSummary` 등). 수집기에 닿지 못할 때의 지금 동작(`collectorReachable: false`)은 그대로. 받아들임 기준: QA에서 2분 쉬었다 불러 **30 ms 이하**(운영 지금 200~216),
  응답 동일.
- **B3 `stock.scorecard`·`analytics.regime*`**: 같은 방법이 그대로 맞으면(입력이 분명하면) 함께, 아니면 기록만. `snapshot` 글은 건드리지 마.
- **B4(작음)** `listEntries`의 즐겨찾기마다 세기를 한 번의 질의로 — 응답 동일. 다른 일과 섞지 말고 따로 커밋.

### 작업 C — 검색 피드 (단계 3)
- **C1 먼저 재기.** 단계 0의 씨앗을 넣은 QA에서 `/search?e=…` 화면을 열 때의 DOM 수, 긴 작업 합, 그리기 시간(`page-apis.js`·`render-profile.js`, 데스크톱과 모바일 CPU 4배)을 재서
  진행 기록에 적어. 응답 300 ms의 내역(수집기에서 읽기·합치기·직렬화)도 QA에서 나눠 재.
- **C2 기준을 넘으면 고쳐.** 넘는 기준: 모바일 CPU 4배에서 긴 작업 합이 600 ms를 넘거나 DOM이 5,000개를 넘을 때. 고치는 방식은 프롬프트 D-4 — 기본은 **화면에서 보이는 만큼만
  그리기**(날짜 묶음 단위로 이어 그림)야. 건수·기간 단추·같은 글 묶기·검색은 지금처럼 받은 전체를 기준으로 계산하고, API와 계약 문서는 바꾸지 마.
  이어 그리는 자리에서 레이아웃이 밀리지 않게 하고, 키보드·화면 낭독기로도 끝까지 갈 수 있어야 해.
- 기준을 넘지 않으면 고치지 말고 잰 값만 기록해.
- 응답 크기를 줄이는 일(칸 줄이기·쪽 나누기)은 계약이 바뀌니 이번에는 하지 마 — 필요해 보이면 근거와 함께 보고만.
- 받아들임 기준(C2를 했을 때): 같은 씨앗에서 긴 작업 합과 DOM이 기준 아래, 보이는 줄의 내용·순서·건수 표시는 고치기 전과 같음(화면 시험), `make smoke` 통과.

### 작업 D — 모바일 레이아웃 밀림 (단계 3)
- §2 표의 일곱 화면에서, 응답이 오기 전 자리(뼈대·빈 상태)의 높이를 응답 뒤와 맞춰 밀림을 없애. **내용·순서·숫자는 그대로**(프롬프트 D-5). 2차 E의 방식과 같아.
- QA에서만 뜨는 안내 때문인 몫은 먼저 가려(외부가 정상으로 올 때를 흉내 내는 방법은 2차 진행 기록의 '측정 함정' — 바꿔 끼운 응답에 CORS 머리글이 없으면 화면이 연결 실패를 그림).
  QA 전용으로 판정한 몫은 고치지 말고 근거와 함께 기록해.
- 데스크톱에서 0이던 화면(기관 상세·`/search`)이 모바일에서만 밀리는 까닭부터 봐 — 좁은 폭에서만 줄이 꺾이는 자리일 가능성이 커(추정).
- `/scorecard`·`/markets/i/us10y`(0.06~0.07)는 같은 원인으로 함께 고쳐지면 고치고, 아니면 기록만.
- 받아들임 기준(출처 경고 요청을 막은 상태, `page-apis.js` 모바일): 일곱 화면 모두 **0.05 이하**(QA 전용 몫은 빼고 셈 — 뺀 근거를 적어), 데스크톱 값이 늘지 않음,
  58화면 전후 비교에서 0.02 넘게 늘어난 화면 없음, `/s/us/NVDA` 모바일 Lighthouse(3회 중앙값) 0.10 이하, 화면 시험·`ui-audit.js`·`make smoke` 통과.

## 5. 지켜야 할 규칙

원문은 `CLAUDE.md`·`docs/DEVELOPMENT.md`·`docs/PRINCIPLES.md`·`docs/adr/README.md` — 먼저 읽어. 이 지시문과 충돌하면 프로젝트 규칙이 우선이고,
무엇을 따랐는지 진행 기록에 적어.

- 작업 브랜치 `claude/perf-round3-2026-11`(단계별로 나눠도 됨). 커밋 `type(scope): 요약`(요약은 한국어, type은 이 저장소가 쓰는 fix·test·feat·refactor·docs·chore) +
  `Co-Authored-By` 줄. 옮기는 커밋과 고치는 커밋을 나눠. 모든 커밋이 `make test`를 통과해야 해 — `make`의 종료 코드를 따로 확인해.
  커밋 전에 `git diff --cached`로 딸려 들어가는 변경이 없는지 봐(2차 때 미리 올려 둔 변경이 문서 커밋에 섞인 일이 있었음).
- 작업 A·B1·B2·D는 결함으로 다뤄: `QA-###` — 재현 시험 `test(QA-###)`(고치기 전 strict xfail/`@Disabled`) → `fix(QA-###)`. 다음 번호는 결함 기록(`docs/qa/` 최신 파일)의 끝과
  `git log`에서 확인해(2026-11-27 기준 QA-1039). 다른 세션과 겹치지 않게 시작할 때 쓸 번호를 먼저 적어.
- **성능 시험은 QA 스택에서만.** 로컬 스택(3002…)에는 하지 마. QA 스택은 하나뿐이고 포트가 고정이야 — 떠 있으면 누가 띄웠는지 먼저 보고
  (컨테이너 라벨 `com.docker.compose.project.working_dir`), 다른 세션의 작업 폴더면 다시 빌드하거나 내리기 전에 사용자에게 물어봐.
- **운영 서버 측정 규칙(읽기만)**: 조회(GET) API를 한 번에 하나씩, **경로마다 여섯 번까지 — 부른 횟수를 적어 가며**(1·2차 모두 이 수를 넘긴 일이 있었음), 응답은 버리고 시간만 적어.
  실제 계좌 경로(`/api/brokerage/account`·`/api/manual/*`·`/api/realtrade/*`·`/api/toss/*`)는 부르지 마. 매매·결정 시각(§7)을 피해. 부하·브라우저 시험·Lighthouse는 운영에 하지 마.
  운영 DB는 통계 표·크기·`EXPLAIN`(실행 없음)까지만. 주소·IP·tailnet 이름을 저장소에 적지 마.
- 운영의 글·공지 원문·실제 계좌(토스·ISA) 자료는 저장소·시험 자료·QA 기록·로그 어디에도 넣지 마(합성 자료만).
- 모의 매매·실제 매매 코드와 프롬프트·스키마·패킷 고정본은 건드리지 않아. 닿게 되면 멈추고 물어봐.
- 테이블마다 쓰는 프로세스는 하나(ADR 0008). 정보 검색의 예산·상한(ADR 0041)과 차단 통과 수집의 규칙은 바꾸지 마.
- 화면은 작업대 화면 언어(ADR 0042)와 화면 계층(ADR 0004)을 지켜. 고친 화면은 `node scripts/qa/ui-audit.js`를 전후로 돌려.
- 새 의존성·스키마 변경·백엔드의 새 `/api` 경로는 하지 마(프롬프트 D-6). 꼭 필요하면 이유를 설명하고 멈춰.
- 이모지 금지(코드·주석·문서·스크립트 출력·커밋 메시지). 날짜는 KST, 없는 숫자는 `null`.
- 라이브러리 동작은 기억으로 쓰지 말고 문서(Context7이 연결돼 있으면 그것)에서 지금 판 기준으로 확인해.

## 6. 검증 수단

| 묶음 | 명령 |
|---|---|
| 수집기 · 백엔드 · 화면 | `make test-collector` · `make test-backend` · `make test-frontend` |
| 전체 | `make test`(CI와 같은 명령) — 여러 작업 폴더에서 함께 돌릴 때는 `make test-isolated` |

- 계획 세션은 `make test` 기준선을 재지 않았어. 시작할 때 `main`에서 한 번 재서 진행 기록에 적어.
- 성능은 고치기 전후를 **같은 QA 스택·같은 DB·같은 백엔드**에서 재. Lighthouse는 3회 중앙값. '쉬었다 부르기'는 쉰 시간을 함께 적어.

## 7. 전달과 배포

- 단계마다: 작업 브랜치 → `make test` 통과 → 본체 폴더 `main`에 fast-forward → `git push origin main <브랜치>` → CI 6/6 확인 → (서버 코드가 바뀐 단계면) 배포.
  새 push에 밀려 취소된 실행은 그 위 커밋의 실행으로 확인하고, GitHub 쪽 사정으로 취소된 job만 다시 돌려.
- 배포 여부는 프롬프트 D-2를 따라. 서버에서 `bash ~/My_macro_dashboard_v2/scripts/vultr/deploy.sh`. 앱 컨테이너가 1~2분 다시 만들어지니 매매·결정 시각을 피해:
  한국 거래 창(평일 08:45~15:35 KST — `deploy.sh`가 막음), 미국 정규장과 두 시장의 정기 결정·고정 장중 판단·마감 브리핑 전후(시각은 서버 설정으로 확인),
  일요일 주간 복기(21:00·22:00), 백업(08:00·일 23:00), 토요일 09:30 복원 확인. 권하는 창은 평일 16:30~22:00, 토요일 낮, 일요일 20:30 전이야.
- 배포 뒤 확인: 컨테이너 여섯 정상, `make status`, 백엔드 ERROR 0, 그 단계의 운영 확인 항목. 확인한 것과 못 한 것을 구분해 보고.
- 서버 접속은 Tailscale SSH야. 추가 확인(브라우저 재인증)에서 멈추면 `timeout`으로 끊고 사용자에게 재인증을 부탁해 — 비상 키 경로로 돌아가지 마.

- 받아들임 기준에 못 미칠 때, 또는 기준을 바꿔야 한다고 볼 때
- 계산 결과가 고치기 전과 달라질 수 있거나, 신선도 표시(`ageSeconds`·`stale`)를 60초 안에서 맞게 둘 방법이 없을 때(작업 B)
- 검색 화면의 보이는 내용·건수 표시가 달라지거나 API·계약을 바꿔야 할 때(작업 C), 화면의 내용·순서·구조가 바뀌는 방법이 필요해 보일 때(작업 D)
- 스키마·색인 변경, 백엔드의 새 `/api` 경로, 새 의존성이 필요할 때
- 모의 매매·실제 매매 코드나 고정본에 닿게 될 때
- QA 스택을 다른 세션이 쓰고 있을 때
- 이 지시문과 지금 코드가 크게 달라 계획대로 할 수 없을 때
