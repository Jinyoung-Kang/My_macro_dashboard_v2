### 0-1. 테이블 소유 규칙 (ADR 0008의 핵심)

- 테이블마다 **쓰는 프로세스는 하나**입니다.

  | 쓰는 쪽 | 테이블 |
  |---|---|
  | 수집기 | `snapshots`·`timeseries`·`observations`·`collector_*`·`refresh_requests`·`schema_migrations` |
  | 백엔드 | 아래 §1의 새 테이블 |

- 반대쪽은 읽기만 합니다. 예외는 하나입니다: 수집기가 **관심 종목 코드 목록을 읽는 것**(§4-5).
- 스키마 파일은 지금처럼 **`db/migrations/` 한 곳**에서 번호를 매기고, 수집기가 기동할 때 적용합니다.
  - 백엔드에 Flyway를 따로 두면 번호 체계가 둘이 되어 충돌합니다.
  - 대신 백엔드는 기동할 때 `schema_migrations`에서 **필요한 최소 버전**을 확인합니다. 모자라면 기동을 멈춥니다.
  - 이 확인이 없으면 테이블이 없는 채로 돌다가 첫 쓰기에서 500이 납니다.
- **선행 조건:** 지금 테스트 DB(`make db-test`)와 CI는 SQL 파일을 psql로 적용만 하고 버전을 기록하지 않습니다(`macrodash_test`에 `schema_migrations`가 없음).
  - 이대로 최소 버전을 확인하면 백엔드 테스트와 CI가 깨집니다.
  - 그래서 A1에서 `make db-test`와 CI도 **수집기와 같은 적용기**(`collector/app/migrations.py`)로 적용해 버전을 남기게 바꿉니다. 적용 경로를 하나로 줄이는 효과도 있습니다.
- 지키는 방법: 아키텍처 테스트에 "백엔드 소스가 수집기 테이블에 `INSERT/UPDATE/DELETE`하지 않는다"를, 수집기 테스트에 그 반대를 추가합니다.
- DB 계정을 둘로 나누는 것(테이블별 권한)은 공개 배포 단계의 강화 항목으로 남깁니다. 지금은 둘 다 `macro`입니다.

### 0-2. 백엔드 정기 작업

**방식**

- Spring의 `@Scheduled`를 씁니다. 새 의존성은 없습니다.
- 작업마다 PostgreSQL **advisory lock**을 잡습니다. 백엔드를 두 대 띄우거나 재시작이 겹쳐도 같은 작업이 두 번 돌지 않게 하려는 것입니다.

**작업 목록**

| 작업 | 주기 | 하는 일 |
|---|---|---|
| `RegimeRecorder` | 30분 | 오늘(KST) 판정 기록이 없고 입력이 갱신됐으면 한 건 기록 |
| `AlertEvaluator` | 5분 | 세 트리거를 **매번 전부** 평가 → 사건 생성(이미 있으면 무시) → 규칙이 맞는 사용자의 알림함에 넣기 |

알림이 화면 알림함만이라(D2) 발송 작업은 두지 않습니다. 외부 채널을 붙일 때 `AlertSender`를 더합니다(§4-4).

**새 데이터를 아는 방법 — 알아내지 않고 매번 전부 평가**

- 수집기가 백엔드를 부르게 하지 않습니다. 그러면 수집기가 백엔드를 알게 되어 의존 방향이 뒤집힙니다.
- `collector_task_runs`의 번호를 이어 처리 지점으로 쓰는 방법은 버렸습니다. 놓치는 건이 생기기 때문입니다.
  - 시간 초과로 `error`가 기록된 태스크가 뒤늦게 저장본을 씁니다. 이 경우 `ok` 기록이 없습니다.
  - 태스크 8개가 스레드마다 따로 커밋해 번호 순서와 커밋 순서가 다릅니다.
- 대신 평가를 **멱등**으로 만듭니다. 사건 키 `UNIQUE`가 있으므로, 같은 데이터를 다시 평가해도 새 사건은 생기지 않습니다.
  - 매번 읽는 양은 작습니다. 판정 기록 2행, 토스 흐름 저장본 2개, 13F 저장본 12개입니다.
- 그래서 이어 처리 지점 테이블이 필요 없습니다.

**정기 작업은 수집을 일으키지 않습니다**

- 지금 `auto` 읽기 모드에서는 저장본이 오래됐으면 **읽기만 해도** 수집을 요청합니다.
- 정기 작업이 같은 길로 읽으면 5분마다 수집을 깨웁니다.
- 그래서 정기 작업은 `StoreReader`에 수집 요청 없이 읽는 방법(지금의 `store_only`와 같은 동작)을 두고 그것만 씁니다.
- 오래된 저장본이면 평가하지 않습니다. 명세 C의 "오래된 저장본으로는 알림 없음"과 같은 규칙입니다.

### 0-3. 패키지 배치 (ADR 0001 규칙 안에서)

```
feature/auth/      (기존을 넓힘) 계정·세션·접근 정책·등급·사용량 한도·운영자 사용자 관리. URL(/api/auth/*)은 그대로
feature/alert/     규칙·관심 목록·알림함·평가기·알림 문구
feature/insight/   (기존) 국면 — 판정 기록기·성과 서비스 추가
store/             (기존) DB 접근. 새 쓰기 저장소 UserStore·SessionStore·AlertStore·RegimeLogStore 추가
support/           CurrentUser(id·역할·등급) record — 모든 컨트롤러가 읽을 수 있는 자리
analytics/         PointInTime · ForwardReturns(CotExtremes에서 떼어 냄) · RegimeBacktest · AlertRules
config/WebConfig   SessionFilter가 feature/auth의 세션 조회·접근 정책을 씀 (config → feature 허용)
```

**저장소 클래스 위치 — `store`에 둡니다**

- ADR 0001은 DB 접근을 `store`에 두고, `store`는 우리 다른 패키지를 모르게 합니다. 새 쓰기 저장소도 이 규칙대로 `store`에 두고, 입출력 타입(record)도 `store` 안에 정의합니다.
- `store`의 뜻은 "수집기 테이블 읽기"에서 **"DB 접근 전부"** 로 넓어집니다. ADR 0001 표의 설명을 같이 고칩니다.
- **지키는 방법:** `ArchitectureRulesTest`에 "JDBC(`JdbcTemplate`·`java.sql`)는 `store`에서만"을 추가합니다. 지금은 이 규칙이 없어 기능 패키지가 DB를 직접 써도 막지 못합니다.

**사용자 정보 타입은 `support`에**

- ADR 0001 규칙 2에 따라 컨트롤러는 자기 기능의 서비스와 `support`·`config`만 씁니다.
- 그래서 다른 기능의 컨트롤러가 `feature/auth`의 사용자 타입을 가져다 쓸 수 없습니다.
- 대신 `SessionFilter`가 요청 속성에 `support.CurrentUser`를 넣고, 컨트롤러는 그것을 서비스에 넘깁니다.

**기능 사이 의존(새로 생기는 것)**

| 의존 | 왜 |
|---|---|
| `alert → insight` | 판정 기록 |
| `alert → positioning` | 수급 |
| `alert → institution` | 13F |
| `alert → auth` | 수신자(사용자·등급) |
| `ai → auth` | 사용량 한도 |

- 순환은 없습니다. `auth`는 아무 기능도 쓰지 않습니다.
- 등급에 따라 범위를 줄이는 서비스(국면 기록 30건, 13F 최신 분기 등)는 `support.CurrentUser`만 받으므로 `auth`에 의존하지 않습니다.

**분석 계층**

- `analytics`는 지금처럼 `java.*`만 씁니다.
- 판정 기록·사건 판정은 입력을 record로 받는 **순수 함수**로 두고, 규칙을 테스트로 고정합니다.

## 1. 데이터 모델 (새 마이그레이션)

번호는 단계 순서대로 붙입니다(V3: 판정 기록, V4: 계정, V5: 알림). 모든 파일은 여러 번 실행해도 안전하게 씁니다(`IF NOT EXISTS`). 저장소 클래스는 모두 `store`에 둡니다(§0-3).

| 테이블 | 단계 | 열(요지) | 제약·비고 |
|---|---|---|---|
| `regime_log` | A | `verdict_date date PK`, `code`, `label`, `inputs jsonb`(값·입력별 기준일), `missing text[]`, `computed_at`, `rule_version` | 추가만 함. 백엔드 코드에 UPDATE·DELETE 문이 없음(테스트). `rule_version`은 판정 규칙(임계치)이 바뀐 날을 구분 |

**사건 키**

사건 키(`event_key`)가 중복 방지와 "처음 본 것" 판정을 함께 맡습니다.

| 트리거 | 키 모양 |
|---|---|
| 국면 전환 | `regime:{판정일}:{이전}>{이후}` |
| 외국인 연속 순매수 | `streak:{대상}:foreign:{도달일}:{N}` |

## 2. 기능 A 설계 — 판정 성과

### 2-1. 라이브 판정 기록 (`RegimeRecorder`)

1. 매 30분마다 오늘(KST) 행이 있는지 봅니다. 있으면 끝냅니다.
2. 화면과 **같은 계산**(`AnalyticsService`의 현재 판정)으로 판정을 냅니다. 화면과 기록이 갈라질 여지를 없애려는 것입니다. 다만 읽기는 수집을 일으키지 않는 방법으로 합니다(§0-2).
3. 입력 넷의 기준일이 모두 "허용 지연" 안이면 기록합니다.
   - 허용 지연: 일별은 4영업일, NFCI는 12일.
   - 하나라도 넘으면 "판정 불가(입력 오래됨: …)"로 기록합니다.
   - 단, **KST 18:00 전에는 기록하지 않고 기다립니다.** 아침에는 수집이 아직 안 돌았을 수 있기 때문입니다.
4. `INSERT … ON CONFLICT (verdict_date) DO NOTHING`. 두 대가 동시에 돌아도 한 건입니다.

### 2-2. 시점 기준 재현 (`analytics/PointInTime`, `RegimeBacktest`)

**발표 지연 규칙**

시리즈마다 "관측일 → 쓸 수 있게 되는 날"을 정합니다. 값은 보수적으로 잡습니다(늦게 알았다고 가정). 일정 자체는 **구현할 때 FRED 발표 일정으로 다시 확인합니다** — 지금 표는 일반적인 발표 관행을 적은 가정입니다.

| 시리즈 | 관측일 | 쓸 수 있는 날(가정) |
|---|---|---|
| T10Y3M | 매 영업일 | 다음 영업일 |
| 하이일드 스프레드 | 매 영업일 | 다음 영업일 |
| NFCI | 금요일 | 다음 주 수요일 |
| 순유동성 | 매일(주간 WALCL·TGA를 일별 RRP에 맞춰 이어 붙인 값) | 다음 영업일. WALCL·TGA는 수요일 값이 목요일에 나오며, 이어 붙인 값은 발표 전 수요일 값을 쓰지 않음 |

**평가 방법**

- **평가일:** 매주 목요일로 고정합니다(WALCL 발표일). 지금 화면처럼 기간 시작일에 따라 요일이 바뀌지 않게 합니다.
- **입력 이력:** `timeseries`(누적)에서 읽습니다. 그래야 하이일드가 FRED의 3년 창을 넘어서도 남습니다.
- **가격:** 스냅샷(`equity.price_history`, `sector.etf_history`)에서 읽습니다.
- **같은 값 확인:** 화면의 현재 판정(스냅샷)과 재현(`timeseries`)이 겹치는 날에 같은 값을 쓰는지 대조합니다. 두 저장소가 갈라지면 화면과 성과표가 다른 말을 합니다.
  - 대상은 개정이 드문 세 입력(T10Y3M·하이일드·순유동성)뿐입니다.
  - NFCI는 대조하지 않습니다. 스냅샷은 최신 개정본이고 `timeseries`는 개정본이 섞여 있어, **구조상 다릅니다.**
  - 대조는 운영 데이터 복사본으로 QA 스택에서 돌리는 점검 스크립트로 합니다. 단위 테스트에는 맞춘 고정 데이터를 씁니다.
- **NFCI 개정:** `timeseries`의 NFCI는 당시 발표값이 아닙니다. 처음 수집한 날의 개정본과 관측 1~2주 뒤의 값이 섞여 있습니다. 한계는 화면에 적습니다(명세 §2-5).
  - ALFRED 빈티지(`realtime_start`)로 당시 값을 받는 것은 2단계 선택 사항입니다. 수집기 변경과 FRED 호출 수가 늘어납니다.

### 2-3. 이후 수익률 (`analytics/ForwardReturns`)

**COT 코드에서 떼어 내기**

- `CotExtremes`의 `forwardReturn`·`summarize`·`baseline`을 떼어 공통 클래스로 옮깁니다.
- **옮기는 커밋**(동작 동일, 기존 테스트 그대로 통과)과 **고치는 커밋**을 나눕니다.

**고칠 것**

## 3. 기능 B 설계 — 다중 사용자

### 3-1. 비밀번호와 세션

**비밀번호 해시**

- **Argon2id**로 저장합니다.
- 새 의존성이 필요합니다. 구현 단계에서 Maven Central의 GA 버전을 확인하고, 이유를 먼저 말씀드린 뒤 넣습니다.
  - `spring-security-crypto`: 해시만 씁니다. Spring Security 전체를 들이지는 않습니다.
  - Argon2용 BouncyCastle.
- 대안은 bcrypt입니다. `spring-security-crypto`만으로 되지만, OWASP 권장 순위가 Argon2id보다 아래입니다.

**세션**

- 쿠키에는 32바이트 무작위 토큰을 넣고, DB에는 SHA-256 해시만 둡니다.
- 요청마다 해시로 세션을 찾습니다. 이 규모에서는 인덱스 조회 한 번이면 충분합니다.
- `last_seen_at`은 5분에 한 번만 갱신합니다.

**JWT를 버리는 이유**

- 즉시 끊어야 할 일이 많아집니다: 로그아웃, 비밀번호 변경, 등급 변경, 계정 삭제.
- 상태 없는 토큰으로 이를 하려면 결국 서버에 차단 목록이 필요합니다. 지금 그 목록이 메모리에 있어 재시작하면 사라집니다.
  - 반대로 `JWT_SECRET`이 비었거나 짧으면 실행마다 서명 키가 바뀌어, 재시작할 때 모든 사람이 로그아웃됩니다.
- DB 세션이면 이 문제가 한 번에 없어지고, `jjwt` 의존성도 뺄 수 있습니다.

**쿠키 속성과 요청 출처 확인**

- 쿠키 속성은 그대로입니다: `HttpOnly`, `SameSite=Strict`, `COOKIE_SECURE=true`일 때 `Secure`(HTTPS를 자동으로 감지하지 않음).
- 상태를 바꾸는 요청(POST·PUT·DELETE)에 `Origin` 확인을 더합니다. 지금은 SameSite에만 기대고 있습니다.

**로그인 지연**

- 지금의 주소 기준 지연(`LoginThrottle`)에 **계정 기준** 지연을 더합니다. 같은 이메일로 10회 실패하면 지연합니다.
- 없는 이메일도 가짜 해시와 비교해 **같은 시간**이 걸리게 합니다. 응답 시간으로 계정이 있는지 알아낼 수 없게 하려는 것입니다.

### 3-2. 접근 정책

- `AccessPolicy`(feature/auth)는 표 하나입니다. `(메서드, 경로 패턴) → PUBLIC | MEMBER | PRO | OWNER`.
- `SessionFilter`가 세션 → 사용자(역할·등급)를 찾아 정책과 비교합니다.
  - 세션이 없으면 401, 등급이나 역할이 모자라면 403입니다.
  - 403 응답은 `{"error":"…","required":"PRO"}` 모양입니다.
- **같은 경로 안의 범위 제한**(예: 무료는 최근 30건)은 정책 표가 아니라 서비스가 사용자 등급을 받아 처리합니다. 정책 표는 "부를 수 있나"만 정합니다.
- **지키는 방법:** `AccessPolicyTest`가 `RouteInventoryTest`의 경로 목록 전부가 정책에 있는지 대조합니다. 한 경로라도 빠지면 실패합니다.
- **응답 캐시:** 두 가지를 지킵니다. 넣으면 다른 사용자의 응답이 섞일 수 있습니다.
  - 사용자별 데이터(관심 목록·알림함·계정)는 `ComputedCache`에 넣지 않습니다.
  - 등급에 따라 범위가 다른 응답은 키에 등급을 넣습니다.
  - 두 규칙은 컨트롤러 테스트로 고정합니다.

### 3-3. 기존 운영 이전 (명세 B8)

1. 백엔드가 기동할 때 `users`가 비어 있고 `APP_PASSWORD`·`OWNER_EMAIL`이 모두 있으면 `OWNER` 계정을 만듭니다. 비밀번호는 `APP_PASSWORD`의 Argon2id 해시입니다.
2. 둘 중 하나라도 없으면 계정을 만들지 않고, 로그인을 받지 않으며, 무엇을 `.env`에 넣을지 기동 로그로 안내합니다. `APP_PASSWORD`가 공개된 옛 기본값(`admin1234@`)이어도 없는 것으로 봅니다. 지금 코드도 이 값을 거부합니다.
   - 지금 `APP_PASSWORD`가 비었을 때 임시 비밀번호를 만들어 로그로 알리는 것과 같은 계열의 처리입니다.
   - 자리표시 이메일을 코드 기본값으로 두지 않습니다(CLAUDE.md 규칙).
   - `make setup`은 `OWNER_EMAIL`을 물어 채우고, `make doctor`는 빠졌으면 알려 줍니다.
3. 계정이 생긴 뒤에는 `APP_PASSWORD`를 다시 읽지 않습니다. 비밀번호 변경은 화면에서 합니다.
4. `.env.example`에 `OWNER_EMAIL=`, `MAIL_*` 이름만 추가합니다.

### 3-4. 화면

| 경로 | 내용 |
|---|---|
| `/login` | 이메일 칸 추가 |
| `/signup` · `/verify` · `/reset` | 가입 · 메일 인증 · 비밀번호 재설정 |
| `/account` | 내 정보, 비밀번호 변경, 세션 목록과 "모두 로그아웃", 계정 삭제 |
| `/admin/users` | `OWNER`만. 사용자 목록, 등급·역할 지정, 감사 기록 |

- 사이드바에는 등급이 모자란 메뉴에 자물쇠 표시를 붙입니다. 누르면 안내 카드가 뜹니다.

## 4. 기능 C 설계 — 알림

### 4-1. 흐름

```
5분마다 AlertEvaluator ──► 사건 판정(analytics/AlertRules, 순수) ──► alert_events (event_key UNIQUE)
                                                                            │
             alert_rules(사용자별) ◄── 수신자 찾기 ◄──────────────────────────┘
                    │
                    ▼
             alert_deliveries (UNIQUE event·user·channel, channel='inbox') ──► 화면 알림함 · 읽지 않은 수
```

- **사건**은 "무슨 일이 있었나"(전역)입니다.
- **알림함 항목**(`alert_deliveries`)은 "누구에게"입니다.
- 둘을 나누면 한 번의 사건 판정을 수신자 수만큼 반복하지 않고, 중복 방지를 DB 제약 두 개가 맡습니다. 외부 채널을 붙일 때도 이 구조에 채널만 더하면 됩니다.

### 4-2. 트리거별 판정 (순수 함수)

| 트리거 | 입력 | 판정 |
|---|---|---|
| 국면 전환 | `regime_log`의 오늘 행과 직전 **유효** 행(`UNKNOWN` 제외) | 오늘이 유효하고 직전 유효 판정과 코드가 다르면 사건 |
| 외국인 연속 | 토스 투자자 기록 중 **확정** 기록만 | `streak == N`에 도달한 날 사건. 키에 N을 넣어 N이 다른 규칙은 별도 사건 |
| 13F 신규 | 관심 기관의 최신 분기와 직전 분기 | 최신 공시일이 처음 보이면 `HoldingsDiff.NEW` 목록을 담아 사건 |

**13F 신규 편입의 표본 범위**

- 지금 신규 매수 화면은 **평가액 상위 200종목** 안에서만 비교합니다(`newBuys`).
- 알림은 전체 보유를 비교하고, 본문에는 평가액 상위 10개 + 전체 개수를 적습니다.

**토스 기록의 확정 판정 (C2의 전제)**

- 기록 날짜가 오늘(KST)보다 이전이면 확정입니다.
- 오늘 기록은 다음과 같이 봅니다.
  - **종목별:** 장중에 비어 있다가 저녁 확정 때 채워지는 칸(개인·기관 세부·기타법인·외국인 보유)이 모두 값이 있으면 확정.
  - **시장 전체:** 다음 날부터 확정으로 봅니다. 보수적으로 하루 늦게 알립니다.
- 단위가 다릅니다. 종목별은 **주식 수(주)**, 시장 전체는 **금액(원)** 입니다. 알림 본문에도 그 단위로 적습니다.
- 토스의 정확한 확정 시각은 확인하지 못했습니다(문서·코드에 없음). 구현 단계에서 API 문서로 확인합니다.

### 4-3. 처음 켤 때 몰아 보내지 않기

- 규칙에는 `created_at`이 있습니다. 사건의 `occurred_on`이 규칙 생성일보다 앞이면 그 규칙으로는 알림함에 넣지 않습니다.
- 백엔드를 처음 올리거나 오래 꺼져 있다가 켜지면 밀린 데이터가 한꺼번에 평가됩니다. 이때 사건 발생일이 **3일보다 오래된 것은** 알림함에 "지난 사건"으로 표시해 넣고, 읽지 않은 수에는 세지 않습니다.

### 4-4. 알림함 (D2: 화면 알림함만)

**API**

| 경로 | 내용 |
|---|---|
| `GET /api/alerts/inbox?before=` | 최근 순 목록 |
| `GET /api/alerts/unread-count` | 읽지 않은 수 |
| `POST /api/alerts/inbox/read` | 하나 또는 모두 읽음 |

규칙·관심 목록 CRUD는 `/api/alerts/rules`·`/api/alerts/watch/*`에 둡니다.

**동작**

- 사이드바·탭 제목의 읽지 않은 수는 기존 `useApi` 자동 갱신(5분)으로 읽습니다. 새 실시간 연결(SSE·WebSocket)은 두지 않습니다. 사건이 5분 주기 평가에서 생기므로 더 빠를 이유가 없습니다.
- 90일이 지난 항목은 `AlertEvaluator`가 하루 한 번 지웁니다. 사건(`alert_events`)은 지우지 않습니다. 사건은 중복 판정 키이자 기록입니다.
- 알림 문구는 `feature/alert` 안의 순수 함수로 만들고, 행동 지시어(매수·매도·비중 등) 금지를 테스트로 검사합니다.

**외부 채널을 나중에 붙일 때 (지금 만들지 않음)**

- `alert_deliveries`에 `status`·`attempts`·`next_attempt_at`·`error`를 더합니다.
- `AlertSender`(1분, `FOR UPDATE SKIP LOCKED`)를 둡니다.
- 재시도는 간격을 늘려 최대 5회로 합니다. 다시 해도 안 될 오류(인증 실패 등)는 바로 실패로 둡니다.
- 조용한 시간(발송 시각을 미룸)과 수신 거부 링크(`email_tokens`에 `unsubscribe` 용도 추가)를 둡니다.
- 메일이면 계정 기능의 발송 기반(B2)을 그대로 씁니다. 텔레그램이면 SDK 없이 `RestClient`로 보내고, 봇 토큰은 환경변수에 둡니다.

### 4-5. 관심 종목과 종목별 수급 수집 범위

- 지금 종목별 수급(`toss_stock_flows`)은 수집기가 레이더에서 고른 **최대 40종목**입니다.
- 관심 종목 알림을 하려면 사용자가 고른 종목이 이 범위에 들어가야 합니다.

**바꾸는 방법**

- 수집기가 `watch_stocks`의 서로 다른 코드를 **읽어서** 범위에 더합니다. 이것이 테이블 소유 규칙의 유일한 교차 읽기입니다.
- 상한: 사용자당 20종목, 전체 관심 종목 합계 60종목. 레이더 40종목과 합쳐 최대 100종목입니다.
  - 토스 API 호출 한도는 구현 단계에서 확인하고 조정합니다.
- 범위를 넘으면 규칙을 만들 때 거절합니다. 화면에는 "수집 범위 초과"가 뜹니다. 받아 두고 조용히 안 보내는 일은 없게 합니다.

## 6. 테스트 계획

**`analytics` 순수 함수**

| 대상 | 고정할 규칙 |
|---|---|
| `PointInTime` | 발표 전날까지 직전 값, 발표일부터 새 값 |
| `ForwardReturns` | 가격 시작 전 진입은 `null`. 기간 미완료는 `null`. 기준선 기간 일치. 겹치지 않는 구간 수 |
| `RegimeBacktest` | 입력 하나라도 없으면 `UNKNOWN`. 평가 요일 고정 |
| `AlertRules` | `UNKNOWN` 전환 무시. `streak == N`에서만 사건. 잠정 기록 제외. 13F 첫 공시만 |

**통합 (`macrodash_test`)**

- 새 마이그레이션이 V1부터 순서대로 적용되고 버전이 기록됩니다(테스트 DB·CI도 같은 적용기). 백엔드의 최소 버전 확인이 동작합니다.
- 정기 작업이 오래된 저장본을 읽어도 수집기 호출이 0건입니다(가짜 수집기 클라이언트로 확인).
- 판정 기록을 두 번 실행해도 한 건입니다. 두 스레드로 동시에 돌려도 한 건입니다.
- 사건 키 중복이면 사건이 하나만 생깁니다. 알림함 항목 `UNIQUE`도 같습니다. 평가기 두 개를 동시에 돌려도 알림함에 한 건입니다.
- 세션 해지가 재시작(새 컨텍스트) 뒤에도 유지됩니다.

**보안**

- 계정 존재 여부: 없는 이메일과 틀린 비밀번호의 응답 본문·상태 코드가 같습니다. 시간 차이는 상한 안입니다.
- 재설정·인증 토큰은 한 번만 쓸 수 있고, 만료 뒤에는 거절됩니다.
- 비밀번호와 토큰 원문이 로그에 없습니다. 이 확인은 로그 캡처 테스트로 합니다.
- 다른 출처의 `Origin`으로 보낸 상태 변경 요청은 403입니다.
- `AccessPolicyTest`: 정책 미분류 경로가 0개입니다.

**외부 호출 없음**

- 계정 메일(인증·재설정)은 테스트 안에 띄운 가짜 SMTP 서버(Java)로 받습니다.
- QA 스택에서 실제 흐름을 볼 때는 메일 수신 확인용 컨테이너(mailpit)를 **QA 스택에만** 띄웁니다. 새 이미지라 그 단계에서 이유를 먼저 말씀드립니다.

**화면**

- `lib`의 등급 표시·알림 문구 순수 함수 테스트.
- `endpoints.test.ts`에 새 경로 추가.
- 잠금 메뉴 렌더링 테스트.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 백엔드 쓰기 도입으로 "수집기만 쓴다"는 경계가 흐려짐 | 테이블 소유 표 + 양쪽 소스 검사 테스트(§0-1) |
| 판정 성과의 표본이 작음(3년, 전환 몇 번) | 숫자를 꾸미지 않음. 표본 부족이면 숫자 대신 문구. 라이브 기록을 가장 먼저 시작 |
| 잠정치·오래된 값으로 잘못된 알림 | 확정 판정 규칙, 사건 키, 처음 켤 때 백필 금지, 3일 지난 사건은 알림함만 |
| 정기 작업이 두 번 돎(재시작·다중 인스턴스) | advisory lock + DB 유일 제약. 작업이 두 번 돌아도 결과는 한 번 |
| 계정 메일(인증·재설정)이 스팸함으로 감 | 로컬 단계는 SMTP 계정 자체 발송. 공개 배포 시 발송 서비스와 SPF·DKIM(배포 단계 항목) |
| 알림함만이라 대시보드를 열지 않으면 알림을 못 봄(D2) | 읽지 않은 수를 사이드바·탭 제목에 표시하고, 한계를 알림함 안내에 적음. 외부 채널은 §4-4 방식으로 나중에 붙임 |
| AI 비용 폭주(사용자가 늘어남) | 사용자별 하루 한도. 무료 0건. 운영 상태에 하루 사용량 표시 |
| 법·약관(명세 §5) | 유료 등급을 열기 전 확인. 코드로는 무료·단일 운영에서 문제가 없게 유지 |
| 범위가 커서 중간에 멈춤 | 단계마다 그 자체로 쓸모가 있게 끊음. A1만 해도 라이브 기록이 쌓이기 시작함 |
