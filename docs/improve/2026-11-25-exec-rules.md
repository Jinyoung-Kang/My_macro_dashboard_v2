# 개선 작업 규칙 (공통 규칙과 실행 세션 규칙)

이 파일은 어느 프로젝트에서나 그대로 쓰는 고정 규칙이야. 프로젝트마다 다른 값은 이 파일이
아니라 "프로젝트 사실" 파일에 있어. 이 파일의 문장은 고치거나 옮겨 적지 말고 파일째 복사해서 써.

이 개선 작업은 두 세션으로 나뉘어 있어.

- 계획 세션: 프로젝트를 파악해 무엇을 왜 어떻게 고칠지 계획서를 쓰고, 실행 세션이 이어받을
  문서를 만든다. 제품 코드는 고치지 않는다.
- 실행 세션: 사용자가 계획을 읽고 승인하면 새 세션에서 수정, 독립 검토, 최종 보고를 진행한다.

읽는 세션에 따라 따르는 범위가 달라.

- 계획 세션이면: 2장 "공통 규칙"을 지켜. 1장과 3장은 실행하지 말고, 실행 세션이 그 규칙대로
  일한다는 것을 알고 계획서를 써.
- 실행 세션이면: 이 파일 전체를 따라.


# 1장. 실행 세션의 역할과 읽는 순서

## 역할과 목표

너는 이 프로젝트를 넘겨받은 시니어 소프트웨어 엔지니어야. 계획은 이미 다른 세션에서 세워졌고
사용자가 그 계획을 읽고 승인했어. 이 세션은 승인된 계획을 실행하고, 독립 검토를 받고, 최종
보고를 쓰는 실행 세션이야. 너는 계획 세션의 대화를 볼 수 없어. 사용자가 보낸 프롬프트, 이 파일,
프로젝트 사실 파일, 계획서, 진행 기록이 네가 아는 전부야.

두 세션을 합친 목표는 이 코드를 실무 코드 리뷰를 통과하고, 다음 사람이 안전하게 고칠 수 있는
상태로 만드는 것이야. 코드를 많이 바꾸는 것이 목표가 아니야. 확인해 보니 고칠 이유가 없는
부분은 그대로 두고, 그대로 둔 이유를 적어.

이 작업 뒤에 별도의 QA 작업(출시 검증)이 이어져. 여기서는 코드 리뷰로 드러난 버그와 구조
문제를 다뤄. 부하 테스트, 전체 기능·화면 점검, 접근성 전수 점검 같은 출시 검증은 QA 작업에
맡기고, QA가 이어받을 정보를 최종 보고에 남겨.

## 읽는 순서

1. 사용자가 보낸 프롬프트: 문서 경로, 계획 기준 커밋, 승인 범위, 결정 사항 답변, 동결 영역,
   실행 재량
2. 이 파일
3. 프로젝트 사실 파일: 이 프로젝트의 스택, 실제 명령, 기준선, 따르는 프로젝트 규칙
4. 계획서와 진행 기록
5. 프롬프트에 보안 상세 파일이 적혀 있으면 그 파일

이 문서들은 아직 커밋되지 않은 파일일 수 있어. 네 작업 폴더에 문서가 없으면 프롬프트에 적힌
절대 경로에서 읽고, 네 작업 폴더의 같은 상대 경로로 복사해 와. 보안 상세 파일은 복사하지 말고
적힌 경로에서 읽고 써. 어느 경로에서도 읽을 수 없으면 멈추고 물어봐.

## 이 파일의 표현과 프로젝트 사실 파일

이 파일은 특정 언어, 프레임워크, 도구, 운영체제를 가정하지 않고 일반적인 표현으로 쓰여 있어.
그 표현이 이 프로젝트에서 무엇인지는 프로젝트 사실 파일의 대응표가 정해.

- "검증 수단(전체)": 이 프로젝트에 실제로 있는 테스트, 빌드, 린트·정적 분석, 타입 검사 명령 전부
- "커밋마다 돌릴 검증": 커밋할 때마다 통과시킬 명령. 따로 정해져 있지 않으면 검증 수단(전체)과
  같아.
- 대상 브랜치, 작업 브랜치 이름, 커밋 형식, 항목 번호 형식, 문서 위치, 상태 확인 명령
- 이 파일은 git 용어로 쓰여 있어. 다른 버전 관리 도구면 그 도구에서 같은 역할을 하는 개념에
  규칙을 적용해.
- 이 프로젝트에 해당하지 않는 규칙(예: 화면이 없는 프로젝트의 화면 관련 항목)은 프로젝트 사실
  파일에 적혀 있어. 그 규칙은 건너뛰어.

대응표에 없는 표현은 프로젝트에서 직접 확인하고, 확인한 값을 진행 기록에 적어.

프로젝트 사실 파일은 이 파일에 사실을 더하거나 규칙을 더 엄격하게 만들 수 있어. 규칙을 느슨하게
만들 수는 없어. 느슨하게 읽히는 내용이 있으면 이 파일을 따르고 진행 기록에 적어. 예외는 둘이야.
프로젝트 규칙 문서를 근거로 든 항목(2장 "규칙의 우선순위")과 프롬프트의 결정 사항 답변.


# 2장. 공통 규칙 (두 세션 모두 지킨다)

## 규칙의 우선순위

1. 프로젝트 규칙 문서(CLAUDE.md, AGENTS.md, CONTRIBUTING, README, docs 규약 등)
2. 이 파일
3. 사용자 전역 기본 규칙(여러 프로젝트에 공통으로 적용되는 개인 설정 문서)

- 프로젝트 규칙이 있으면 이 파일의 기본값보다 우선해(브랜치 이름, 커밋 형식, 검증 명령, 문서
  위치, 결함 번호, push·병합 절차). 충돌하면 프로젝트 규칙을 따르고 무엇을 따랐는지 기록에 적어
  (계획 세션은 계획서와 프로젝트 사실 파일, 실행 세션은 진행 기록).
- 다만 프로젝트 규칙이 아래 "안전 규칙"이나 3장 "멈추는 경우"가 막는 일(배포, 실제 외부
  리소스의 변경, 되돌릴 수 없는 작업 등)을 요구하면 그대로 하지 마. 계획 세션은 그 일을
  "내가 결정해야 하는 것"에 올리고, 실행 세션은 프롬프트의 결정 사항 답변에서 사용자가 명시적으로
  승인한 범위에서만 해.
- 사용자 전역 기본 규칙이 "요청할 때만 커밋한다", "계획을 먼저 보여 주고 승인 후 진행한다",
  "기록할지 묻는다"처럼 확인을 요구하는 경우, 실행 세션에서는 사용자가 보낸 프롬프트가 그
  요청이고 승인이야. 다시 묻지 말고 이 파일의 절차대로 진행해. 이 파일과 충돌하지 않는 전역
  규칙(답변 언어, 비밀값 처리 등)은 그대로 지켜.

## 이전 기록과 기록 방식

- 개선 문서 폴더(기본 docs/improve)와 QA 문서 폴더(기본 docs/qa)에 이전 회차 기록이 있으면
  먼저 읽어. 이전 보고서의 "남은 위험·다음 단계"와 그 뒤 바뀐 영역을 이번 회차의 출발점으로 삼아.
- 이전 회차 파일은 덮어쓰지 말고 날짜를 붙인 새 파일로 써. 같은 날짜의 파일이 이미 있으면
  -2처럼 번호를 붙여. 진행 기록(PROGRESS.md)과 항목 번호는 이어서 써.
- 기록에는 코드를 옮겨 적지 말고 파일:줄과 심볼 이름으로 가리켜. 진행 기록은 요약으로 유지해.
- 직접 실행해 확인한 것만 사실로 적어. 코드를 읽고 판단한 것은 추정이라고 표시해.

## 우선순위

1. 보안 결함과 데이터 손실·오염 위험
2. 기능 정확성 (버그)
3. 신뢰성 (오류 처리, 동시성, 외부 의존성 장애)
4. 구조 (계층, 모듈 경계, 테스트 가능성)
5. 성능 효율
6. 사용성 (UI/UX, 명령줄·API 사용 경험)

순위가 높은 문제가 남아 있는 동안 낮은 순위 작업에 시간을 쓰지 마.

## 바꿀지 판단하는 기준

다음 중 하나에 해당할 때만 코드를 바꿔.
- 버그나 보안 결함의 원인이다.
- 구조 때문에 테스트를 작성할 수 없다.
- 같은 수정을 여러 곳에 반복해야 하고, 실제로 서로 달라진 곳이 있다.
- 측정으로 확인된 병목이다.
- 사용자가 적은 "앞으로 예정된 변경"을 막는 구조다(프로젝트 사실 파일에 적혀 있다).

"더 깔끔해 보인다"는 이유만으로는 바꾸지 마. 기준에 해당하지 않지만 아쉬운 부분은
개선 제안으로만 기록해.

하지 않을 것
- 필요가 입증되지 않은 새 인프라(마이크로서비스, 메시지 브로커 등)
- 구현이 하나뿐인 인터페이스 같은 과한 추상화 계층
- 작은 중복까지 모두 추상화하기

## 안전 규칙

- 작업과 테스트는 로컬이나 테스트 환경에서만 해. 운영 데이터와 실제 계정은 쓰지 마.
- 테스트·스크립트가 붙는 DB, 포트, 컨테이너, 볼륨, 파일 경로, 장치가 운영 것과 겹치지
  않는지 실행 전에 확인해. 같은 머신에 다른 프로젝트의 스택이 돌고 있을 수 있어.
- 실제 클라우드·외부 서비스의 리소스는 조회만 해. 생성, 변경, 삭제, 배포는 하지 마.
- 호출 한도나 비용이 있는 외부 API와 외부 AI 모델 호출은 저장된 응답이나 목(mock)으로 대체해.
- 실제 외부(운영 DB, 한도·비용이 있는 API, 외부 AI 모델, 실제 계정)를 부르는 테스트는
  돌리지 마. 프로젝트 사실 파일에 제외 목록과 제외하는 명령이 있으면 그대로 써.
- 작업 환경에만 설치하는 도구는 이유를 적고 진행해. 프로젝트 의존성에 추가해야 하면
  승인 대기로 넘겨(계획 세션은 "내가 결정해야 하는 것"에 올려).
- 비밀값을 발견하면 문서, 로그, 커밋에 원문을 남기지 말고 위치와 종류만 적어.

## 보안 발견을 적는 곳

고쳐지지 않은 취약점의 위치와 재현 방법이 공개 저장소에 올라가면 그것만으로 위험이야.

- 저장소가 비공개라고 확인된 경우, 또는 사용자가 커밋해도 된다고 적은 경우에만 보안 항목의
  상세를 커밋 대상 문서(계획서, 진행 기록, 보고서)에 적어.
- 그 밖에는(공개 저장소, 공개 여부를 확인하지 못한 경우, 원격 저장소가 없는 경우) 보안 항목의
  상세(위치, 재현 방법, 수정 방법)를 보안 상세 파일에만 적어. 커밋 대상 문서에는 번호, 심각도,
  취약 지점을 특정하지 않는 제목만 적고 "상세는 보안 상세 파일"이라고 가리켜.
- 보안 상세 파일은 커밋하지 마. 파일 위치와 버전 관리에서 제외한 방법은 프로젝트 사실 파일에
  적혀 있어.
- 이번 회차에 고친 보안 항목은 최종 보고서에 평소처럼 적어도 돼(수정과 함께 올라가니까).
  고치지 못했거나 이번 회차에 다루지 않은 보안 항목은 계속 보안 상세 파일에만 둬.
- 커밋 메시지에도 고쳐지지 않은 취약점의 상세를 적지 마.

## 심각도 기준

- S1 치명: 인증 없이 또는 타인 권한으로 데이터에 접근·변경 가능, 데이터 손실·오염,
  원격 코드 실행, 비밀값 노출, 서비스(프로그램) 전체 중단
- S2 높음: 핵심 기능이 동작하지 않고 우회 방법이 없음, 특정 조건에서 데이터 불일치,
  악용 조건이 제한적인 보안 결함
- S3 보통: 기능이 잘못 동작하지만 우회 가능, 변경할 때마다 버그를 만드는 구조 문제,
  측정된 성능 저하
- S4 낮음: 표시·문구 오류, 가독성, 사용에 지장이 없는 불편


# 3장. 실행 세션 규칙

## 시작 절차

- 프롬프트에 적힌 값(문서 경로, 계획 기준 커밋, 승인 범위, 결정 사항 답변, 동결 영역,
  실행 재량)을 읽어.
- 프로젝트 사실 파일, 계획서, 진행 기록을 끝까지 읽어. 읽을 수 없으면 멈추고 물어봐.
- 진행 기록에 이번 회차의 실행 기록이 이미 있고 작업 브랜치가 있으면 중단된 작업을 이어가는
  것이야. 아래 "중단된 작업 이어가기"를 따르고, 이 절의 나머지는 건너뛰어.
- 상태 확인 명령으로 작업 폴더를 확인해. 계획 세션이 만든 문서가 커밋되지 않은 채 있는 것은
  정상이야. 그 밖에 추적되는 파일에 커밋되지 않은 변경이 있으면 멈추고 물어봐.
- 현재 코드가 계획 기준 커밋과 같은지 확인해. 달라졌으면 바뀐 파일이 승인된 항목과
  겹치는지 보고, 겹치는 항목은 위치와 근거를 다시 확인해.
- 검증 수단(전체)을 실행해 프로젝트 사실 파일의 기준선과 같은지 확인해. 다르면 원인을 찾아
  진행 기록에 적고, 설명되지 않으면 멈추고 물어봐. 불안정하다고 적힌 테스트만 다르면 그
  테스트를 다시 돌려 확인하고 진행해.
- 작업 브랜치를 만들어(프로젝트 규칙의 이름. 규칙이 없으면 대상 브랜치에서 improve/YYYYMMDD).
  계획 세션이 만든 문서(계획서, 진행 기록, 이 파일의 사본, 프로젝트 사실 파일, 실행 프롬프트
  파일)를 첫 커밋으로 넣어. 보안 상세 파일은 넣지 마. 문서 폴더가 버전 관리 제외 대상이라고
  프로젝트 사실 파일에 적혀 있으면 문서를 커밋하지 말고 그 사실을 진행 기록에 적어.

### 중단된 작업 이어가기

- 작업 브랜치를 새로 만들지 말고 기존 작업 브랜치에서 이어가.
- 진행 기록의 마지막 상태를 작업 브랜치의 커밋 기록과 대조해. 서로 다르면 커밋 기록을 사실로
  보고 진행 기록을 바로잡아.
- 커밋되지 않은 변경이 있으면 어느 항목의 작업인지 확인해. 설명되면 그 항목부터 다시 검증하고
  이어가. 설명되지 않으면 멈추고 물어봐.
- 검증 수단(전체)을 실행해 지금 상태를 확인한 뒤 다음 항목으로 넘어가.

## 승인 범위

- 프롬프트의 "승인 범위"에 든 항목만 수정해. 비어 있으면 계획서의 "이번 회차 제안 범위"
  전체가 승인된 것이야. 프롬프트를 받은 것이 승인이니, "멈추는 경우"에 해당하지 않는 한
  끝까지 진행해.
- 계획서의 "내가 결정해야 하는 것" 중 프롬프트에 답이 없는 항목은 계획서에 적힌
  "답이 없을 때의 행동"을 따라. 그 행동이 "하지 않음"이면 그 결정에 의존하는 항목은 건너뛰고
  승인 대기에 적어.
- 계획서는 출발점이지 확인된 사실이 아니야. 항목을 고치기 전에 직접 재현하거나 코드를
  확인해. 위치만 다르고 문제가 같으면 실제 위치에서 고치고 차이를 진행 기록에 적어.
  문제가 재현되지 않거나 원인이 다르면 고치지 말고 이유를 적은 뒤 다음 항목으로 넘어가.
- 작업 중 새로 찾은 문제는 승인된 항목과 같은 원인이면 함께 처리해. 그 밖은 진행 기록의
  "새 발견"에 심각도와 함께 적고 고치지 마.

## 반드시 지킬 것과 판단에 맡기는 것

반드시 지킬 것 (예외 없음)
- 2장의 "안전 규칙"과 "보안 발견을 적는 곳", 이 장의 "작업 규칙"과 "멈추는 경우", 동결 영역,
  승인 범위. 동결 영역의 파일·기능은 문제를 찾아도 고치지 말고 수정안만 적어.
- 직접 실행해 확인한 것만 사실로 보고하기

네 판단에 맡기는 것
- 승인 범위 안에서 진행 순서와 커밋 크기, 구현 세부
- 계획서의 수정 방법보다 나은 방법을 찾았을 때: 고치는 범위와 밖에서 보이는 동작이 계획과
  같으면 그 방법으로 진행하고 이유를 진행 기록에 적어. 달라지면 승인 대기로 넘겨.

프롬프트의 실행 재량이 "좁게"면 판단에 맡기는 범위가 아래처럼 줄어.
- 계획서의 수정 방법을 그대로 따라. 더 나은 방법을 찾았어도 바꾸지 말고, 그 방법과 이유를
  승인 대기에 적어.
- 계획서의 방법이 적힌 그대로는 동작하지 않으면 같은 설계 안에서 세부를 맞추는 것까지는 해.
  설계가 달라져야 하면 승인 대기로 넘겨.
- 계획서가 "실행 세션이 판단할 것"이라고 표시한 지점에서 적힌 판단 기준만으로 결론이 나지
  않으면 추측으로 정하지 말고 그 항목을 승인 대기로 넘겨.
- 진행 순서는 계획서에 적힌 순서를 따라.

## 진행 순서

### 실행
"작업 규칙"대로, 2장의 우선순위와 계획서의 진행 순서에 따라 진행해.
진행 상황은 진행 기록(PROGRESS.md)에 계속 갱신해. 작업이 중단되거나 앞의 맥락을 잃어도
이 파일만 읽고 이어갈 수 있게 써.

### 독립 검토
별도 에이전트에게 전체 변경(diff), 계획서, 완료 기준만 넘기고, 네 작업 과정은 넘기지 마.
보안 항목을 고쳤으면 보안 상세 파일도 함께 넘겨. 확인할 것은 다음과 같아.
- 정확성이나 요구사항에 영향을 주는 문제가 있는가
- 계획에 없는 동작 변경이 섞여 있는가
- 테스트가 변경을 실제로 검증하는가

검토에서 나온 지적은 네가 코드나 실행으로 직접 확인한 뒤에 반영해. 확인되지 않는 지적은
반영하지 말고 이유를 진행 기록에 적어. 정확성이나 요구사항에 영향을 주는 문제만 고쳐.
취향 수준의 지적은 반영하지 마. 반영한 뒤에는 검증 수단(전체)을 다시 실행해.
별도 에이전트를 쓸 수 없으면 처음 보는 리뷰어 입장에서 직접 재검토하고, 그렇게 했다고 밝혀.

### 최종 보고
"최종 보고" 형식대로 정리해.

## 작업 규칙

버그 수정
- 실패하는 테스트로 먼저 재현해. 그 테스트가 고치려는 버그 때문에 실패하는지(오타, 설정,
  환경 문제로 실패하는 것이 아닌지) 실패 출력에서 확인해.
- 증상을 가리지 말고 근본 원인을 고쳐. 테스트로 재현할 수 없는 종류면 계획서에 적힌 대체
  확인 방법으로 재현하고 그 출력을 남겨.
- 테스트와 수정은 프로젝트 규칙이 정한 커밋 단위로 넣어(규칙이 없으면 한 커밋).
  수정 전 실패 출력은 커밋 메시지나 진행 기록에 남겨.
- 같은 원인이 다른 위치에도 있는지 검색해 함께 처리해.

리팩터링
- 테스트가 없는 코드는 현재 동작을 고정하는 테스트부터 추가해.
- 밖에서 보이는 동작(공개 API와 함수 시그니처, 명령줄 인터페이스, URL, 화면 동작,
  파일·메시지 형식, 저장 스키마)은 바꾸지 마.

커밋과 검증
- 한 가지 주제씩 작게 커밋하고, 리팩터링과 버그 수정은 한 커밋에 섞지 마.
- 커밋마다 "커밋마다 돌릴 검증"을 통과시켜. 그 검증에는 그 커밋이 건드린 코드의 테스트가
  들어 있어야 해. 들어 있지 않으면 그 테스트를 더해서 돌려.
- 계획서의 묶음 하나가 끝날 때, 독립 검토 전, 최종 보고 전에는 검증 수단(전체)을 통과시켜.
- 기준선에서 이미 실패하던 항목은 더 나빠지지 않게 해.
- 불안정하다고 적힌 테스트가 실패하면 그 테스트만 다시 돌려 봐(두 번까지). 통과하면 진행
  기록에 적고 진행해. 목록에 없는 테스트가 돌릴 때마다 결과가 달라지면 계획 기준 커밋에서도
  그런지 확인하고, 네 변경이 원인이 아니면 "새 발견"에 적고 진행해.
- 기존 테스트를 삭제하거나 건너뛰게 하거나 기대값을 느슨하게 바꿔 통과시키지 마. 기존 테스트가
  버그인 동작을 기대하고 있어서 기대값이 바뀌어야 하면, 계획서의 그 항목에 그 변경이 적혀 있을
  때만 바꾸고 커밋 메시지에 이유를 적어. 적혀 있지 않으면 승인 대기로 넘겨.
- 변경 때문에 사실과 달라지는 문서(README, API 문서, 설정 예시 파일, 주석)는 같은 커밋에서
  고쳐. 새 환경 변수는 설정 예시 파일에 이름만 추가하고 값은 넣지 마.
- 전체 파일 포맷 정리처럼 diff를 키우는 변경은 하지 마.
- 원격 push와 대상 브랜치 병합은 프로젝트 규칙이 정한 절차가 있을 때만 그 절차대로 해.
  없으면 하지 마. 그건 사용자가 해.

막혔을 때
- 한 항목에서 서로 다른 수정 시도가 세 번 이어서 검증을 통과하지 못하면 그 항목을 멈춰.
- 그 항목의 커밋되지 않은 변경은 버려. 이미 커밋한 것이 있으면 되돌리는 커밋으로 원래 상태로
  돌려(이력을 다시 쓰지 마).
- 시도한 방법, 마지막 실패 출력, 추정 원인을 진행 기록에 적고 그 항목을 "미해결"로 표시해.
  그 항목에 의존하는 항목은 건너뛰고 이유를 적어. 그 다음 항목으로 넘어가.
- 통과시키려고 테스트를 느슨하게 하거나 검증을 건너뛰지 마.

성능
- 추측으로 고치지 말고 변경 전후를 같은 조건에서 측정한 수치로 판단해.
- 측정 조건(실행 환경, 데이터 건수, 반복 횟수)을 수치와 함께 적어.
- 차이가 측정되지 않으면 변경을 되돌려.

의존성
- 버전은 기억이 아니라 그 생태계의 공식 패키지 저장소나 공식 릴리스 페이지에서 정식
  릴리스를 확인해.
- 패치·마이너 업데이트는 검증 수단(전체)이 통과하면 진행해.
- 메이저 업그레이드는 프롬프트에서 승인된 것만 진행해. 그 밖은 영향 범위를 정리해
  승인 대기로 넘겨.

## 멈추는 경우

즉시 멈추고 물어봐.
- 데이터 삭제, 기존 데이터를 바꾸는 마이그레이션, 버전 관리 이력 재작성이나 강제 푸시처럼
  되돌릴 수 없는 작업이 필요할 때
- 공개 API, URL, 파일 형식 같은 공개 인터페이스의 하위 호환을 깨거나 기능을 없애야 할 때.
  계획서의 승인된 항목이 "밖에서 보이는 동작 변화"로 적어 둔 변경과 프롬프트의 결정 사항
  답변으로 승인된 변경은 적힌 범위 안에서 진행해. 거기에 없는 변경이 필요해지면 멈춰.
- 유료 서비스나 새 인프라를 추가해야 할 때
- 비밀값, 계정, 환경 변수처럼 사용자가 직접 넣어야 하는 값이 없어 더 진행할 수 없을 때
- 프로젝트 사실 파일, 계획서, 진행 기록을 읽을 수 없거나, 기준선이 프로젝트 사실 파일과 다른데
  이유를 설명할 수 없을 때
- 시작할 때나 이어갈 때, 추적되는 파일에 설명되지 않는 커밋되지 않은 변경이 있을 때

프롬프트의 "결정 사항 답변"에서 사용자가 이미 답한 것은 그 답의 범위 안에서 진행하고,
범위를 넘으면 멈춰.

멈추지 말고 모아 뒀다가 물어봐.
- 버그인지 의도된 동작인지 코드만으로 판단하기 어려울 때
- 동결 영역에서 찾은 문제의 수정안
- 메이저 업그레이드처럼 승인이 필요한 변경
- 승인 범위 밖에서 새로 찾은 문제
- "막혔을 때"에 따라 미해결로 남긴 항목
이 항목들은 진행 기록의 승인 대기에 쌓고 다른 작업을 계속해. 남은 작업이 이것뿐이면 한 번에
물어봐.

S1 문제는 발견 즉시 알리고 이어서 진행해.

## 완료 기준

- 미해결 S1·S2가 없거나, 남은 항목이 승인 대기로 정리되어 있다.
- 검증 수단(전체)이 통과한다(기준선에서 이미 실패하던 항목은 따로 표시).
- 의도하지 않은 동작 변경이 없다.
- 커밋만 읽고도 무엇을 왜 바꿨는지 알 수 있다.
- 독립 검토에서 나온 정확성 문제가 모두 처리되었다.
- 변경으로 사실과 달라진 문서가 남아 있지 않다.

## 최종 보고

개선 문서 폴더(기본 docs/improve)에 날짜를 붙인 보고서로 작성하고, 대화에는 요약을 보여 줘.
미해결로 남은 S1·S2가 있으면 보고서와 요약의 맨 위에 적어.

- 변경 내용과 이유 (커밋 묶음별)
- 검증 증거: 실행한 명령과 결과, 기준선 대비 테스트 수, 성능 전후 수치와 측정 조건
- 의도적으로 바꾼 동작 목록 (버그 수정으로 달라진 응답, 화면 동작, 출력)
- 계획서와 달랐던 것: 고치지 않은 항목과 이유, 다른 방법으로 고친 항목
- 하지 않은 것과 이유, 승인 대기 항목, 미해결 항목
- 배포할 때 필요한 조치: 마이그레이션, 새로 생기거나 바뀐 환경 변수, 설정 변경, 적용 순서,
  문제가 생겼을 때 되돌리는 방법. 없으면 "없음"이라고 적어.
- 사용자가 직접 할 일: 계획서의 "내가 직접 할 일" 가운데 아직 남은 것과 작업 중 새로 생긴 것
  (키 폐기·재발급, 이미 잘못 저장된 데이터의 보정, 외부 서비스 설정 등)
- 남은 위험과 다음 단계 (다음 회차의 출발점이 되도록)
