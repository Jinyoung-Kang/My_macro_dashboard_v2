**하는 것** — `scripts/vultr/restore-check.sh`
- 주 1회(권장 토요일 09:30 KST — 08:00 정기 백업 뒤, 두 시장 모두 닫힘, 다른 cron과 겹치지 않음) `.last-s3-ok`가 가리키는 S3 객체를 받아 **운영과 완전히 떨어진 일회용 postgres 컨테이너**에 적재합니다. 컨테이너는 망 없음 · 포트 게시 없음 · 메모리 768MB · CPU 1 · 끝나면 익명 볼륨까지 지움입니다. 운영 DB `macrodash`와 그 볼륨에는 쓰지 않습니다.

- `make status`와 배포 끝 요약에 '마지막 복원 확인 N일 전'(9일 넘거나 없으면 경고 — cron이 빠진 경우를 잡는 유일한 신호).

## 4. P3 — 서버 디스크 관리

**지금 상태(2026-11-27)**
- 디스크 120GB 가운데 87GB 사용(77%). Docker 빌드 캐시 61GB, 그 가운데 56.8GB가 회수 가능합니다. 문서에 남은 값으로는 11-22에 41GB였습니다.
- `deploy.sh`는 성공한 배포의 끝에서 `docker image prune -f`와 `docker builder prune -f --filter until=168h`만 합니다(`deploy.sh:292-293`, 재확인). 배포가 하루에도 여러 번이라 일주일 안의 캐시가 쌓입니다.
- 그 두 줄은 `set -euo pipefail`(`deploy.sh:35`) 아래에 있고 `||`가 없습니다(재확인). 정리 명령이 실패하면 컨테이너는 이미 새로 떴는데 성공 문구 없이 0이 아닌 값으로 끝납니다. 성공한 배포의 정리 인자를 단언하는 시험도 없습니다.
- 디스크 사용률을 읽는 자리는 배포 끝 요약 한 줄뿐이고(`deploy.sh:299`), 문턱이나 알림은 없습니다.
- 로컬 Docker 29.9.3의 도움말에는 `--max-used-space`·`--reserved-space`·`--min-free-space`가 있습니다(재확인). 서버 29.10.0에서는 확인 못 함.

**하는 것**
- (가) 배포 끝 정리를 크기 상한으로: `docker builder prune -f --max-used-space <상한>`(권장 15GB, `BUILD_CACHE_MAX`로 바꿈). 실패하면 지금의 나이 기준으로 물러나고, 정리 실패가 배포 결과를 바꾸지 않게 '경고'만 찍습니다. 인자를 단언하는 시험을 더합니다.
- (나) `scripts/vultr/disk-check.sh`: 디스크와 inode 사용률이 80% 이상이면 '경고', 90% 이상이면 '위험'으로 운영 봇에 하루 한 번. 이미 매일 도는 `reboot-check.sh`의 cron 길에서 부릅니다(새 cron 줄이 필요 없어 다음 배포부터 돎). `--summary`가 배포 요약과 `make status`의 디스크 줄이 됩니다.
- (다) 쌓인 캐시를 한 번 치우기 — 서버에서 손으로, 사용자 승인 뒤.
  1. 읽기만: `docker builder prune --help`에 `--max-used-space`가 있는지, `docker system df`, `df -h /`, `df -i /`.
  2. 평일 16:00~22:00 KST나 주말 낮, 배포가 돌지 않을 때: `docker builder prune -f --max-used-space 15GB`(약 46GB 회수 예상 — 추정).
  3. 확인: `docker system df`, `df -h /`(77% → 약 40% 예상), `docker compose ps`.

**(다)를 코드보다 먼저 하는 이유**: 새 `deploy.sh`가 올라간 첫 배포는 끝에서 약 46GB를 한꺼번에 지웁니다. 그 순간의 디스크 IO와 '서버 판이 그 옵션을 받는가'를 배포 중에 처음 겪지 않으려는 것입니다.

**15GB의 근거**: 회수할 수 없는 바닥이 4.2GB(61 − 56.8)이고, 빌드 단계의 층을 더한 한 세대가 7~8GB(추정)이며, 빌드 중에는 옛 세대와 새 세대가 함께 있습니다. (다) 뒤 첫 배포 끝의 캐시 크기로 보정합니다.

**하지 않는 것**: 볼륨·쓰는 이미지·`backups/` 삭제, `docker system prune`류, dockerd 설정 변경(재시작이 컨테이너를 모두 다시 띄움), 덤프 압축, 메모리 알림.

**남는 한계**: 상한이 한 세대보다 작으면 의존성 층이 밀려 그 배포 한 번이 캐시 없는 속도가 됩니다(7~10분 추정, 평소 2분 안팎). 알림은 하루 한 번이고 reboot-check cron이 빠지면 함께 빠집니다. `backups/`는 덤프가 커지는 만큼 계속 늘어납니다(알림이 잡는 범위).

## 5. P4 — 실제 계좌 기록의 정합성

### P4-가 — ISA 매매 적기의 중복 방지

**지금 상태**
- ISA 쓰기 경로는 POST 11개이고 모두 계좌 행을 잠근 한 트랜잭션 안에서 돕니다. 같은 요청을 두 번 받았을 때 10개는 이미 안전합니다(상태 검사 · 절대값 쓰기 · 유일 색인).
- **`POST /api/manual/isa/trades`(지시 없는 매매 적기)만 두 번 들어갑니다** — 내역 두 줄, 현금과 보유에 두 번 반영. `manual_trades`의 유일 색인은 지시 번호가 있는 줄에만 걸려 있습니다(`db/migrations/V31__manual_balance.sql:55-56`, 재확인).
- 화면의 ISA 쓰기 11개는 시간 한도 없이 보냅니다(`frontend/src/components/screens/isa/isaRequests.ts`, 재확인). 응답이 안 오면 단추가 '반영하는 중…'에 묶여, 사용자가 새로 고친 뒤 다시 적게 됩니다.

**하는 것**
- `manual_trades`에 NULL 허용 열쇠 칸과 `(account, 열쇠)` 부분 유일 색인(새 마이그레이션 — 칸과 색인을 더하기만).
- 요청 본문에 선택 칸 `requestId`. 서버는 잠금 안에서 그 열쇠의 줄을 먼저 찾아, 있으면 쓰지 않고 첫 결과에 `replayed: true`를 붙여 돌려줍니다. 열쇠가 없는 요청(옛 화면)과 옛 줄은 지금과 같습니다.
- 화면: 창을 열 때 열쇠를 만들고, 본문이 바뀌면 새로 만들고, 성공하면 버립니다. ISA 쓰기 11개에 시간 한도(권장 20초)를 두고, 시간이 넘으면 계좌를 다시 읽고 "처리됐을 수 있습니다 — 매매 내역을 확인하세요"를 보입니다.
- 새 칸은 ISA 전체의 '준비됨' 판정에 넣지 않습니다(넣으면 새 백엔드가 옛 스키마를 만난 동안 ISA 전체가 '준비 중'이 됨). 칸이 없으면 열쇠를 무시합니다.

**하지 않는 것**: 나머지 10개 경로의 열쇠, 자동 다시 보내기, 새 API 경로.

**검증**: 서비스 DB 시험(같은 열쇠 두 번 · 다른 열쇠 · 열쇠 없음 · 되돌린 뒤 같은 열쇠 · 모양이 틀린 열쇠), 통합 시험 한 건, 화면 시험(시간 초과 → 안내와 다시 읽기, 다시 누르면 같은 열쇠, 본문을 고치면 새 열쇠). 완료 기준은 기존 `recordTrade*` 시험 넷의 기대값이 그대로인 것입니다.

**남는 한계**: 새로 고친 뒤 다시 적으면 열쇠가 달라 막지 못합니다(화면이 '방금 같은 매매가 내역에 있음' 경고만 보임). 되돌린 뒤 옛 탭이 같은 열쇠로 다시 보내면 다시 적힙니다. 시간 한도 20초는 서버 쪽이 DB 읽기·쓰기뿐이라는 전제입니다(추정).

### P4-나 — 줄여 낸 매수의 나머지 (설계 선택지)

**지금 상태**
- 현금이 모자라 줄여 낸 매수는 건너뜀도 표시도 남기지 않습니다(`RealTradePlanner.java:648-656`, 재확인). 줄이기 전 수량은 어느 표에도 없습니다.
- 종목·용도마다 시도는 둘까지이고, 시도 1이 전량 체결되면 그날 나머지를 살 길이 없습니다. 6차 후속(2026-11-27 배포)은 마무리 계획에서 매도가 함께 있으면 줄일 매수를 미루게만 했습니다.
- 다음 거래일의 묶음이 목표와 보유의 차이를 다시 세므로, 차이가 1주 이상이고 순자산의 1% 이상이면 다시 삽니다(`RealTradePlanner.java:386`, 재확인). 1% 미만의 잔여는 남습니다.

**선택지**

| | A. 같은 날 이어 사기 | B. 다음 거래일에 맡김 | C. 주문은 그대로, 보이기만 |
|---|---|---|---|
| 주문 동작 | 줄여 낸 마무리 매수가 끝나면 같은 창에서 나머지를 시도 2로 한 번 | 없음 | 없음 |
| 필요한 것 | 주문 행에 '줄이기 전 수량' 칸(스키마), 시도 규칙 변경 | 문서에 명시 | 계획 출력에 줄임 목록, 창 요약에 건수와 순자산 대비 부족 % |
| 회전율 예외 | 넓히지 않음(그 묶음이 이미 센 금액 안) | 그대로 | 그대로 |
| 기대값이 바뀌는 기존 시험 | 있음(확실 1건, 추정 5~6건) | 없음 | 없음(추정) |

**권장: C를 지금, A는 2026-12-09 무렵 재선정 다음 묶음을 본 뒤 따로 승인.**
- 6차 후속의 '미룸'이 운영에서 아직 한 번도 보이지 않았습니다. 실제 돈의 동작 변경을 겹치면 어느 쪽 효과인지 가를 수 없습니다.
- 다음 거래일 묶음이 1% 이상의 잔여를 채웁니다.
- A는 종목마다 하나뿐인 재시도 자리를 씁니다. 이어 산 주문이 지나가는 거절을 받으면 그날은 끝입니다.
- C가 남기는 '줄임' 건수와 부족 %가 A를 할지 정할 근거가 됩니다.

**C의 주의**: 줄임을 기존 건너뜀 목록에 새 사유로 넣으면 안 됩니다. 같은 계획 함수를 ISA 지시와 켜기 창 예상 목록이 쓰고, 정기 작업이 그 목록으로 남은 몫과 대기 여부를 판정합니다. 계획 결과에 칸을 따로 더합니다. 창 요약과 알림에는 건수와 %만 싣고 종목·수량·금액은 싣지 않습니다.

**어느 쪽이든 남는 것**: 순자산의 1% 미만 잔여, 매도가 창 끝까지 끝나지 않는 날, 대금 반영 시점의 순서. 토스의 실제 응답으로는 아무것도 확인하지 못했습니다.

## 6. P5 — 옛 이미지가 새 마이그레이션을 적용하지 못하게

**지금 상태**
- 수집기 이미지에는 마이그레이션이 없습니다. 호스트의 `db/migrations`를 읽기 전용으로 마운트하고(`docker-compose.yml`의 수집기 `volumes`, 재확인), 수집기가 기동할 때 기록에 없는 번호를 적용합니다.
- 그래서 코드를 받은 뒤 새 컨테이너가 뜨기 전에 옛 수집기 컨테이너가 다시 뜨면 **옛 코드가 새 스키마를 적용합니다.** 빌드 실패, 가드에서 멈춤, 덤프 실패, 재부팅, 메모리 상한 뒤 자동 재시작이 모두 그 길이고, 정상 배포의 빌드 몇 분도 같은 창입니다. 6차의 QA-1015는 실제 매매 창 안에서 받기 전에 멈추게만 했습니다.
- 로컬도 같습니다. 본체 폴더에서 새 마이그레이션이 든 브랜치를 체크아웃한 채 수집기가 다시 뜨면 로컬 DB에 적용됩니다.

**선택지와 권장**

| | 1. 상한 번호를 이미지에 새김 | 2. 폴더를 이미지에 넣고 마운트 제거 | 3. 적용기를 따로 뗌 |
|---|---|---|---|
| 보장 | 번호만 봄 | 이미지가 아는 파일 = 적용하는 파일 | 2와 같음 |
| 약한 곳 | 모든 빌드 길이 인자를 넘겨야 함 | compose의 `additional_contexts` 지원(로컬 v5.7.1, 서버는 확인 못 함) | 배포·복원·QA 순서를 모두 바꿈, ADR 0008 결정 변경 |

**권장 2.** 부르는 쪽이 지킬 약속이 없고 내용으로 고정됩니다. 스키마 파일은 여전히 `db/migrations` 한 곳이고 수집기가 기동 때 적용하므로 ADR 0008의 뜻은 그대로입니다(덧붙임만). 서버 compose가 그 옵션을 받지 못하면 1로 물러납니다.

**DB가 이미지보다 앞서 있을 때**(되돌림 배포): 경고 로그를 남기고 기동은 계속합니다. 이미지의 최대 번호와 DB의 최대 번호를 `/status`에 실어 `make doctor`와 배포 요약이 보게 합니다. 멈추면 자동 재시작과 겹쳐 재기동 반복이 되고, 수집과 실제 매매 주문 길(수집기 전용 세션)이 함께 섭니다.

**검증**: 정적 시험(수집기 서비스에 그 마운트가 없고 Dockerfile이 이름 붙은 컨텍스트에서 복사), 'DB가 앞섬' 경고 시험, CI의 이미지 빌드 job에 '이미지 안 파일 수 = 저장소 파일 수'. QA 스택에서 손으로: 이미지를 빌드한 뒤 작업 폴더에 임시 높은 번호 파일을 두고 수집기만 다시 시작해 기록의 최댓값이 그대로인지 봅니다.

**배포할 때**: 이 변경을 처음 배포하는 한 번은 옛 위험이 그대로입니다(돌던 컨테이너는 만들 때의 마운트를 유지). 그래서 새 마이그레이션 없이, P4-가보다 먼저 배포합니다. 배포 전에 서버에서 `docker compose version`을 확인합니다.

**남는 한계**: 마이그레이션만 고쳐도 수집기 이미지를 다시 빌드해야 적용됩니다. 옛 백엔드와 새 스키마가 함께 있는 순간(`up`이 두 컨테이너를 바꾸는 사이)은 그대로입니다.

## 7. P6 — 시험 체계

### (가) 흔들리는 시험

**지금 상태**
- 화면: vitest 설정에 한도가 없어 기본값(시험 5초)이고(`frontend/vitest.config.mts`, 재확인), 일꾼 수 기본이 CPU − 1이라 이 PC에서는 11입니다. 흔들린 화면 파일들은 모두 기본 한도이고 가짜 시계도 실제 sleep도 없습니다. `noEmoji`는 대기가 아니라 `src` 전체를 파싱하는 CPU 일입니다.
- 수집기: `test_sidecar_request_cap.py:403`의 `elapsed < cap + cleanup / 2`(재확인)는 정리 시간에 프로세스 찾기·끝내기 시간이 더해지는 구조라 부하에 약합니다. inventory 시험이 어느 단언에서 왜 실패했는지는 기록이 없습니다.
- 여러 벌을 함께 돌린 실측: 넷은 로컬 postgres가 죽었고, 셋 + 일회용 DB는 흔들렸고, 둘 + 일회용 DB는 10번 모두 통과했습니다.

**하는 것 — 먼저 분류하고 종류마다 다르게**
0. 부하를 걸고 그 파일들만 여러 번 돌려 실패 문구를 모읍니다. 한도를 10배로 올려도 실패하면 진짜 경합이므로 결함 절차로 보냅니다.
1. 한도가 고장 감시일 뿐인 조건 대기(화면): 전역 한 곳에서 올립니다(권장 시험 20초 · 조건 대기 5초 — 저장소의 두 파일이 이미 쓰는 값). 조건이 맞으면 바로 통과하므로 통과 시간과 단언은 그대로입니다.
2. 실제 시계가 단언에 든 것(수집기): 시간이 아니라 '2단계 정리 함수가 불리지 않았다'는 관찰로 바꿉니다. 재현 시험은 프로세스 찾기에 지연을 넣어 부하를 흉내 냅니다.
3. CPU 일(`noEmoji`): 원문에 그림 문자가 하나도 없는 파일은 파싱을 건너뜁니다(결과가 같음).
4. inventory 시험: 원인을 재현한 뒤 분류합니다. 그 전에는 고치지 않습니다.

**완료 기준**: 고치기 전후로 같은 부하(세 벌 동시)에서 그 파일들을 20회씩 돌려, 수정 뒤 실패 0건이고 혼자 돌린 전체 시간이 ±5% 안.

**기대값이 바뀌는 기존 시험**: `test_sidecar_request_cap.py`의 상한 단언 교체, 조건 대기를 500ms로 줄여 둔 27줄(8파일)과 개별 한도 설정 2파일의 정리. 승인 대상입니다(D-12).

### (나) 격리 실행

- `scripts/test-isolated.sh`와 `make test-isolated`. 칸마다 일회용 postgres 컨테이너를 띄우고(다른 compose 프로젝트 · 루프백 포트 · 메모리 상한 없음 · `fsync=off`), 끝나거나 중단되면 볼륨까지 지웁니다. `.env`를 읽지 않고 프로젝트 이름과 compose 파일을 명시해 떠 있는 로컬 스택을 건드리지 않습니다.
- 동시 실행은 잠금으로 최대 2칸(실측 근거). 칸마다 yfinance 캐시 폴더와 화면 시험의 일꾼 수를 나눕니다.
- `make test`의 뜻은 바꾸지 않습니다.
- 검증: 가짜 docker·make로 인자·환경·정리를 보는 시험, 로컬에서 두 벌 동시 실행, 끝난 뒤 컨테이너·볼륨 흔적 없음, 도중에 끊어도 지워짐.

### (다) 시험 없는 자리 목록

- 문턱값으로 막는 용도가 아닙니다. `make coverage`가 세 묶음의 커버리지 보고서를 합쳐 '파일 · 안 지난 줄 범위'를 큰 순서로 내고, 선을 못 보는 자리(API 모듈을 통째로 목으로 둔 화면 시험 267파일, 시험 파일이 없는 훅)는 정적 목록으로 함께 냅니다.
- 백엔드는 pom을 고치지 않고 JaCoCo를 명령줄 좌표로 돌립니다. 화면은 개발 의존성 `@vitest/coverage-v8`(vitest와 같은 판, 운영 이미지에는 들어가지 않음)이, 수집기는 `coverage`가 필요합니다. GA 판은 구현할 때 공식 저장소에서 확인합니다.
- 로컬 명령으로만 두고 CI에는 넣지 않습니다.
- 확인 못 함: JaCoCo 0.8.16과 JDK 25의 조합(안 되면 CLAUDE.md의 JDK 21 컨테이너 절차로).

## 10. 하지 않기로 한 것

- 실제 주문의 쓰기 경로 추가, 회전율 임계값·예외 범위 변경(P4-나의 A도 승인 전에는 하지 않음).
- 커버리지 문턱값으로 CI를 막는 것, 백엔드 시험의 병렬화, `make test`의 뜻 바꾸기.
- 덤프 형식 변경(압축), dockerd 설정 변경, 메모리 알림, 백엔드의 스키마 판 검사.
- 의존성 자동 갱신 도구.

## 11. 이 계획이 확인하지 못한 것

- 서버 Docker 29.10.0의 `docker run`·`docker builder prune` 옵션과 서버 compose의 `additional_contexts` 지원(모두 로컬 도움말 기준 — 각 항목의 첫 단계가 서버에서 읽기만으로 확인).
- 시간과 크기의 어림 전부(연기 시험 8분, 적재 2~5분, 캐시 한 세대 7~8GB, 캐시 없는 배포 7~10분).
- CI runner의 크롬, JaCoCo와 JDK 25의 조합, inventory 시험이 흔들린 원인.
- 토스의 실제 응답과 운영의 '미룸'·'줄임' 장면(아직 한 번도 일어나지 않음).
