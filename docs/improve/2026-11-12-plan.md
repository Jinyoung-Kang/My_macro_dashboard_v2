#### QA-389 [S3 · 자원] 본문 상한(8MB)이 다 받은 뒤에 적용되고 계층 2에는 상한이 없음
- 위치: `CO/app/fetch/impersonate.py:85-90` `send`(`body = response.content` 뒤에 길이 검사) · `CO/app/fetch/browser_client.py:85-96` `send`(`response.json()`으로 통째로 읽음) · 사이드카는 `page.content()`를 그대로 돌려줌
- 근거(코드 확인): 스트리밍이 아니라 압축을 풀어 전부 메모리에 올린 뒤에야 길이를 잽니다. 등록 호스트(또는 QA-388의 리다이렉트 목적지)가 압축 폭탄이나 수 GB 응답을 주면 그 전에 수집기(메모리 상한 1g)가 죽고, 그 태스크가 다시 도는 동안 반복됩니다. 요청 전체 40초 상한과 컨테이너 메모리 상한이 피해를 제한하고, 정상 출처에서는 일어나지 않습니다(가장 큰 피드가 약 2.9MB).
- 수정: 계층 1은 `stream=True`로 받아 조각을 세다가 상한을 넘으면 끊고 `TransportError`를 냅니다. 계층 2는 사이드카가 본문 길이가 상한을 넘으면 502를 주고, 클라이언트도 `Content-Length`와 누적 길이를 확인합니다.
  - 설치된 curl_cffi 0.16.3의 스트리밍 API(인자 이름, 조각 읽기 함수, 조각이 압축을 푼 뒤의 바이트인지)는 **설치된 패키지 소스에서 먼저 확인**합니다(기억으로 쓰지 않음). 예상과 다르면 전송 바이트 상한 옵션과 '압축을 푼 뒤 길이 검사'를 함께 쓰고, 막지 못하는 경우(압축 폭탄)를 진행 기록에 남은 위험으로 적습니다.
  - 버린 대안: 전송 바이트 상한만 걸기(압축 폭탄을 못 막음).
- 검증: `CO/tests/test_fetch_ladder.py` — `MAX_BODY_BYTES`를 1KB로 바꾸고, 로컬 서버가 `Content-Encoding: gzip`으로 풀면 수 MB가 되는 본문을 줄 때 `FetchFailed`이고 읽은 누적 바이트가 상한 근처에서 멈춤(읽기에 계수기를 끼워 확인). 사이드카 쪽은 `CO/tests/test_sidecar.py`에 큰 본문 → 502.
- 효과·위험·동작 변화: 정상 응답은 같습니다. 상한을 넘는 응답의 실패 글이 달라집니다.
- 선후: QA-388 뒤(같은 함수).

- 위치: `FE/components/screens/info/ReaderDialog.tsx:42-62` `translate`, `:67` `offerTranslate`(`!translated`를 요구), `:77-81` · 서버 `BE/feature/info/InfoService.java:202-211`, `BE/feature/info/InfoTranslator.java:433-434`
- 근거(코드 확인 — 계획 세션도 읽음): 영어 제목·영어 본문 글에서 번역을 누르면 서버는 제목을 먼저 옮기고 본문을 옮깁니다. 본문이 실패하면 응답은 '제목 번역 있음, 본문 번역 없음, 오류 글: 다시 누르면 남은 부분만 번역합니다'인데, 화면은 제목 번역이 있으면 번역 결과를 채우고 그 뒤로는 단추를 내지 않습니다. 팝업을 닫았다 다시 열어야 합니다.
- 수정: 단추를 낼지를 `FE/lib/info.ts`의 순수 함수로 옮깁니다. 본문 번역이 필요한데(한국어가 아닌 본문·요약) 본문 번역이 없고 '이미 한국어'도 아니면 계속 내고, 실패 뒤 문구는 '다시 번역'으로 합니다.
  - 버린 대안: 실패 때 번역 결과를 비우기(성공한 제목 번역까지 사라짐).
- 검증: `FE/components/screens/info/__tests__/InfoHub.test.tsx` — 한국어 제목이 없는 글의 팝업에서 번역 요청이 '제목 번역만 있는 실패 응답'을 돌려준 뒤 오류 글과 번역 단추가 함께 남고, 다시 눌러 성공 응답이면 본문이 한국어로 바뀜(수정 전에는 첫 응답 뒤 단추 없음). `info.test.ts`에 순수 함수 시험.

- 실제 주문의 이중 전송 방지: 설정 행 잠금 안의 SENDING 선기록, 유일 색인 둘, 같은 키·같은 바이트 재전송. 재기동·시간 초과·늦은 보유 반영에서도 새 주문이 나가지 않습니다.

- 로그·텔레그램: 실제 매매는 사유 코드와 건수만, ISA는 종목 코드·이름·수량만 읽습니다.
- 인가 표(새 경로 모두 운영자 전용, 컨트롤러와 표를 대조하는 시험), 경로 정규화, 쓰기 요청의 출처 검사, 수집기 토큰(빈 값 거부·상수 시간 비교), SQL 바인딩.
- ISA: 같은 요청 두 번 방어, 여러 줄 확인의 한 트랜잭션, 숫자 입력 해석(전각·쉼표·지수 표기를 0으로 읽지 않음), 수능일 시각.
- 장중 판단: 하루 호출 상한(검사와 증가가 한 문장), 세션당 3회(기본키와 CHECK), 응답 뒤 쓰기 실패의 재호출 방지.
- 마이그레이션 V20~V32: 다시 적용해도 안전하고 큰 표에 긴 잠금이 없습니다. 적용은 한 트랜잭션과 advisory lock.
- 차단 통과 수집: 닫힘·예산·일정 상태가 원자적이고 재기동 뒤 이어집니다. 사이드카는 포트 없음·비root·사설 대역 차단.
- 정보 수집 수집기(11-12 리뷰): 개인 IP 금지가 태스크 머리와 틱 두 곳에서 걸리고 기반 compose가 `"false"` 고정입니다. KRX 계정 값은 환경변수에서만 읽고 예외 글·실행 기록·저장본에 싣지 않으며 세션 쿠키는 메모리에만 있습니다. 사이드카 입력(공유 비밀의 상수 시간 비교, https + 허용 호스트, 한 번에 한 건)과 허용 호스트·정책 표의 대조 시험이 있습니다. 피드의 외부 엔티티는 꺼져 있습니다. 하루 예산은 한 문장 upsert이고 KST 날짜 기준입니다. 스키마 V33~V35는 다시 적용해도 안전하고 CHECK 값이 코드와 맞습니다. 본문은 40,000자에서 자르고 180일 정리가 있습니다. 저장하는 링크는 http·https만 받습니다.
- 정보 수집 백엔드: 새 경로 10개가 모두 운영자 전용이고 쓰기 요청은 출처 검사를 지납니다. 입력 검증(id 모양, 종류·묶음 허용 목록, 쪽 크기 1~50)과 SQL 바인딩·LIKE 이스케이프가 있고 목록은 본문을 읽지 않습니다. 백엔드는 수집기 표를 읽기만 합니다(구조 시험에 새 표가 들어감). Gemini 키는 머리글로만 가고 로그·응답에 싣지 않습니다. 번역의 하루 글자 상한, 일꾼 수, 대기 한도가 있고 일부 실패는 성공한 조각만 저장합니다. 끊김 알림은 표에 기록해 재기동 뒤 반복하지 않습니다.
- 패킷 수집 글 섹션: 스위치를 끄거나 창에 글이 없거나 초기 결정이면 섹션을 싣지 않아 패킷이 이전과 바이트까지 같습니다(고정본 57개는 11-10 뒤 하나도 바뀌지 않음). 구분자 모양은 전각·보이지 않는 글자 변형까지 지웁니다. 장중 확인·장중 판단 패킷에는 이 섹션이 없습니다. 토스 자료는 들어가지 않습니다.
- 정보 수집 화면: 외부 글을 HTML로 넣는 곳이 없고 글자로만 그립니다. 새 창 링크 10곳 모두 `rel="noopener noreferrer"`입니다. 탭 경로는 목록 밖이면 404이고, 늦게 온 응답이 다른 글·다른 탭에 덮이지 않습니다(`useApi`의 경로 확인, 팝업의 `key`). 없는 값은 '—'입니다. 안내 띠는 운영자가 아니면 요청하지 않습니다.
- 수급 레이더: Naver·KRX 파서가 추정 값과 금액 없는 행을 빼고 부호·단위를 맞춥니다. 누적 이력은 행의 기준일로 쌓고 빈 수집으로 지우지 않습니다. 뉴스 요약 저장(ADR 0037)은 피드가 준 것만, HTML을 떼고 상한을 두며, 패킷은 요약을 읽지 않습니다.

## 9. 개선 제안 (변경 기준에 해당하지 않음)

- 사용자 관리(승격)와 실제 매매 켜기 창, 미리보기.
- 실제 매매 알림·대조(`RealTradeJob`·`RealTradeExecutor`·`RealTradeNotices`), 백엔드 종료 순서.
- ISA 매매 내역 고치기·되돌리기와 체결 입력 창.
- 월 상한 셈, 장중 판단 요청 검증, 스탑 감시의 덮음 판정, 수집기 `paper_stopwatch`·`kr_paper_timed`·`yahoo`.
- 차단 통과 수집의 받기 계층(`fetch/impersonate.py`·`ladder.py` — 리다이렉트와 본문 상한), 정보 수집 태스크(`tasks/info.py`의 KRX·네이버, `info_blogs.py`), 출처 상태와 끊김 알림(수집기 상태 기록 → 백엔드 `SourceAlertJob` → 화면 안내 띠).
- 수급 레이더(`RadarService`의 저장본·지금 받기 갈래, 교집합, 수집기 체인의 KRX 단계).
- Claude 결정 패킷의 수집 글 섹션(`PacketBuilder`·`ReadingSection`), 번역(`InfoTranslator`·`GeminiClient`)과 원문 팝업.
- 운영 스크립트 `deploy.sh`·`db-restore.sh`, compose의 `PAPER_ENABLED`.

**테스트가 부족한 경로**
- 백업·복원 시험은 이 PC에서 통째로 건너뜁니다(CI에서만 돎).
- 화면 변경은 jsdom으로만 봅니다. 실제 브라우저에서 응답 없는 끄기, 켜기 창의 '지금 나감' 표시, 승격 비밀번호 창, 정보 수집의 시각 표시·번역 팝업·안내 띠.
- 토스·Yahoo·텔레그램·Claude·Gemini는 목과 고정본뿐입니다.
- 차단 통과 수집은 서버에서만 돌아 이 PC와 QA 스택에서는 실제 출처로 확인할 수 없습니다(가짜 응답·로컬 임시 서버·합성 표본뿐). 브라우저 컨테이너(계층 2)의 실제 드라이버는 CI의 이미지 빌드에서만 뜹니다.
- 백엔드 종료 시간(연결을 연 채 정지)은 QA 스택에서 재야 합니다.
- 한국 패킷의 수집 글 섹션 경로와 `useDismissed`·쪽 나눔 도우미에는 직접 시험이 없었습니다(QA-402·408·410이 일부를 더함).

**배포 뒤 서버에서 읽기로 확인할 것(배포는 D-1의 답대로)**
- 백엔드 시작 로그의 '모의 매매 정기 작업 켜짐'(QA-341).
- 첫 polite 주기 뒤 출처 상태에 '정책 표 밖으로 리다이렉트'로 실패한 출처가 있는지(QA-388). 있으면 그 호스트를 정책 표와 `BROWSER_ALLOWED_HOSTS`에 넣을지 사용자가 정합니다.
- 며칠 동안 부분 실패 알림이 평소에도 뜨는 출처가 있는지(QA-391), KRX가 깰 때마다 다시 로그인하지 않는지(QA-390 — 실행 기록의 요청 수).
- 전에 닫아 둔 안내 띠가 한 번 다시 뜨는 것은 예상된 동작입니다(QA-408).
- 레이더에서 개인·연기금 등과 기관 순매도가 조회마다 새로 받아지는지, 그때의 응답 시간(QA-395).
- 운영자 계정이 하나인지(QA-338).

**확인하지 못한 의심 사항**
- 운영 서버: 운영자 계정 수(QA-338), ISA 보유·매입 금액이 이미 틀어졌는지(QA-339), 수집기 메모리 추이(QA-368), 한 달 주문 행 수(QA-358), 수집기 로그의 건너뛴 회차(QA-374), Tailscale Serve가 넘기는 호스트 값(QA-383), 미국 비용 소급 뒤 현금 음수 여부, 스케줄 밖 레이더 저장본이 실제로 멈춰 있는지(QA-395), 수집 글의 작성 시각과 처음 받은 시각의 분포(QA-400의 누락 비율), 첫 적용 결정의 패킷 크기(섹션이 붙는 날 '패킷이 목표보다 큽니다' 경고가 뜨는지), 서버 `.env`에 쓰지 않는 LS증권 키 줄이 남아 있는지.
- 외부 동작: 토스가 봉투 밖 오류 본문을 내는지(QA-350), 체결 0건 주문의 체결 수량 칸, 주문 목록의 날짜 기준, Yahoo가 장중에 SPY를 빈 시계열로 주는지(QA-361), 09:15 ET 저장본의 일봉 날짜(QA-359), 브라우저 드라이버가 리다이렉트 홉에 목적지 검사를 부르는지(QA-414), 어느 출처가 리다이렉트에 기대는지(QA-388), KRX가 18:30에 그날 자료를 확정하는지와 어느 화면이 평소에도 비는지(QA-390·391), Financial Juice 피드의 링크가 줄마다 고유한지, 네이버 매매상위의 2쪽 요청이 1쪽과 겹치는지(QA-412)·순매도 표의 금액 부호·당일 매매동향이 잠정치인지, Gemini가 일부 글과 함께 정상 종료가 아닌 사유를 주는지(QA-405).
- 한국 계좌2 끈 판이 켠 판 작업 전과 바이트까지 같은지(QA-362).
- 수집 글의 요약을 240자에서 자를 때 이모지 같은 두 단위 글자의 가운데가 잘릴 수 있습니다(`ReadingSection.clip`의 `substring`). 그 패킷이 API에서 거절되는지는 확인하지 못했습니다(코드 읽기로 본 의심 — 사건 섹션의 자르기도 같은 방식인지 함께 볼 것).
- 결정 대기 항목 QA-376~386, QA-400·413·414 전부.

**사용자에게 따로 알릴 것(코드 변경 아님)**
- 이 PC의 `.env`(git 추적 밖)에 지금은 쓰지 않는 LS증권 앱 키·시크릿 줄이 남아 있습니다(리뷰어가 줄 위치만 확인, 값은 옮기지 않음). 줄을 지우고 증권사 쪽에서 키를 폐기하는 것을 권합니다. 서버 `.env`도 같은지 확인이 필요합니다.
- ADR 0035 결정 11의 '`KRX_ID`·`KRX_PW` 줄은 지워도 됩니다'는 ADR 0036으로 뒤집혔습니다. 서버 `.env`에서 그 두 줄을 지우면 KRX 수집이 실패합니다(QA-375가 문서를 고침).
