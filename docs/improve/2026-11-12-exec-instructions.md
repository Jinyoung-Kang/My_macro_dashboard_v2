# 실행 세션 지시문 — My_macro_dashboard_v2 5차 개선 (계획 2026-11-12)

## 1. 역할과 목표

너는 이 프로젝트를 넘겨받은 시니어 풀스택 소프트웨어 엔지니어야. 이 개선 작업은 두 세션으로 나뉘어 있어. 계획 세션이 이미 프로젝트를 파악해 무엇을 왜 어떻게 고칠지 계획서를 썼고, 사용자가 그 계획을 읽고 승인했어. 이 세션은 승인된 계획을 실행하고, 독립 검토를 받고, 최종 보고를 쓰는 실행 세션이야. 너는 계획 세션의 대화를 볼 수 없어. 계획서, 진행 기록, 이 지시문, 사용자가 보낸 프롬프트가 네가 아는 전부야.

두 세션을 합친 목표는 이 코드를 실무 코드 리뷰를 통과하고 다음 사람이 안전하게 고칠 수 있는 상태로 만드는 것이야. 코드를 많이 바꾸는 것이 목표가 아니야. 확인해 보니 고칠 이유가 없는 부분은 그대로 두고, 그대로 둔 이유를 적어.

이 작업 뒤에 별도의 QA 작업(출시 검증)이 이어져. 여기서는 코드 리뷰로 드러난 버그와 구조 문제만 다뤄. 부하 테스트, 전체 기능·화면 점검, 접근성 전수 점검은 QA에 맡기고, QA가 이어받을 정보를 최종 보고에 남겨.

### 프로젝트 규칙과 이전 기록

- 프로젝트 규칙 문서(`CLAUDE.md`, `docs/DEVELOPMENT.md`, `docs/PRINCIPLES.md`, `docs/adr/README.md`, `README.md`)가 이 지시문의 기본값보다 우선해(브랜치 이름, 커밋 형식, 검증 명령, 문서 위치, 결함 번호, push·병합 절차). 충돌하면 프로젝트 규칙을 따르고 무엇을 따랐는지 진행 기록에 적어.

- 이전 회차 파일은 덮어쓰지 말고 날짜를 붙인 새 파일로 써. 진행 기록(`PROGRESS.md`)과 결함·제안 번호는 이어서 써.
- 기록에는 코드를 옮겨 적지 말고 파일:줄과 심볼 이름으로 가리켜. 진행 기록은 요약으로 유지해.

### 안전 규칙

- 작업과 테스트는 로컬이나 테스트 환경에서만 해. 운영 데이터와 실제 계정은 쓰지 마. 운영 DB 이름은 `macrodash`이고 테스트는 `macrodash_test`(병렬로 나누면 `macrodash_<이름>_test`)만 써.
- 테스트·스크립트가 붙는 DB, 포트, 컨테이너, 볼륨, 파일 경로가 운영 것이나 다른 프로젝트 것과 겹치지 않는지 실행 전에 확인해. 이 PC에는 다른 스택이 있어: `Local_macro_dashboard_v3`(3000/8080/8000/5432), `My_macro_dashboard_v1`(3001/8081/8001/5433), 이 저장소(3002/8082/8002/5434), 이 저장소의 QA 스택(13002/18082/18002/15434), 그리고 관계없는 다른 프로젝트의 스택과 볼륨. 이 저장소의 것만 다뤄.

- 로컬 스택 전체를 `make up`으로 띄우지 마. 수집기가 실제 외부 출처를 불러. 화면이나 API를 실제로 띄워 봐야 하면 QA 스택(`bash scripts/qa/qa-stack.sh up`, 외부 호출 차단)을 써.
- 실제 클라우드·외부 서비스의 리소스는 조회만 해. 생성, 변경, 삭제, 배포는 하지 마. Vultr 서버에 접속하거나 `scripts/vultr/deploy.sh`를 돌리는 것은 D-1에서 승인된 경우뿐이야. AWS 자원은 건드리지 마.

- 비밀값을 발견하면 문서, 로그, 커밋에 원문을 남기지 말고 위치와 종류만 적어. `.env`·`.env.qa`의 값을 출력하지 마. QA-340의 주소 원문도 어디에도 옮기지 마.
- 임시 파일과 별도 worktree는 프로젝트 밖(세션 임시 폴더)에 둬. `/tmp`는 12GB 메모리 파일 시스템이라 worktree를 여러 개 두면 가득 차(지난 회차에 실제로 찼어). 다 쓴 것은 지워.

### 심각도 기준

- S1 치명: 인증 없이 또는 타인 권한으로 데이터에 접근·변경 가능, 데이터 손실·오염, 원격 코드 실행, 비밀값 노출, 서비스 전체 중단
- S2 높음: 핵심 기능이 동작하지 않고 우회 방법이 없음, 특정 조건에서 데이터 불일치, 악용 조건이 제한적인 보안 결함
- S3 보통: 기능이 잘못 동작하지만 우회 가능, 변경할 때마다 버그를 만드는 구조 문제, 측정된 성능 저하
- S4 낮음: 표시·문구 오류, 가독성, 사용에 지장이 없는 불편

## 4. 실행 세션의 규칙

### 시작 절차

- 프롬프트에 적힌 값(문서 경로, 계획 기준 커밋, 승인 범위, 결정 사항 답변, 동결 영역)을 읽어.
- 계획서와 진행 기록을 끝까지 읽어. 읽을 수 없으면 멈추고 물어봐.
- 현재 코드가 계획 기준 커밋(`caabacf2`)과 같은지 확인해. 계획 문서(`docs/improve/2026-11-12-plan.md`, `2026-11-12-exec-instructions.md`, `2026-11-12-exec-prompt.md`, 고친 `PROGRESS.md`, 그리고 11-10 문서 셋)는 커밋되지 않은 채 작업 트리에 있는 것이 정상이야. 그 밖에 달라졌으면 바뀐 파일이 승인된 항목과 겹치는지 보고, 겹치는 항목은 위치와 근거를 다시 확인해.
- postgres가 떠 있지 않으면 `make infra`로 띄우고, 위 안전 규칙의 5432 확인을 한 뒤 검증 수단을 모두 실행해 위 기준선과 같은지 확인해. 다르면 원인을 찾아 진행 기록에 적고, 설명되지 않으면 멈추고 물어봐.
- `main`에서 작업 브랜치 `claude/improve-r5-2026-11`을 만들고, 계획 문서를 첫 커밋으로 넣어(`docs(improve): …`). 11-10 문서 셋은 프롬프트의 D-12 답을 따라(답이 없으면 함께 커밋).

### 승인 범위

- 프롬프트의 '승인 범위'에 든 항목만 수정해. 비어 있으면 계획서 §5의 '이번 회차 제안 범위' 전체(1차 33건, 2차 38건)가 승인된 것이야. "1차"라고만 적혀 있으면 1차 33건만이야. 프롬프트를 받은 것이 승인이니, 아래 '멈추는 경우'에 해당하지 않는 한 끝까지 진행해.
- 계획서 §7 '내가 결정해야 하는 것'(D-1~D-12) 가운데 프롬프트에 답이 없는 항목은 계획서 표의 '답이 없을 때' 칸을 따라.
- 계획서는 출발점이지 확인된 사실이 아니야. 항목을 고치기 전에 직접 재현하거나 코드를 확인해. 계획서가 '리뷰어 코드 확인'이나 '추정'이라고 적은 항목은 더 그래. 위치만 다르고 문제가 같으면 실제 위치에서 고치고 차이를 진행 기록에 적어. 문제가 재현되지 않거나 원인이 다르면 고치지 말고 이유를 적은 뒤 다음 항목으로 넘어가.
- 작업 중 새로 찾은 문제는 승인된 항목과 같은 원인이면 함께 처리해. 그 밖은 진행 기록의 '새 발견'에 심각도와 함께 적고 고치지 마.

### 반드시 지킬 것과 판단에 맡기는 것

반드시 지킬 것(예외 없음)
- 안전 규칙, 작업 규칙, 멈추는 경우, 동결 영역, 승인 범위
- 직접 실행해 확인한 것만 사실로 보고하기

네 판단에 맡기는 것
- 승인 범위 안에서 진행 순서와 커밋 크기, 구현 세부
- 계획서의 수정 방법보다 나은 방법을 찾았을 때: 고치는 범위와 밖에서 보이는 동작이 계획과 같으면 그 방법으로 진행하고 이유를 진행 기록에 적어. 달라지면 승인 대기로 넘겨.

### 진행 순서

**실행.** 작업 규칙대로 우선순위 순서(계획서 §5의 순서 — QA-399가 맨 앞)로 진행해. 진행 상황은 진행 기록(`docs/improve/PROGRESS.md`의 '2단계 — 실행' 표)에 계속 갱신해. 작업이 중단되거나 앞의 맥락을 잃어도 이 파일만 읽고 이어갈 수 있게 써.

**독립 검토.** 별도 에이전트에게 전체 변경(diff), 계획서, 아래 완료 기준만 넘기고, 네 작업 과정은 넘기지 마. 확인할 것은 다음과 같아.
- 정확성이나 요구사항에 영향을 주는 문제가 있는가
- 계획에 없는 동작 변경이 섞여 있는가
- 테스트가 변경을 실제로 검증하는가

정확성이나 요구사항에 영향을 주는 문제만 고쳐. 취향 수준의 지적은 반영하지 마. 별도 에이전트를 쓸 수 없으면 처음 보는 리뷰어 입장에서 직접 재검토하고, 그렇게 했다고 밝혀.

**최종 보고.** 아래 '최종 보고' 형식대로 정리해.

### 작업 규칙

버그 수정
- 실패하는 테스트로 먼저 재현하고, 증상을 가리지 말고 근본 원인을 고쳐. 테스트로 재현할 수 없는 종류면 계획서에 적힌 대체 확인 방법으로 재현하고 그 출력을 남겨.
- 테스트와 수정은 프로젝트 규칙대로 두 커밋(`test(QA-###)` → `fix(QA-###)`)으로 넣어. 수정 전 실패 출력은 수정 커밋 본문이나 결함 기록에 남겨.
- 같은 원인이 다른 위치에도 있는지 검색해 함께 처리해.

리팩터링
- 테스트가 없는 코드는 현재 동작을 고정하는 테스트부터 추가해.
- 밖에서 보이는 동작(공개 API와 함수 시그니처, 명령줄 인터페이스, URL, 화면 동작, 파일·메시지 형식, 저장 스키마)은 바꾸지 마.

커밋
- 한 가지 주제씩 작게 커밋하고, 리팩터링과 버그 수정은 한 커밋에 섞지 마.
- 커밋마다 검증 수단을 모두 통과시켜. 기준선에서 이미 실패하던 항목은 더 나빠지지 않게 해(지금은 그런 항목이 없어).
- 기존 테스트를 삭제하거나 건너뛰게 하거나 기대값을 느슨하게 바꿔 통과시키지 마. 계획서가 미리 적어 둔 기대값·고정 자료 변경(QA-343의 대조 시각, QA-347·353의 안내 글, QA-359의 이른 예약 거절, QA-360의 고정 자료에 `mode` 넣기, QA-400이 승인됐을 때의 창 기대)만 하고, 커밋 메시지에 이유를 적어.
- 전체 파일 포맷 정리처럼 diff를 키우는 변경은 하지 마.
- 원격 push와 `main` 병합은 프로젝트 규칙의 절차대로만 해: 작업 브랜치를 push해 CI를 확인하고, 본체 폴더의 `main`에 fast-forward로 병합해 `origin/main`에 push한 뒤 CI 6개 job을 확인해. 이것도 D-1의 답이 허락하는 범위까지만 해. 강제 푸시와 이력 재작성은 하지 마.
- 다른 세션이 그사이 `main`에 커밋을 올렸으면 받아서 합쳐(아직 push하지 않은 브랜치는 rebase, 이미 push한 브랜치는 병합 커밋 — 저장소 선례). 합친 뒤 `make test`를 다시 돌려.
- CI가 GitHub 쪽 사정으로 취소되면('job was not acquired by Runner') 취소된 job만 다시 돌리고, 코드 실패와 구분해 보고해.

성능
- 추측으로 고치지 말고 변경 전후를 같은 조건에서 측정한 수치로 판단해.
- 측정 조건(실행 환경, 데이터 건수, 반복 횟수)을 수치와 함께 적어.
- 차이가 측정되지 않으면 변경을 되돌려. 이번 범위에서는 QA-368(끝난 스레드 객체)과 QA-399(시험 시간)가 여기에 해당해.

의존성
- 버전은 기억이 아니라 공식 저장소(npm, Maven Central, PyPI)와 공식 릴리스 페이지에서 정식 릴리스를 확인해. 마일스톤·RC는 올리지 마. 설치된 라이브러리의 API(예: QA-389의 스트리밍 받기)는 기억으로 쓰지 말고 설치된 패키지 소스나 공식 문서에서 확인해.
- 패치·마이너 업데이트는 검증 수단이 통과하면 진행해. 이번 범위는 DEP-1(화면 패치)과 DEP-2(bcprov — 공식 릴리스 노트에 보안 수정이 있을 때만)뿐이고 수집기 의존성은 올리지 않아(계획서 §1의 이유).
- 메이저 업그레이드는 프롬프트에서 승인된 것만 진행해. 그 밖은 영향 범위를 정리해 승인 대기로 넘겨.

### 멈추는 경우

즉시 멈추고 물어봐.
- 데이터 삭제, 기존 데이터를 바꾸는 마이그레이션, 버전 관리 이력 재작성이나 강제 푸시처럼 되돌릴 수 없는 작업이 필요할 때
- 공개 API, URL, 파일 형식 같은 공개 인터페이스의 하위 호환을 깨거나 기능을 없애야 할 때. 계획서가 미리 적어 승인받은 것은 예외야: QA-338의 `password` 칸, QA-339·348·355의 400, QA-356의 200, QA-359의 이른 HOURLY 예약 거절과 수동 요청 400, QA-388의 정책 표 밖 리다이렉트 실패, QA-395의 조회 방식, QA-396의 날짜가 다른 교집합 비움, QA-397의 실제 기간 표시. 응답에 칸만 더하는 것(QA-344·396·397·403·408)은 하위 호환을 깨지 않아.
- 유료 서비스나 새 인프라를 추가해야 할 때
- 비밀값, 계정, 환경 변수처럼 사용자가 직접 넣어야 하는 값이 없어 더 진행할 수 없을 때
- 계획서나 진행 기록을 읽을 수 없거나, 기준선이 계획서와 다른데 이유를 설명할 수 없을 때
- 기존 고정본(`paper/golden/`) 파일이 바뀌어야만 통과하는 수정이 나왔을 때, 또는 계획서가 적은 범위 밖으로 Claude 패킷·프롬프트의 글자가 바뀌는 수정이 나왔을 때

프롬프트의 '결정 사항 답변'에서 사용자가 이미 답한 것은 그 답의 범위 안에서 진행하고, 범위를 넘으면 멈춰.

멈추지 말고 모아 뒀다가 물어봐.
- 버그인지 의도된 동작인지 코드만으로 판단하기 어려울 때
- 동결 영역에서 찾은 문제의 수정안
- 메이저 업그레이드처럼 승인이 필요한 변경
- 승인 범위 밖에서 새로 찾은 문제

이 항목들은 진행 기록에 쌓고 다른 작업을 계속해. 남은 작업이 이것뿐이면 한 번에 물어봐.

S1 문제는 발견 즉시 알리고 이어서 진행해.

### 완료 기준

- 미해결 S1·S2가 없거나, 남은 항목이 승인 대기로 정리되어 있다.
- 검증 수단이 모두 통과한다(기준선에서 이미 실패하던 항목은 따로 표시).
- 의도하지 않은 동작 변경이 없다.
- 커밋만 읽고도 무엇을 왜 바꿨는지 알 수 있다.
- 독립 검토에서 나온 정확성 문제가 모두 처리되었다.
