#### QA-1008 [S3] 쓰기 뒤 다시 읽기가 쓰기 전에 나간 같은 GET에 합류해 옛 값이 남음
- 위치: `frontend/src/lib/sharedRequest.ts:15-24`(`createSharedFetcher`), `frontend/src/lib/api.ts:183-196`(`sharedGet`·`apiGetShared`), `frontend/src/hooks/useApi.ts:96-113`(`load`).

- 근거와 확인 상태: **실행으로 확인.** `sharedRequest.ts`를 그대로 import해 "GET 진행 중 → 서버 상태 바뀜 → 같은 열쇠로 다시 호출"을 돌리니 두 호출이 같은 약속을 받고 옛 값(`OFF`)이 돌아오며 요청은 한 번뿐이었습니다(`{ same: true, reloaded: 'OFF', serverState: 'LIVE', gets: 1 }`). `useApi.load`는 자기 컨트롤러만 새로 만들고 `apiGetShared`의 진행 중 약속을 그대로 받습니다. 저장소 자신의 주석(`useInfoSearchWatch.ts:55-56`)도 같은 현상을 적고 그 훅만 막았습니다.
- 잘못되는 장면: 주기 읽기·탭 복귀 읽기·앞 쓰기의 다시 읽기가 나가 있는 동안 쓰기가 끝나면 성공 뒤 `reload()`가 쓰기 전 응답을 받습니다. 예: 알림 규칙 줄 1을 켠 직후 줄 2를 켜면 줄 2가 옛 상태로 남고 다시 눌러도 같은 값을 보냅니다(새로고침 전까지). 실제 매매 켜기 성공 안내와 함께 '꺼짐' 칩이 다시 보입니다(다음 15초 주기까지). 잘못된 주문·장부 오염으로 이어지는 길은 없습니다(서버가 버전·상태로 막음).
- 수정 방법(뿌리에서 한 번): `lib/api.ts`에 모듈 단위 '쓰기 차례'(정수)를 둡니다. `request()`가 **GET이 아닌 요청**을 끝낼 때(성공·실패·시간 초과 모두 — 서버가 처리했을 수 있음) 차례를 1 올립니다. `apiGetShared`의 묶는 열쇠를 `${쓰기 차례}|${timeoutMs}|${path}`로 바꾸고 `sharedGet`의 열쇠 풀이를 거기에 맞춥니다. 쓰기 뒤에 시작한 GET은 쓰기 전에 나간 GET에 합류하지 않고, 앞 응답이 늦게 와도 `useApi.load`가 앞 컨트롤러를 끊어 버립니다. 같은 차례 안의 동시 GET은 지금처럼 한 번만 나갑니다.
  두 훅의 개별 우회(`reloadAfterWrite`, `apiGet` 직행)는 **그대로 둡니다**(동작이 같고, 걷어내는 것은 '더 깔끔'일 뿐).
  버린 대안: `useApi.reload`만 공유를 건너뛰게 하기 — 쓰기 뒤 다른 컴포넌트의 주기 읽기가 옛 GET에 합류하는 것은 남고, 호출부마다 어떤 읽기가 '쓰기 뒤'인지 알려야 합니다.
- 검증 방법(먼저 쓸 실패 시험): `frontend/src/lib/__tests__/api.test.ts` — `fetch`를 목으로 두고 GET P를 끝나지 않게 둔 채 `apiGetShared(P)` → `apiPost(다른 경로)` 완료 → `apiGetShared(P)` 다시 → `fetch`의 GET 호출이 2번이고 둘째 호출의 약속이 첫째와 다름(지금은 1번 — 재현 커밋에서는 `it.fails`). 대조: 쓰기 없이 두 번 부르면 지금처럼 1번.

- 효과·부작용: 쓰기 뒤 화면이 늘 쓰기 뒤 값을 봄. 쓰기 직후의 GET 묶기가 한 번 덜 됨(요청 한 번 더 — 무시할 크기).
- 밖에서 보이는 동작 변화: 쓰기 직후 같은 경로의 GET이 한 번 더 나갈 수 있음.

#### QA-1009 [S3] 경로가 바뀌기 전에 잡아 둔 `reload`를 부르면 지금 경로의 값이 지워짐
- 위치: `frontend/src/hooks/useApi.ts:96-135`(`load` — `[path, …]`에 묶인 useCallback), `:187-188`(`reload: load`). 드러나는 곳: `components/screens/paper/DecisionsSection.tsx`의 `runNow`(수십 초 걸리는 수동 결정 뒤 `list.reload()`), `components/screens/paper/ReviewsSection.tsx`(복기 실행 뒤 `detail.reload()`).
- 근거와 확인 상태: **코드 읽기로 확인(추정).** 옛 그리기의 `load`(경로 A)가 불리면 `controllerRef.current?.abort()`로 지금 경로 B의 진행 중 읽기를 끊고, 응답을 `dataPath: A`로 적습니다. 반환부의 `state.dataPath === path ? state.data : null`에서 지금 경로 B의 값이 null이 되고 `loading=false, error=null`이라 패널이 제목만 남고 빕니다. `useApi.test.ts`의 경로 변경 시험은 '경로가 바뀐 뒤 옛 reload를 부름'을 다루지 않습니다.
- 잘못되는 장면: 결정 로그에서 Claude 계좌의 '지금 결정 실행'을 기다리는 동안 머리에서 규칙 계좌로 바꿔 보면, 실행이 끝날 때 규칙 계좌의 '결정 기록'이 빕니다(다음 60초 주기까지). 주간 복기 상세는 주기 읽기가 없어 더 오래 빕니다.
- 수정 방법: `useApi` 안에 '지금 경로'와 '지금 load'를 가리키는 ref를 두고(그릴 때마다 갱신), `load`의 들머리에서 자기 `path`가 지금 경로와 다르면 아무것도 고치지 않고 지금 load를 대신 부릅니다. 반환하는 `reload`의 정체(경로가 바뀌면 새 함수)는 그대로 둡니다 — `reload`를 의존 목록에 넣은 소비자의 동작이 바뀌지 않게.
  버린 대안: `reload`를 늘 같은 함수로 내보내기 — `useEffect(…, [reload])` 꼴의 소비자가 있으면 다시 읽기 시점이 바뀝니다.
- 검증 방법: `frontend/src/hooks/__tests__/useApi.test.ts` — 경로 A로 그린 뒤 `reload`를 잡아 두고, 경로 B로 다시 그려 B 값을 받은 다음 잡아 둔 `reload()`를 부름 → `data`가 B 값 그대로이고 요청은 B 경로로 한 번 더 나감(지금은 `data`가 null이고 A 경로로 나감).
- 기대값이 바뀌는 기존 시험: 없음.

#### QA-1012 [S3] 새 글 수·알림이 '표에 넣은 시각'이 아닌 칸을 기준으로 삼아 일부 글이 빠짐
- 위치: 수집기 `collector/app/tasks/search_watch.py:174`(`now` = 깨기 시작 시각)·`:437-439`(`_rows` — 작성 시각 없는 저장본 글은 `first_seen_at`을 원래 받은 시각으로, 그 밖은 깨기 시작 시각으로), `:107`(`TIME_LIMIT_SECONDS = 600`). 백엔드 `backend/src/main/java/com/macrodash/store/SearchWatchStore.java:137-139`(`NEW_ITEM` — `i.first_seen_at > COALESCE(w.last_seen_at, w.created_at)`), `:288-297`(`notifyCandidates` — `i.first_seen_at > w.notified_at`·`> since`), `feature/search/SearchWatchAlertJob.java:49`(`FRESH` 6시간).
- 근거와 확인 상태: **실행으로 확인**(수집기 쪽 — `store.search_watch_item_titles`만 스텁하고 `_rows`를 부르니, 넣는 시각 05:00Z에 작성 시각 없는 글이 `first_seen_at = 전날 22:00Z`, `published_at = None`으로 나옴). 백엔드 SQL 세 조건은 코드 읽기.
- 잘못되는 장면: (가) 작성 시각이 없는 저장본 글(Nikkei Asia 피드 등)은 표에 넣는 순간 이미 몇 시간 전의 `first_seen_at`을 갖습니다. 그 사이에 사용자가 그 대상을 봤거나(`last_seen_at`) 알림이 나갔으면(`notified_at`) 새 글 수·알림에서 빠지고, 지연이 6시간을 넘으면 늘 알림에서 빠집니다. (나) 한 번 깰 때 여러 대상을 차례로 처리하면서 모든 줄에 깨기 시작 시각을 넣으므로, 그 뒤 커밋되기 전에 사용자가 그 대상을 열면 뒤이어 커밋되는 줄이 영영 새 글이 아닙니다.
  수집기의 `first_seen_at` 값 자체는 계약(`docs/specs/2026-11-14-info-search-contract.md` §6-3)대로이고 시험이 고정합니다. 결함은 백엔드가 그 칸을 '표에 들어온 시각'으로 쓰는 맞물림입니다.
- 수정 방법:
  1. 스키마 `db/migrations/V45__search_watch_added_at.sql`(다음 번호 — 쓰기 전에 `ls db/migrations`로 확인): `search_watch_items`에 `added_at TIMESTAMPTZ` 칸을 더하고(`ADD COLUMN IF NOT EXISTS`), 기존 행은 `added_at = first_seen_at`으로 채운 뒤(`WHERE added_at IS NULL` — 여러 번 돌려도 같은 결과), 기본값 `clock_timestamp()`와 `NOT NULL`을 겁니다. 기존 칸의 값은 바꾸지 않습니다. `NEW_ITEM`이 쓰는 인덱스가 `first_seen_at`을 포함하면 같은 꼴의 `added_at` 인덱스를 더합니다(V37의 인덱스 정의를 보고 판단).
  2. 수집기: 넣는 문장(`collector/app/store.py`의 `insert_search_watch_items`)은 `added_at`을 주지 않습니다(DB 기본값 = 넣는 순간). `first_seen_at`·`published_at`은 지금 그대로(화면의 '받은 시각' 표시용).
  3. 백엔드: `NEW_ITEM`의 첫 조건과 `notifyCandidates`의 두 조건(`> w.notified_at`, `> since`)을 `i.added_at`으로 바꿉니다. `NEW_ITEM`의 둘째 조건(작성 시각의 되돌아보기 창)은 그대로 둡니다. 스키마 준비 검사(`SearchWatchStore.ready()` 또는 `store/SchemaCheck` — V38 때 알림 칸을 더하며 쓴 방식)에 새 칸을 넣어, 마이그레이션 전의 DB에서는 지금처럼 '아직 준비 안 됨'으로 답하게 합니다.
  4. 문서: 계약 §6-3·§6-4에 '새 글·알림의 기준은 넣은 시각(`added_at`)'을 적고, ADR 0041에 덧붙입니다.
  버린 대안: `first_seen_at`을 넣는 시각으로 바꾸기 — 계약 §6-3과 화면의 '받은 시각' 표시가 달라지고 기존 시험의 기대가 바뀝니다.
- 검증 방법(먼저 쓸 실패 시험):
  - 백엔드 `SearchWatchStoreDbTest`: `last_seen_at = T-3h`, 줄의 `first_seen_at = T-7h`·`added_at = T-1h`(작성 시각 NULL) → `newCounts` 1(수정 전 코드에서는 칸이 없어 재현 커밋은 `@Disabled`로 넣고, 같은 장면을 `first_seen_at`만으로 만든 '지금은 0' 단언을 실패 출력으로 남김).
  - 백엔드 `SearchWatchAlertJobDbTest`: 작성 시각 NULL, `first_seen_at = now-7h`, `added_at = now-1분` → 알림 1건(지금은 0건).
  - 수집기 `collector/tests/test_search_watch.py`: 줄을 넣은 뒤 그 행의 `added_at`이 넣은 시각(깨기 시작 시각이 아님)이고 `first_seen_at`은 지금 값 그대로.
  - `collector/tests/test_migrations.py`의 기존 틀로 V45를 두 번 적용해도 같은 결과.
- 기대값이 바뀌는 기존 시험: 백엔드 DB 시험 가운데 줄을 `first_seen_at`만으로 넣고 새 글·알림을 기대하는 것은 넣는 문장이 `added_at`을 주지 않아 기본값(지금)이 들어가므로, '이미 본 글'을 흉내 내려고 과거 `first_seen_at`을 준 사례는 `added_at`도 같은 과거 값으로 주도록 **준비 자료만** 고칩니다(기대는 그대로). 기대 자체가 바뀌어야 하는 시험이 나오면 승인 대기.
- 효과·부작용: 작성 시각 없는 출처의 글과 커밋이 늦은 줄이 새 글·알림에 듭니다. 기존 행은 `added_at = first_seen_at`이라 판정이 지금과 같습니다.
- 밖에서 보이는 동작 변화: 스키마에 칸 하나 추가(V45). 새 글 수와 텔레그램 알림에 지금까지 빠지던 글이 듦. 응답 계약은 그대로.
- 배포: 수집기가 기동 때 V45를 적용합니다. 새 백엔드는 칸이 생기기 전에는 '준비 안 됨'으로 답합니다(3번). `deploy.sh`는 스키마 적용 뒤 기동하므로 평소 순서로 충분합니다. 되돌릴 때는 코드만 되돌리면 됩니다(칸은 남아도 옛 코드가 쓰지 않음).

#### QA-1011 [S3] '봤음'을 서버의 지금으로 적어, 화면에 보이지 않은 새 글의 새 글 수·알림이 사라짐
- 위치: 백엔드 `feature/search/SearchWatchService.java:296-312`(`seen` — `watches.markSeen(id, user.id(), clock.instant())`), `store/SearchWatchStore.java:248-251`(`markSeen`). 수집기 `collector/app/services/search.py:432-446`(`_watch_spec` — 모은 글 표 읽기를 `sources.cached`로 15분 캐시), `collector/app/services/search_sources.py:48`(`SOURCE_TTL = 900.0`). 화면 `frontend/src/components/screens/search/EntityView.tsx:108-118`(타임라인을 그리면 본문 없이 `seen` 한 번), `hooks/useInfoSearchWatch.ts`(`seen`).

- 잘못되는 장면: 10:00 대상 E의 타임라인을 엶(15분 캐시 시작, 봤음 10:00) → 10:05 정기 수집이 새 글 3건을 넣음(왼쪽 목록의 새 글 수 3) → 10:07 E를 다시 엶(결과는 10:00 캐시라 3건이 없음, 봤음 10:07) → 새 글 수 0, 그 3건은 어디에도 새 글로 표시되지 않고 알림 작업이 아직 돌지 않았으면 알림도 없음.
- 수정 방법:
  1. 수집기: `_watch_spec`의 모은 글 읽기는 캐시하지 않습니다(자기 DB 읽기 — `search_store.watch_items`를 바로 부름. `refresh` 인자는 뜻이 없어지지만 시그니처는 그대로).

  4. 화면: `EntityView`가 그린 타임라인 결과의 `watchAsOf`를 `seen(id, watchAsOf)`로 보냅니다(없으면 본문 없이 — 지금과 같음).
  5. 문서: `docs/API.md`의 그 경로 줄, 계약 §6-4·§7, ADR 0041 덧붙임.

- 검증 방법(먼저 쓸 실패 시험):

#### QA-1013 [S3] 구글 경유 줄이 먼저 들어온 기사가 다음 회차에 원문 주소로 한 번 더 새 글이 됨
- 위치: `collector/app/tasks/search_watch.py:369-381`(`stored_id`), `:419-424`(`_rows` — 제목 대조는 약한 줄(경유·주소 없음)에만 걸림).
- 근거와 확인 상태: **실행으로 확인**(같은 제목으로 회차 N은 구글 경유 줄 1행, 회차 N+1(그 행을 기존 행으로 줌)은 원문 줄 1행이 또 나옴. 반대 순서는 0행). 백엔드에 제목 중복 제거가 없는 것은 SQL 읽기. 운영에서의 빈도는 **모름**.
- 잘못되는 장면: 같은 기사가 새 글 수에 두 번 들고 알림이 한 번 더 나갑니다(화면은 합칠 때 경유 줄을 밀어 한 줄로 보임).
- 수정 방법: `_rows`가 약하지 않은 줄을 넣을 때, 같은 대상에 **전체 제목이 같은 경유 행**이 이미 있으면 새 행의 `added_at`(QA-1012)과 `first_seen_at`을 그 경유 행의 값으로 넣습니다(행은 넣되 '새로 들어온 글'이 아니게). 이를 위해 `store.search_watch_item_titles`가 제목마다 경유 행의 `added_at`·`first_seen_at`을 함께 돌려주게 넓히고, 넣는 문장이 `added_at`을 선택 인자로 받게 합니다(주지 않으면 DB 기본값).
  버린 대안: 경유 행을 지우고 원문 행으로 바꾸기 — 행 삭제가 들어가고 화면의 합치기 규칙과 겹칩니다.
- 검증 방법: `collector/tests/test_search_watch.py`의 '이미 있는 글은 …' 시험 옆에 반대 순서 시험 — 구글만 준 실행 뒤 Bing이 같은 제목을 준 실행에서, 둘째 실행이 넣은 행의 `added_at`이 첫 실행의 값과 같음(지금은 둘째 실행의 지금).
- 기대값이 바뀌는 기존 시험: 없음.
- 밖에서 보이는 동작 변화: 같은 기사의 새 글 수·알림 중복이 사라짐.
- 선후: QA-1012 뒤.

#### QA-1014 [S3] 모으지 않는 CIK를 즐겨찾기에 더하면 성공으로 답하지만 저장본이 생기지 않음

- 수정 방법:
  1. 수집기 `filings.py`: `_not_favorite_targets()`가 까닭을 가릅니다 — 기본 기관·합산 자회사는 `default`, 트랙레코드 후보의 **지금 CIK**는 `track_record`(지금 그대로), 후보의 **선행 CIK**는 `track_record_predecessor`와 함께 `currentCik`를 응답에 싣습니다. 까닭 값이 늘어나는 것뿐이고 정기 수집의 대상은 그대로입니다.
  2. 백엔드 `Sec13FFavoriteService`: `refused`가 `track_record`가 아닌 값이면 방금 넣은 줄을 지우고(`favorites.delete` + `cache.clear()` — 이미 있는 실패 갈래와 같은 정리) 409로 답합니다. 문구: `default` → "기본 기관에 합쳐 모으는 CIK라 따로 더할 수 없습니다.", `track_record_predecessor` → "이 CIK는 <currentCik>의 옛 제출자 번호입니다 — 그 CIK로 더하세요.", 그 밖의 값 → "이 기관은 13F를 모으지 않는 대상입니다(<값>)."
  버린 대안: 넣기 전에 `/sec13f/filer` 응답으로 미리 거르기 — 수집기 응답 계약을 한 곳 더 넓혀야 하고, 넣은 뒤 지우는 실패 갈래가 이미 있습니다.
- 검증 방법: `Sec13FFavoriteServiceTest` — 수집기 목이 `refused: "default"`를 주면 줄이 지워지고 409·위 문구, `refused: "track_record_predecessor", currentCik: "000…"`이면 409·지금 CIK가 든 문구, `refused: "track_record"`는 지금처럼 `waiting`. 수집기 `collector/tests/`의 즐겨찾기 수집 시험(파일은 `grep -rn "track_record" collector/tests`로 찾음)에 선행 CIK → `track_record_predecessor`.

### 4-4. 배포 스크립트

#### QA-1015 [S3] `deploy.sh`가 실제 매매 가드보다 먼저 작업 트리를 새 `main`으로 옮김
- 위치: `scripts/vultr/deploy.sh:73-83`(2단계 — `git fetch`·`git merge --ff-only`), `:202`(3단계 뒤 `realtrade_guard before-build`), `:205-208`(빌드), 기동 직전 가드(`before-up`). `docker-compose.yml:138`(`./db/migrations:/app/db/migrations:ro` — 수집기가 호스트 폴더를 그대로 봄), `collector/app/main.py:203`(기동 때 `store.init_schema()`).
- 근거와 확인 상태: **코드 읽기로 확인(추정)** — 병합이 가드보다 앞이고, 디렉터리 bind mount는 호스트 변경을 바로 반영하며, 마이그레이션 적용은 수집기 기동 때입니다. 실제 피해는 그때 대기 중인 마이그레이션 내용에 달려 있습니다(칸·표를 더하기만 하는 파일이면 무해).
- 잘못되는 장면: 평일 장중에 `deploy.sh`를 돌리면 2단계에서 서버 작업 트리가 새 `main`이 되고 가드가 "거래 창이라 배포하지 않았습니다"로 끝납니다. 컨테이너는 옛 이미지 그대로인데 옛 수집기가 새 `db/migrations`를 봅니다. 다시 배포하기 전에 수집기가 다시 뜨면(재부팅, 메모리 상한 초과 뒤 자동 재기동, `docker compose restart`) 새 마이그레이션을 옛 코드 아래에서 적용합니다. 데이터를 바꾸는 마이그레이션(V44 같은 것)은 옛 코드와 함께 돌다 결과가 뒤집혀도 다시 적용되지 않습니다.
- 수정 방법: 가드를 `git fetch`·병합 **앞에서도** 한 번 돌립니다(모드 `before-fetch` — 판정과 넘기는 방법(`REALTRADE_DEPLOY_OK=1`)은 `before-build`와 같고, 멈출 때의 글만 "코드를 받기 전에 멈췄습니다 — 서버 폴더와 돌던 컨테이너 그대로"). 가드 함수 정의와 그것이 쓰는 값(창 계산)을 2단계 앞으로 올립니다(함수 본문은 그대로 — 옮기는 커밋과 고치는 커밋을 나눔). 기존 두 가드는 그대로 둡니다(빌드하는 동안 창에 들어오는 경우).
  남는 경로(빌드 실패, 기동 직전 가드로 멈춤 — 그때는 작업 트리가 이미 새 `main`)는 코드로 닫지 않고 `docs/DEVELOPMENT.md` §7 '배포'에 적습니다: "빌드 실패나 기동 직전 가드로 멈췄으면 다시 배포하기 전까지 수집기를 다시 띄우지 않는다. 다시 띄워야 하면 먼저 서버 폴더를 돌고 있는 판으로 되돌린다(`git checkout --detach <화면 왼쪽 아래의 커밋>`) — 다음 `deploy.sh`가 `main`으로 다시 옮긴다." 근본 수정(이미지에 마이그레이션 상한을 새김)은 §8 제안으로 남깁니다.
- 검증 방법: `collector/tests/test_vultr_scripts.py`의 실제 매매 가드 시험 틀(가짜 git·docker, `rt_fakes`)에 — 실제 매매 켜짐 + 창 안 시각이면 `deploy.sh`가 0이 아닌 값으로 끝나고 가짜 git 기록에 `fetch`·`merge --ff-only`가 **없음**(지금은 있음). 기존 시험 `test_RT2_COL_1_…`은 "빌드 전·기동 직전 가드마다 psql 한 번"으로 호출 수 2를 단언하는데, 가드가 한 번 더 돌므로 3이 됩니다.
- 기대값이 바뀌는 기존 시험: `collector/tests/test_vultr_scripts.py`의 가드 호출 수 단언(`len(psql) == 2` → 3)과 그 설명 글. 가드가 통과하는 경로에서 git 호출 차례를 글자 그대로 보는 단언이 있으면 새 차례에 맞춥니다(이 항목이 승인하는 변경).
- 밖에서 보이는 동작 변화: 거래 창 안에서 `deploy.sh`를 돌리면 코드를 받기 전에 멈춤(출력 글 한 줄 추가). 창 밖의 배포는 가드 질의가 한 번 더 도는 것뿐.

#### QA-1017 [S3] 추가 매수·장중 교체 매수 뒤 보유 종목의 이어받은 조건이 패킷에서 빠짐 — D-2

- 검증 방법: `ContinuityTest`에 `holdingChecksSurviveATopUpBuy`(결정 1이 T 조건 + 매수, 결정 2가 T 추가 매수만 → 결정 1의 조건 묶음을 기대 — 지금은 빈 표), `holdingChecksSurviveAnIntradayReplaceBuy`, 그리고 기존 재매수 시험(`holdingChecksComeFromTheLatestDecisionThatNamedTheTicker`)이 그대로 통과.

#### QA-1018 [S3] 현금 부족으로 줄여 보낸 매수가 체결되면 그날 나머지를 사지 않음 — D-3
- 위치: `backend/src/main/java/com/macrodash/feature/realtrade/RealTradePlanner.java:611-620`(`limit` — 남은 현금 ÷ 상한가로 수량을 줄이고 표시를 남기지 않음), `RealTradeJob.java:1909-1928`(`nextAttempt` — 시도 1이 전량 체결로 끝나면 0), `runFollowup`의 보낼 종목 고르기.
- 근거와 확인 상태: **코드 읽기로 확인(추정)** — 두 곳을 직접 읽었습니다. 기존 시험 `RealTradeJobDbTest.rebalanceExemptFollowupSendsDeferredBuys`의 사례에서 목표 1,000주인 종목이 첫 주기에 92주로 나가고(시험 주석에 적힘) 나머지 908주는 어디서도 보내지 않습니다. 이 계획 코드는 지난 회차 뒤 바뀌지 않았지만, 월 2회 재선정과 회전율 예외(2026-11-18~21)가 이 길을 정기적으로 밟게 만들었습니다. 운영에서 실제로 일어났는지는 **모름**(U-4).
- 잘못되는 장면: 재선정 날 첫 주기는 매도와 매수를 함께 계획하는데, 매수 가능 금액은 매도 대금이 들어오기 전의 남은 현금뿐입니다. 종목 코드 순으로 `floor(남은 현금 ÷ 상한가)`가 1주 이상인 종목은 줄인 수량으로 나가고, 그 주문이 전량 체결되면 그 종목의 시도가 닫혀 같은 창의 마무리가 나머지를 사지 않습니다. 그 종목들은 다음 거래일 묶음까지 목표에 못 미칩니다(현금으로 남음). 손실로 직접 이어지지는 않고 추종 오차입니다.
- 수정 방법(승인됐을 때만 — 선택지는 D-3):
  - (가) 같은 계획에 이 기능의 매도가 있거나 그 창에 진행 중인 매도가 있으면, 현금으로 줄여야 하는 매수는 보내지 않고 `deferred-cash`로 미룹니다(대금이 들어온 다음 주기에 온전한 수량으로 시도 1). 매도가 없는 계획에서는 지금처럼 줄여 보냅니다.
  - (나) 줄인 매수에 표시를 남기고(`capped`와 같은 자리), 마무리가 '목표 수량 − 체결 수량'을 시도 2로 보냅니다.
  권장은 (가) — 시도 번호 규칙과 하루 건수 셈을 건드리지 않습니다. 어느 쪽이든 회전율 멈춤 판정(`RealTradeRebalance`)의 입력이 달라지지 않는지 `RealTradeRebalanceTest` 전부와 '안전 고정 시험'이 그대로 통과해야 합니다.
- 검증 방법: `RealTradePlannerTest`에 '현금이 목표 수량에 모자란 매수 + 같은 계획의 매도 → 줄인 주문 대신 `deferred-cash`'. `RealTradeJobDbTest`의 위 사례를 이어 — 첫 주기 뒤 매도 체결·대금 반영 → 다음 주기에 그 종목의 온전한 수량 매수가 나감.
- 기대값이 바뀌는 기존 시험: `rebalanceExemptFollowupSendsDeferredBuys`의 첫 주기 기대(그 종목 92주 매수)가 '미룸'으로 바뀝니다(D-3이 (가)로 승인됐을 때만).
- 밖에서 보이는 동작 변화: **실제 돈의 주문**이 달라짐 — 매도가 함께 있는 날의 일부 매수가 한 주기(30초) 뒤에 온전한 수량으로 나감. ADR 0028에 덧붙입니다.
- 답이 없으면: 고치지 않고 승인 대기에 둡니다.

#### QA-1016 [S4] flex 틱이 태스크를 차례로 돌려 긴 태스크가 발표 직후 수집을 늦춤

## 8. 개선 제안 (판단 기준에 해당하지 않아 고치지 않음)

1. 수집기 이미지에 '적용할 마이그레이션의 최대 번호'를 새겨, 옛 이미지가 새 `db/migrations`를 적용하지 않게 하기(QA-1015의 근본 수정).

3. `/institutions?cik=<CIK>`를 받아 기관 상세의 링크가 같은 기관을 열게 하기.
4. 배포 요약에 떠 있는 태그로 받는 이미지(postgres·caddy)의 실제 판을 적기.
5. `.env.example`의 `DATABASE_PASSWORD` 기본값을 `setup.sh`가 무작위로 만들게 하기(포트는 루프백뿐이지만 같은 compose 망의 다른 컨테이너에서는 그 값으로 붙음).
6. GitHub Actions를 태그가 아니라 커밋 SHA로 고정하기(권한은 읽기뿐이고 비밀값을 쓰지 않아 급하지 않음).
7. 지금 코드가 읽지 않는 `certs/rds-ap-northeast-2-bundle.pem`(AWS 데모 시절의 공개 CA 묶음) 정리.

9. ISA 쓰기 요청(`POST /api/manual/isa/trades` 등)에 시간 한도와 중복 방지 열쇠 두기(지금은 화면의 `busy`로만 막음 — 응답을 못 받은 뒤 다시 적으면 두 번 들어가고 '되돌리기'로 고침).
10. 화면 시험이 `apiGetShared`를 통째로 목으로 두는 관행 때문에 공유 GET의 실제 동작을 지나는 시험이 없음 — QA-1008의 시험을 본보기로 `fetch` 수준 목 시험을 늘리기.

## 12. QA로 넘길 것

**변경이 집중될 영역**: 보안 공지 기능(수집·버전 목록·판정 — 무엇이 바뀌는지는 최종 보고서에), 관심 대상의 새 글 수·알림(스키마 V45 + 세 층), 화면의 API 클라이언트(`lib/api.ts` — 모든 화면의 다시 읽기에 닿음), `deploy.sh`의 가드 순서.

**테스트가 부족한 경로**
- 화면: `apiGetShared`의 실제 합류 동작을 지나는 화면 시험이 없음. 직접 시험이 없는 훅(`useSec13fFavorites`·`useInfoSearchExcludes`·`useInfoSearchLinks`·`useRemembered`·`useKrOfficialHolidays`). `lib/api.ts`의 시간 상한은 응답 머리까지만 걸림(본문이 멈추는 경우).
- 실제 매매: 재선정 날의 3분 창 안에서 매도 체결 → 매수가 실제로 다 나가는지는 시계를 고정한 DB 시험으로 볼 수 없음. `RealTradeJobDbTest`의 재선정 시험은 `PaperMirrorService`를 목으로 둠 — 실제 규칙 계좌 결정 행과의 통합 확인은 다음 재선정(12-09 무렵)이 처음.
- 모의 매매: `KrStopFillStep.night()`의 갈래 일부(밤 사다리 기다림, 재기동 뒤 `nightWaiting` 유실), 한국 14:50 고정 판단 직전에 사건 판단이 끝난 경우, `PaperBriefingJob`의 응답 뒤 저장 실패, `ReviewMarket`의 단위 시험 없음.
- 정보 검색: 수집기와 백엔드의 새 글·알림 규칙을 층을 가로질러 보는 시험이 없음(QA-1011~1013이 각 층의 시험만 더함). 실제 AI 엔진 응답으로 본 요약·번역.
- 보안 공지: 합성 HTML → 수집기 해석 → 백엔드 판정을 한 번에 잇는 시험이 없음.
- 배포: 백업·복원과 `deploy.sh`의 상태 질의 시험은 `psql`이 있는 CI에서만 돎. 빌드 실패·기동 직전 가드 뒤의 작업 트리·이미지 태그 상태를 보는 시험이 없음.

**확인하지 못한 의심 사항**(계획 세션이 코드로 확인하지 않았거나 실행으로만 가릴 수 있는 것)
- 정보 수집 화면의 `href={item.url}`(`NewsSection`·`OverviewSection`·`Reader`)만 화면 쪽 스킴 검사가 없음. 수집기가 http(s)만 저장하고 React가 `javascript:`를 막는 것으로 읽히지만, 속보 수집 경로의 검사는 확인하지 못함.
- 종목 상세의 AI 요약 단추가 시세가 오기 전에도 눌려 검색어 없이 유료 요약이 나갈 수 있음(서버의 캐시 열쇠 미확인). 요약·번역 POST에 화면 쪽 시간 상한이 없음.
- `http._CHALLENGE_MARKERS`의 `_incapsula_resource`가 정상 페이지에도 있어, 본문 보기가 정상 기사를 '거부'로 보고 그 호스트를 6시간 닫을 수 있음(서버 로그의 차단 건을 실제 페이지와 대조해야 함).
- `SearchArticleService.minutesUntilSlot`이 잠금 밖에서 목록을 읽어 같은 사용자의 동시 요청에서 예외가 날 수 있음.
- `IntradayScheduler.fixedTime` — 한국 14:30~14:48에 끝난 사건 판단이 있으면 마감 전 고정 판단이 조용히 빠질 수 있음. `PaperBriefingJob.runLocked` — 과금 응답 뒤 저장이 실패하면 60초마다 다시 부를 수 있음.
- `RealTradeJob.fresh()`가 매수 가능 금액에서 진행 중 매수의 상한가 합을 한 번 더 뺄 수 있음(토스 응답을 봐야 확인 — QA-1018을 키우는 쪽).
